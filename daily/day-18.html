log bytes가 업무 side effect가 되기까지의 상태 소유자와 실패 창 · 이론 55분 + 실습 35분

한 줄 요약
poll()은 “broker에서 매번 record를 바로 읽는 함수”가 아니다. consumer network layer가 미리 가져와 local buffer에 둔 record batch bytes를 key/value deserializer로 객체화하고, max.poll.records만큼 application에 반환하는 경계다. 그 뒤의 업무 처리와 offset commit은 Kafka가 자동으로 하나의 원자 연산으로 묶어주지 않으므로 failure window를 따로 설계해야 한다.

1. 선수 용어 사전

Poll loopapplication이 poll(Duration)을 반복 호출해 record를 받고 처리하는 주 실행 루프. 단순 조회가 아니라 group liveness·callback·fetch 진행도 함께 전진시키는 경계다.
FetchRequestconsumer가 broker에 “각 partition의 이 offset부터 batch를 달라”고 보내는 Kafka protocol 요청.
Fetch position다음에 가져오거나 반환할 record의 offset을 나타내는 consumer 내부 위치. committed offset과 같지 않을 수 있다.
Committed offsetgroup이 재시작·rebalance 후 다시 시작할 위치로 Kafka의 __consumer_offsets에 저장한 checkpoint.
Deserializerwire의 byte 배열을 String, Avro 객체, Protobuf 객체 같은 application type으로 바꾸는 코드. schema 불일치가 여기서 poison pill이 된다.
Record batchbroker log·compression·fetch의 묶음 단위. fetch limit보다 첫 batch가 커도 consumer가 전진하도록 반환될 수 있다.
Local bufferfetch response로 받은 뒤 아직 application에 모두 반환하지 않은 record를 consumer process memory에 보관하는 영역.
Side effectDB update, API 호출, 파일 쓰기처럼 consumer process 밖의 상태를 바꾸는 업무 효과.
Poison pill현재 deserializer나 처리 코드가 계속 실패하는 특정 record. 같은 offset에서 재시작할 때마다 진행을 막을 수 있다.
Backpressure처리가 fetch보다 느릴 때 유입을 제한하거나 pause해 memory·lag 폭주를 막는 제어.
Lag보통 log end offset과 committed offset 또는 consumer position의 차이. 정의에 따라 의미가 달라 측정 기준을 함께 말해야 한다.

2. 왜 중요한가

“consumer가 느리다”는 한 문장에는 적어도 네 병목이 숨어 있다. broker가 fetch response를 늦게 만드는가, network bytes가 큰가, deserializer CPU·allocation이 비싼가, DB/API 처리가 느린가. 이 단계를 분리하지 않으면 consumer 수나 fetch 크기만 올려 장애를 증폭한다.

또한 poll()이 record를 반환한 순간, fetch position은 전진할 수 있지만 업무 처리는 아직 시작도 안 했다. 처리 완료 전 commit하면 유실 window, 처리 완료 후 commit하면 중복 window가 생긴다. 오늘은 commit 설정 자체보다 그 전 단계의 상태가 어디에 있고 언제 성공이 확정되는지 해부한다.

3. Architecture: broker log에서 업무 처리까지

1 · poll()application thread가 poll timeout과 함께 consumer 진입
↓ assignment·metadata·heartbeat 상태 진행
2 · Fetchbroker leader에 partition별 fetch position을 담은 FetchRequest
↓ fetch.min.bytes 또는 fetch.max.wait.ms 조건
3 · Responsebroker page cache/log에서 compressed record batch bytes 반환
↓ consumer local completed-fetch buffer
4 · Decodebatch CRC·decompression·record parse → key/value deserializer
↓ max.poll.records 범위로 ConsumerRecords 반환
5 · Processapplication validation → DB/API/file side effect
↓ 처리 시간·실패·retry·commit은 application 책임
6 · Next poll남은 local buffer를 반환하거나 다음 fetch를 기다리며 loop 반복
  1. poll 진입: consumer는 thread-safe하지 않다. 일반적으로 한 owner thread가 poll·position·commit 상태를 직렬화한다.
  2. fetch 요청: 한 request가 여러 assigned partition을 포함하며 consumer는 broker node별 fetch를 병렬 수행할 수 있다.
  3. broker 응답: fetch.min.bytes가 채워지거나 wait deadline이 오면 반환한다. 작은 값은 latency, 큰 값은 batch efficiency 쪽이다.
  4. decode: 압축을 풀고 header와 record를 검사한 뒤 사용자 deserializer가 객체를 만든다. 이 구간은 consumer CPU·heap·GC 비용이다.
  5. processing: Kafka client가 업무 함수의 성공을 알지 못한다. 따라서 side effect와 commit 사이 원자성은 별도 설계가 필요하다.
  6. loop: max.poll.records보다 많이 fetch해 cache해도 poll마다 일부만 반환한다. fetch와 poll 반환량은 독립된 두 제어면이다.

Fetch 크기 제어의 계층

fetch.max.bytes는 fetch response 전체의 대략적 상한이고, max.partition.fetch.bytes는 partition별 상한이다. 둘 다 첫 non-empty partition의 첫 record batch가 더 크면 전진 가능성을 위해 그 batch를 반환할 수 있어 절대 hard limit가 아니다. 반면 max.poll.records는 이미 fetch된 cache에서 application에 한 번에 반환할 record 수만 제한하며 network fetch량을 줄이지 않는다.

이 구분은 heap sizing에 중요하다. assigned partition 수 × per-partition fetch 범위 × 병렬 broker fetch × decompression 후 object 크기를 고려해야 한다. wire에서 1MiB로 압축된 batch가 heap 객체로는 훨씬 커질 수 있다.

5. 실무 설계 판단

상황판단이유·trade-off
DB 처리 20ms/recordmax.poll.records를 poll interval 예산 안으로 제한, batch DB write 검토500개 직렬 처리면 10초. 처리량·메모리·rebalance 안전을 함께 맞춘다.
저유량·throughput 우선fetch.min.bytes를 높이고 wait budget 측정큰 response로 syscall/request 비용 감소, 저유량 latency 증가.
큰 message topictopic max batch와 consumer partition/total fetch 설정 정렬progress 예외가 있어도 큰 decompress·allocation으로 OOM 가능.
poison pill원본 bytes·topic/partition/offset·schema ID를 격리하고 명시 정책 적용무한 재시도는 partition 전체 HOL blocking, 무조건 skip은 데이터 유실.

Best practice: fetch latency/size/rate, records-lag, time-between-poll, processing latency, deserialize error, sink latency를 한 dashboard에서 단계별로 본다. poll thread와 worker pool을 분리한다면 partition별 완료 frontier를 추적하고 pause/resume·bounded queue·rebalance drain을 함께 설계한다.

Anti-pattern: max.poll.records를 내리면 network memory도 자동 감소한다고 믿기, deserialization error를 catch하지 못한 채 process 재시작만 반복하기, lag 0을 업무 처리 성공으로 간주하기, consumer instance를 여러 thread에서 공유하기.

Version/engine 경계: Kafka 4.3에는 classic과 consumer group protocol이 공존하며 heartbeat 설정 주체가 다를 수 있다. 그러나 오늘의 fetch bytes→deserialize→poll 반환 data path 핵심은 group protocol 선택과 분리해서 이해한다. framework(Spring Kafka, Flink, Connect)는 poll loop를 감추므로 container concurrency·ack mode·error handler의 실제 offset semantics를 문서로 확인해야 한다.

7. 35분 실습: fetch·decode·poison pill 관찰

실행 전 예측
max.poll.records=2는 broker가 매 fetch에서 정확히 두 record만 보내게 할까? 아니면 consumer가 더 많이 fetch해 cache한 뒤 두 개씩 반환할까? 또 String으로 쓴 payload를 IntegerDeserializer로 읽으면 어느 단계에서 멈출지 적는다.

사전 조건: 저장소 루트, Docker 실행 가능, local Kafka 4.3.1 단일 broker. production topic에는 실행하지 않는다.

  1. 환경·topic:
    make up make smoke make topic-create TOPIC=day18.poll
  2. 5개 record 입력:
    make produce TOPIC=day18.poll대화형 입력에 event-1부터 event-5까지 한 줄씩 넣고 종료한다.
  3. 작은 poll 반환량 관찰:
    docker compose exec broker /opt/kafka/bin/kafka-console-consumer.sh \ --bootstrap-server localhost:9092 --topic day18.poll \ --group day18-string --from-beginning --max-messages 5 \ --consumer-property max.poll.records=2 \ --property print.partition=true --property print.offset=trueCLI 출력은 빠르게 이어질 수 있으므로 두 개씩 보이는 UI만으로 fetch량을 단정하지 않는다.
  4. 실패 주입 — 잘못된 deserializer:
    docker compose exec broker /opt/kafka/bin/kafka-console-consumer.sh \ --bootstrap-server localhost:9092 --topic day18.poll \ --group day18-bad --from-beginning --max-messages 1 \ --consumer-property value.deserializer=org.apache.kafka.common.serialization.IntegerDeserializerString bytes 길이가 Integer 형식과 맞지 않아 deserialization exception이 나는지, 오류에 partition·offset 단서가 있는지 기록한다.
  5. 안전 복구: 같은 group을 무작정 offset reset하지 말고 StringDeserializer 기본값으로 다시 실행해 원본 record가 정상인지 확인한다. 실제 서비스라면 raw bytes·schema ID를 격리하고 승인된 skip/DLQ 정책을 적용한다.

예상 관찰: 정상 consumer는 partition/offset과 5개 문자열을 읽는다. bad consumer는 fetch 자체가 아니라 byte→Integer 변환 단계에서 실패한다. 이 실패는 broker에 record가 없어서가 아니며, 재시작만 하면 같은 offset을 다시 만나 반복될 수 있다.

자주 나는 오류와 해결: service 이름은 broker다. topic이 이미 있으면 --if-not-exists라 안전하다. CLI가 deserializer 옵션을 덮어쓰는 버전이면 출력된 effective error와 --help를 확인하고, application client 실험으로 옮긴다. group이 이전 offset을 가졌다면 새 group 이름을 쓴다.

Cleanup:
docker compose exec broker /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server localhost:9092 --delete --topic day18.poll make down

8. 놓치기 쉬운 함정

  • poll timeout과 max poll interval은 다르다: 전자는 한 호출이 기다리는 시간, 후자는 group member가 다음 poll을 호출해야 하는 liveness 상한이다.
  • max.poll.records는 fetch bytes knob가 아니다: cache에서 application으로 꺼내는 수만 제한한다.
  • 첫 batch progress 예외: 설정 byte limit을 절대 메모리 상한으로 계산하면 위험하다.
  • position 전진은 처리 성공이 아니다: poll 반환 뒤 crash하면 commit 정책에 따라 재처리 또는 skip window가 생긴다.
  • deserializer는 신뢰 경계다: 외부 payload로 객체를 만들므로 size limit·schema validation·오류 격리가 필요하다.
  • worker pool은 공짜 병렬화가 아니다: partition ordering, 완료 frontier, commit, rebalance drain을 새로 책임져야 한다.

9. 대기업 기술 면접 질문 3개

Q1. poll() 한 번의 내부 흐름을 상태 소유자까지 설명해보세요.
좋은 답변 구조: assignment/position → broker별 FetchRequest → fetch min/wait → batch bytes/local cache → decompression/deserialization → max.poll.records 반환 → position과 committed offset 분리 → application side effect failure window.

Q2. consumer lag이 오르는데 CPU는 낮습니다. 어떻게 진단합니까?
좋은 답변 구조: 요구 SLO·유입률 확인 → data/control path 분리 → fetch latency/rate/size·throttle·assignment → poll interval·sink latency → partition skew → 증거 기반 canary → rollback과 replay. consumer 수부터 늘리지 않는다.

Q3. 초당 10k records, 처리 5ms/record인 consumer를 설계하세요.
좋은 답변 구조: record 크기·key ordering·partition 수·sink batch 가능성 질문 → 직렬 한 partition 약 200 records/s 가정 → 필요한 병렬성 계산 → max.poll.records × p99가 poll interval 예산 내인지 검증 → bounded worker/pause-resume → commit frontier·idempotent sink → poison pill·rebalance 복구.

  2. in-flight=5는 무엇의 수인가?
