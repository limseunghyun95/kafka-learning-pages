Kafka Connect worker·task·offset·converter

누가 상태를 갖고, 어느 지점에서 성공이 확정되는가 · 이론 80분 + 실습 30분

한 줄 요약
Connector는 일을 나누고, Task는 실제 record를 옮기며, Worker는 lifecycle·client·offset을 실행하고, Converter는 Connect의 Schema+Value와 Kafka의 byte[] 경계를 번역한다. 장애를 풀려면 “어느 프로세스가 죽었나”보다 “어느 상태가 어디까지 확정됐나”를 먼저 묻는다.

1. 선수 용어 사전

Kafka ConnectKafka와 DB·object storage·search engine 같은 외부 시스템 사이의 data 이동을 표준화한 runtime. Connector plugin을 실행하고 확장·복구·offset 관리를 맡는다.
WorkerConnect runtime JVM process. Connector와 Task instance를 올리고, producer/consumer, converter, REST, offset/status 저장을 제공하는 실행 노드다.
Connector외부 시스템을 발견하고 작업을 어떻게 나눌지 결정하는 control-plane plugin. 실제 record 하나하나를 지속적으로 옮기는 주체는 보통 Task다.
Task실제 data 이동을 수행하는 병렬 실행 단위. SourceTask는 외부에서 poll해 Kafka로 보내고, SinkTask는 Kafka record를 받아 외부 시스템에 쓴다.
Source partition외부 source의 논리적 shard 식별자. 예: DB table+server, file path. Kafka partition과 같은 개념이 아니며 connector가 정의한다.
Source offset외부 source에서 어디까지 읽었는지 나타내는 위치. 예: binlog file+position. Kafka consumer offset과 형식·소유자가 다르다.
ConverterConnect 내부의 Schema+Value와 Kafka record의 byte[] 사이를 양방향 변환하는 plugin. key와 value converter를 따로 설정한다.
Standalone / DistributedStandalone은 한 process와 local offset file 중심이라 개발·작은 작업에 적합하다. Distributed는 여러 worker가 group을 이루고 config·offset·status를 Kafka internal topic에 저장해 재배치·복구한다.
RebalanceWorker membership이나 connector/task 구성이 바뀔 때 실행 ownership을 다시 배치하는 과정. 짧은 정지와 중복 가능 구간을 만든다.
Poison pillConverter 또는 connector가 처리하지 못해 같은 위치에서 계속 실패하게 만드는 record. DLQ는 격리 수단이지 원인 해결이나 재처리 책임의 종착지가 아니다.

2. 왜 중요한가

Connect는 “설정 몇 줄로 DB를 Kafka에 붙이는 도구”처럼 보이지만, production에서는 분산 상태 기계다. Source system의 위치, Kafka produce 결과, source offset commit이 서로 다른 시점에 끝난다. Sink에서는 외부 side effect와 Kafka consumer offset commit이 원자적이지 않을 수 있다. 이 틈이 중복·유실의 failure window다.

또한 scale-out 단위는 worker가 아니라 실제로 생성된 task와 upstream/downstream partition이다. Worker를 10대로 늘리고 tasks.max=100을 줘도 connector가 source shard 하나만 발견하면 task 하나뿐일 수 있다. 반대로 task 수만 늘리면 DB connection·API quota·consumer group rebalance 비용이 커진다.

면접과 장애 대응에서 중요한 질문은 네 가지다. 상태 소유자는 누구인가, 불변식은 무엇인가, 성공은 어느 지점에서 확정되는가, crash 후 어느 지점부터 replay되는가.

왜 Connector와 Task를 분리했는가

Connector는 전체 외부 topology를 알아야 한다. 어떤 table이 생겼는지, 어떤 shard를 몇 task로 나눌지 판단한다. Task는 자기에게 주어진 작은 config만 알고 hot loop에서 I/O를 수행한다. 이 분리는 control path를 비교적 가볍게 유지하고, task만 여러 worker에 분산할 수 있게 한다.

tasks.max는 scheduler가 무조건 채워주는 replica count가 아니다. Connector의 taskConfigs(maxTasks)가 반환한 config 수, source shard 수, sink Kafka partition 수가 실질 병렬성의 상한이다. 병렬성은 대략 min(tasks.max, connector가 나눌 수 있는 단위, downstream 허용 동시성)으로 생각한다.

Converter는 Serializer와 같은가

둘 다 bytes 경계를 다루지만 추상화가 다르다. 일반 Kafka client의 Serializer는 application object→byte[]에 초점을 둔다. Connect Converter는 connector가 포맷별 코드를 몰라도 되도록 Connect Schema+Value↔byte[] 계약을 제공한다. Source에서는 Task 뒤, producer 앞에 있고, Sink에서는 consumer 뒤, Task 앞에 있다. 그래서 sink poison pill은 SinkTask.put()에 도달하기 전에 converter에서 실패할 수 있다.

State transition과 성공 확정

Connector/task는 보통 UNASSIGNED→RUNNING→PAUSED/FAILED/STOPPED 같은 운영 상태를 가진다. REST config 성공, RUNNING 상태, offset 증가, destination side effect 성공은 서로 다른 사건이다. Source record의 “완료”도 외부 poll, conversion, Kafka ack, source offset flush라는 여러 관측점이 있다. SLO와 alert는 단일 RUNNING flag가 아니라 input rate·success rate·error rate·offset age·task restart·destination latency를 함께 본다.

5. 실무 설계 판단

  • Distributed 기본: Production shared service는 distributed mode를 기본으로 하고 config/offset/status topic을 명시적으로 생성해 replication, partition, compaction, ACL을 검토한다. Single-broker lab에서만 replication factor 1을 쓴다.
  • Connector cluster 분리: Security principal, failure domain, plugin 충돌, blast radius, workload 특성이 다르면 worker cluster를 분리한다. 모든 connector를 한 거대 cluster에 넣지 않는다.
  • Plugin supply chain: Plugin version, checksum, CVE, Java/Kafka compatibility를 image에 고정하고 rolling upgrade 전 canary를 둔다. Runtime에 임의 JAR를 복사하지 않는다.
  • Capacity: Task 수만 보지 말고 task별 records/sec, batch size, poll latency, CPU, heap, GC, network, external connection quota를 측정한다. Scale-out 전에 connector가 실제로 task를 더 만들 수 있는지 확인한다.
  • Converter ownership: Worker default와 connector override 우선순위를 문서화한다. Key와 value를 동일 converter로 가정하지 말고 schema registry endpoint·auth·subject 전략도 배포 artifact로 관리한다.
  • Offset reset: Pause/stop, impact range, destination idempotency, replay 예상 건수, rollback plan이 없는 상태에서 offset을 임의 수정하지 않는다. Kafka 4.3의 connector offset management endpoint도 stopped 상태 제약과 connector별 의미를 확인한다.
  • Error handling: errors.tolerance=all은 가용성을 높일 수 있지만 data loss처럼 보이는 silent skip을 만든다. DLQ topic ownership, retention, PII, alert, replay tool, 최종 disposition을 함께 설계한다.
  • Exactly-once 범위: Source exactly-once 지원 여부·worker mode·connector 구현을 확인한다. Sink의 외부 시스템까지 자동 원자성이 확장된다고 단정하지 않는다.

Version 차이: 이 자료는 Apache Kafka 4.3.1 문서를 기준으로 한다. Connector vendor마다 offset shape, task split, retry/DLQ, transaction, plugin isolation, supported REST 동작이 다르므로 connector 문서와 실제 plugin version을 별도 고정해야 한다.

Anti-pattern: RUNNING만 보고 정상 판정, tasks.max를 실제 task 수로 오해, source offset과 Kafka offset 혼동, worker disk에만 중요 상태 저장, config/status/offset topic 자동 생성 방치, converter 변경을 connector 변경과 분리 배포, 무한 retry로 poison pill에 전체 task를 묶어두기.

7. 20~40분 실습: Task 수와 source offset failure window 관찰

목표: Standalone worker에서 FileStreamSourceConnector를 실행한다. tasks.max=2여도 file 하나는 task 하나인 점, StringConverter가 bytes 경계를 담당하는 점, offset file 삭제가 replay와 중복을 만드는 점을 관찰한다.

사전 조건: 이 저장소 root, Docker Desktop, 약 30분. Production 설계가 아니라 상태 경계를 눈으로 보는 single-broker lab이다.

0) 실행 전 예측

  1. tasks.max=2이면 file 하나를 두 task가 절반씩 읽을까?
  2. Kafka topic에 들어간 value는 Connect 내부 String 객체인가, byte[]인가?
  3. Source offset file을 지우고 worker를 재시작하면 이미 보낸 line은 어떻게 될까?

2) Worker·connector config 생성

docker compose exec -T broker bash -lc \
  'cat > /tmp/day38-worker.properties' <<'EOF'
bootstrap.servers=localhost:9092
key.converter=org.apache.kafka.connect.storage.StringConverter
value.converter=org.apache.kafka.connect.storage.StringConverter
offset.storage.file.filename=/tmp/day38.offsets
offset.flush.interval.ms=3000
plugin.path=/opt/kafka/libs/connect-file-4.3.1.jar
plugin.discovery=only_scan
EOF

docker compose exec -T broker bash -lc \
  'cat > /tmp/day38-file-source.properties' <<'EOF'
name=day38-file-source
connector.class=org.apache.kafka.connect.file.FileStreamSourceConnector
tasks.max=2
file=/tmp/day38-input.txt
topic=day38-connect-output
EOF

docker compose exec broker bash -lc \
  'printf "order-1\n" > /tmp/day38-input.txt'

예상: Worker default converter가 key/value의 Connect String을 Kafka byte[]로 바꾼다. FileStream connector는 file 하나를 안전하게 두 reader가 나눌 수 없으므로 실제 task는 하나일 가능성이 높다.

3) Standalone worker 실행·관찰

docker compose exec -d broker bash -lc \
  'nohup /opt/kafka/bin/connect-standalone.sh \
    /tmp/day38-worker.properties \
    /tmp/day38-file-source.properties \
    >/tmp/day38-connect.log 2>&1 & echo $! >/tmp/day38-connect.pid'

docker compose exec broker bash -lc \
  'tail -80 /tmp/day38-connect.log'

docker compose exec broker /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 \
  --topic day38-connect-output --from-beginning \
  --max-messages 1 --timeout-ms 10000

예상 관찰: Log에서 connector와 task 0의 start를 찾고 consumer에서 order-1을 본다. tasks.max=2는 두 task 생성 보장이 아니다. Kafka log에는 converter가 만든 bytes가 저장되며 console consumer가 이를 문자열로 보여줄 뿐이다.

8. 놓치기 쉬운 함정

  • Connector RUNNING ≠ Task RUNNING: connector control instance와 data-moving task 상태를 따로 본다.
  • tasks.max ≠ task count: connector가 분할 가능한 source unit보다 늘어날 수 없다.
  • Source offset ≠ Kafka offset: source offset은 외부 위치이고, sink 쪽 Kafka offset은 consumer group progress다.
  • Converter 위치: SourceTask는 Connect data를 내고 converter 뒤에 Kafka bytes가 생긴다. Sink에서는 converter 실패 시 SinkTask가 record를 보지도 못한다.
  • Worker default 숨김: Connector config에 converter가 없어도 worker default가 작동한다. Cluster migration 때 default 차이가 사고를 만든다.
  • Offset은 backup이 아님: Compact topic도 잘못된 tombstone·ACL·retention·cluster loss에서 보호하려면 DR와 복구 절차가 필요하다.
  • DLQ 만능론: Serialization/converter 단계, connector 자체 오류, source connector에는 동일한 DLQ 의미가 적용되지 않을 수 있다.
  • 무한 retry: 한 poison pill이 task thread와 partition progress를 영구 정지시킬 수 있다.
  • 외부 side effect: Kafka offset commit과 DB/API write가 자동 원자적이라고 가정하지 않는다.

9. 대기업 기술 면접 질문

Q1. Worker 3대, tasks.max=20인데 task가 4개뿐이다. 왜이며 어떻게 확장할까?

좋은 답변 구조: Worker·Connector·Task 정의 → tasks.max는 상한이라는 불변식 → source shard/Kafka partition/connector taskConfigs 확인 → task별 throughput·외부 quota 수치화 → shard/partition/connector split과 worker scale의 순서 → rebalance·connection 비용까지 방어한다.

Q2. Source connector가 crash 후 일부 record를 중복 발행했다. 정확히 어떤 window인가?

좋은 답변 구조: Source partition+offset 정의 → poll→convert→produce ack→offset flush 순서 → ack 후 flush 전 crash라는 가설 → connector logs·producer metrics·offset topic evidence → idempotent destination/reconciliation → exactly-once 지원 범위와 대안까지 설명한다.

Q3. Converter를 JSON에서 Avro로 바꾸는 무중단 migration을 설계하라.

좋은 답변 구조: Topic의 기존 bytes와 consumer fleet inventory → worker default vs connector override → mixed-format 허용 여부와 schema registry dependency → 새 topic dual-publish 또는 tolerant reader-first 전환 → canary·lag·DLQ → rollback과 replay 기간 → key converter가 partition routing에 미치는 영향까지 답한다.

10. 복습과 정답

어제 내용 회상 3문제

  1. Backward compatibility를 writer/reader 방향으로 말하라.
  2. Latest-only compatibility가 오래된 replay를 보장하지 못하는 이유는?
  3. Schema syntax는 같지만 semantic breaking change가 되는 예를 하나 들어라.
어제 정답/채점: ① 새 reader가 old writer data를 읽음(2점). ② 후보를 직전 version과만 검사해 더 오래된 writer schema와의 gap을 놓칠 수 있음(3점). ③ type은 같지만 통화 단위·timezone·enum 의미를 바꾸는 예(2점).

오늘 확인 문제 3개

  1. Connector와 Task의 책임을 한 문장씩 구분하라.
  2. Source offset과 sink의 Kafka consumer offset은 각각 무엇을 가리키는가?
  3. SinkTask가 DB write 후 offset commit 전에 죽으면 어떤 결과와 대응이 필요한가?
오늘 정답/채점: ① Connector는 작업 분할·재구성, Task는 실제 data I/O(3점). ② Source offset은 외부 source 위치, sink offset은 Kafka topic progress(3점). ③ Replay로 중복 side effect 가능; idempotency key/upsert/dedup과 reconciliation 필요(3점). 총 9점 중 7점 이상이면 통과.
