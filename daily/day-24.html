APACHE KAFKA 4.3 · WEEK 4 / DAY 24 · DURABILITY

acks=all + min.insync.replicas

성공 응답의 조건과 쓰기 중단 정책을 RF=3 장애 표로 방어하기 · 이론 70분 + 실습 30분

한 줄 요약
acks=all은 leader가 현재 ISR 전체의 복제를 기다리는 producer 요청 조건이고, min.insync.replicas는 ISR이 이 수보다 작으면 그 쓰기를 거부하는 최소 안전선이다. RF=3·min ISR=2라면 한 replica 장애까지 쓰되, 두 번째 replica를 잃으면 가용성을 포기하고 acknowledged record의 내구성을 지킨다.

1. 선수 용어 사전

Acknowledgment요청을 받았고 요구 조건까지 처리했다는 응답. 줄여서 ack라고 한다. TCP 전송 성공, broker local append, replica 복제 성공은 서로 다른 ack 단계다.
acksProducer가 ProduceRequest를 완료로 판단하기 위해 broker에 요구하는 응답 수준. 현재 공식 값은 0, 1, all(또는 -1)이다.
Replication factorRF. Partition에 배정된 전체 replica 수. RF=3은 세 copy의 배치 계획이지 현재 세 copy가 모두 동기화됐다는 뜻이 아니다.
ISRIn-Sync Replicas. 현재 leader를 충분히 따라온 동적 replica 집합. Leader도 ISR 구성원으로 센다.
min ISRmin.insync.replicas의 줄임말. acks=all 쓰기를 허용할 최소 ISR 크기다. “몇 개만 ack 받으면 된다”가 아니라 admission floor다.
HWHigh Watermark. 복제 안전 조건을 만족해 consumer에게 공개 가능한 next-offset 경계. Leader LEO와 다르다.
Durability성공했다고 답한 데이터가 장애 뒤에도 남는 성질. “디스크에 썼다” 하나가 아니라 실패 domain과 동시에 잃을 수 있는 copy를 포함해 정의한다.
Availability요청을 받아 성공 또는 유효한 응답을 계속 제공하는 성질. min ISR을 높이면 특정 장애에서 write availability를 의도적으로 포기할 수 있다.
Retriable error재시도하면 성공할 수 있는 일시 오류. 하지만 첫 시도의 결과가 불명확할 수 있으므로 idempotence 없이 무작정 재시도하면 중복 위험이 있다.
ELREligible Leader Replicas. Kafka 4.x에서 strict min ISR 안전성을 이용해 일부 non-ISR replica를 안전한 선출 후보로 추적하는 기능.

2. 왜 중요한가

acks=all만 켜고 min.insync.replicas=1을 그대로 두면 ISR이 leader 하나로 줄어든 상태에서도 쓰기가 성공할 수 있다. 그 직후 마지막 최신 leader를 잃으면 acknowledged record를 가진 살아 있는 replica가 없을 수 있다. 반대로 min ISR을 RF와 같게 두면 하나의 느린 replica만으로도 쓰기가 오래 중단된다.

따라서 두 설정은 성능 숫자가 아니라 어떤 장애까지 성공을 약속할 것인지 정하는 정책이다. RF=3·min ISR=2는 “한 replica 장애 때는 두 ISR 모두에 복제해 계속 쓰고, ISR이 하나가 되면 쓰기를 거부한다”는 선택이다. 이는 모든 workload의 정답이 아니라 흔한 production 출발점이다.

면접에서는 “acks all이면 안전합니다”로 끝내면 부족하다. 요구 failure domain, ISR 전이, pre/post append 오류, timeout의 unknown outcome, idempotent retry, consumer visibility, cross-AZ 비용까지 설명해야 설계 판단을 했다는 인상을 준다.

3. Architecture: ProduceRequest가 성공하기까지

1 · Producerbatch + requiredAcks=-1 → P0 leader B1
↓ DATA PATH · ProduceRequest
2 · Pre-check현재 ISR 크기 ≥ min ISR인가? 아니면 append 전 거부
↓ Leader local append · LEO 전진
3 · ReplicateB2·B3 follower fetch → local append → progress 보고
↓ 현재 ISR 전체 복제 + min ISR 조건 유지
4 · CommitHW가 batch 뒤로 전진 → ProduceResponse success
↔ CONTROL PATH · ISR shrink/expand·leader epoch
5 · KRaftController가 ISR·leader metadata 전이를 확정·전파
  1. Client contract: producer Sender는 batch를 현재 partition leader에 보내고 response를 기다린다. acks=all은 broker가 요구 복제 조건 전에 success를 반환하지 못하게 한다.
  2. Admission: leader는 append 전 ISR 크기가 min ISR보다 작은지 검사한다. 미달이면 NotEnoughReplicas 계열 오류로 쓰기를 받지 않는다.
  3. Append and pull: leader가 local log에 append한 뒤 followers가 fetch한다. min ISR=2라고 해서 ISR=3일 때 둘만 복제하고 끝나는 것이 아니다. 공식 4.3 문서상 acks=all은 ISR 전체를 기다린다.
  4. State change: 대기 중 ISR이 바뀔 수 있다. 미달이 append 뒤 발견되면 NotEnoughReplicasAfterAppend처럼 “local append는 있었지만 성공 확정은 안 됨”을 나타내는 오류가 가능하다.
  5. Success: 요구 복제가 완료돼 HW가 batch 뒤로 전진하고 min ISR 조건이 유지될 때 success response가 돌아온다. 응답 packet 유실 시 server 성공과 client timeout이 동시에 가능하므로 결과는 다시 불명확해질 수 있다.

Broker가 죽었다고 ISR이 즉시 줄어드는 것은 아니다. Failure detector와 replica.lag.time.max.ms, controller state 전이 동안 request가 대기하거나 timeout될 수 있다. ISR이 3→2로 확정된 뒤에는 남은 두 ISR로 성공할 수 있지만, 그 사이의 latency spike를 장애 행렬에 포함해야 한다.

오류가 말해 주는 failure window

NotEnoughReplicas: append 전 현재 ISR이 min ISR보다 작다는 검사에 걸린 경우다. 해당 시도의 batch가 leader log에 append되지 않았다고 추론할 수 있다. NotEnoughReplicasAfterAppend: append 후 낮은 ISR이 발견된 retriable 오류다. Local append는 이미 일어났을 수 있으므로 결과를 “무조건 실패·미기록”으로 취급하면 안 된다.

Timeout·disconnect: broker가 성공 조건을 만족하고 response를 보냈지만 packet이 사라졌을 수도 있고, 복제가 끝나지 않았을 수도 있다. Client 관점에서는 unknown outcome이다. Kafka producer idempotence는 PID·epoch·partition sequence로 같은 batch retry의 broker-log 중복을 막는다. 다만 외부 DB side effect까지 자동으로 exactly-once가 되는 것은 아니다.

OS·network·분산 시스템 비용

acks=all latency는 leader local append만이 아니라 ISR follower의 fetch round-trip, inter-broker TCP, follower page cache append, leader progress 관찰까지 포함한다. 가장 느린 ISR의 disk await·network loss·GC pause가 p99를 끌어올릴 수 있다. Lagging follower를 ISR에서 빼면 latency는 회복되지만 copy margin은 줄어든다.

min ISR은 consensus quorum 그 자체가 아니다. RF=3·min ISR=2에서는 수치상 과반이지만 RF=5·min ISR=2는 과반이 아니다. 또한 replica 두 개가 같은 rack이나 power domain에 있으면 “두 copy”가 한 장애로 동시에 사라진다. 수량 threshold와 failure-domain diversity를 별도로 설계한다.

Kafka 4.x ELR의 strict min ISR

Kafka 4.0부터 ELR이 제공되고 새 Kafka 4.1+ cluster에서는 기본 활성화되는 구성이 있다. ELR 활성화 시 ISR 크기가 min ISR보다 작으면 data partition HW가 전진하지 않는 strict min ISR 규칙이 핵심이다. 그 안전성 덕분에 controller가 일부 non-ISR replica를 ELR로 추적할 수 있다. Kafka 4.3 운영에서는 feature level과 cluster/topic min ISR 적용 위치를 확인한다.

Best practice: Topic 중요도별 RF·min ISR·acks 정책을 코드와 review 대상으로 관리한다. Producer에서 idempotence, delivery timeout, request timeout, retry를 함께 검토한다. UnderMinIsrPartitionCount, AtMinIsrPartitionCount, UnderReplicatedPartitions, ISR shrink rate, produce request latency·error rate, disk/network를 같은 dashboard에 둔다. 정기 chaos test로 broker/AZ 하나 상실 시 예상 행렬을 검증한다.

Anti-pattern: 모든 topic에 RF3만 적용하고 min ISR default 1 방치, 장애 때 증거 없이 min ISR을 1로 낮추기, acks=all을 “모든 assigned replica 영구 보존”으로 설명, acks=1에서 min ISR이 동일한 보호를 준다고 기대, timeout을 확정 실패로 취급해 non-idempotent retry.

Edge case: ISR shrink 전후 in-flight request, follower가 매우 느리지만 아직 ISR인 구간, topic override와 cluster default 충돌, RF보다 큰 min ISR 오설정, transaction/internal topic의 별도 min ISR, rack 정보 누락, managed service가 broker-level 설정을 감추는 경우를 확인한다.

Version/engine 차이: Kafka 4.3 producer의 acks 유효값은 0, 1, all/-1이다. 다른 ack 모드를 제안하는 미채택 KIP를 현재 기능처럼 쓰지 않는다. ELR 활성화 시 min ISR의 cluster-level 관리와 HW 규칙이 달라질 수 있으므로 공식 4.3 ELR 문서를 우선한다. ZooKeeper legacy는 control path가 다르다.

7. 30분 실습: min ISR이 쓰기를 멈추는 순간

실행 전 예측
RF=1 topic에 min ISR=2를 설정하고 acks=all로 보내면 leader는 local append를 할까, append 전에 거부할까? min ISR을 1로 돌리면 같은 producer 조건에서 무엇이 달라질까?

사전 조건: 저장소 루트, Docker, 공식 Kafka 4.3.1 단일 broker KRaft. 이 실습은 의도적인 RF<min ISR 오설정으로 pre-append 거부를 빠르게 관찰한다. Production에서는 이런 구성을 만들지 않는다.

Step 1 · RF=1, min ISR=2 topic

make up docker compose exec broker /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server localhost:9092 --create --if-not-exists \ --topic day24.minisr --partitions 1 --replication-factor 1 \ --config min.insync.replicas=2 docker compose exec broker /opt/kafka/bin/kafka-configs.sh \ --bootstrap-server localhost:9092 --entity-type topics \ --entity-name day24.minisr --describe

예상: Topic override에 min.insync.replicas=2가 보인다. 현재 Apache Kafka는 이 위험한 불일치가 구성될 수 있으므로 CI policy에서 1 ≤ min ISR ≤ RF를 별도로 검사하는 것이 안전하다.

Step 2 · 실패 주입: acks=all produce

printf 'must-fail\n' | docker compose exec -T broker \ /opt/kafka/bin/kafka-console-producer.sh \ --bootstrap-server localhost:9092 --topic day24.minisr \ --producer-property acks=all \ --producer-property delivery.timeout.ms=5000 \ --producer-property request.timeout.ms=3000

예상: ISR은 leader 하나뿐이라 min ISR 2를 만족하지 못하고 NOT_ENOUGH_REPLICAS 또는 이에 대응하는 producer exception이 난다. 짧은 delivery timeout은 실습이 기본 재시도로 오래 멈추는 것을 제한한다.

Step 3 · 안전선과 RF를 일치시켜 성공

docker compose exec broker /opt/kafka/bin/kafka-configs.sh \ --bootstrap-server localhost:9092 --entity-type topics \ --entity-name day24.minisr --alter \ --add-config min.insync.replicas=1 printf 'now-succeeds\n' | docker compose exec -T broker \ /opt/kafka/bin/kafka-console-producer.sh \ --bootstrap-server localhost:9092 --topic day24.minisr \ --producer-property acks=all docker compose exec broker /opt/kafka/bin/kafka-get-offsets.sh \ --bootstrap-server localhost:9092 --topic day24.minisr --time -1

예상: 두 번째 record는 성공하고 latest offset 경계는 1이다. 실패한 첫 batch가 append 전 거부됐다는 증거다. 단일 replica 성공은 고가용성이나 broker 장애 내구성을 의미하지 않는다.

Step 4 · 설정·상태·요청을 함께 기록

docker compose exec broker /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server localhost:9092 --describe --topic day24.minisr docker compose exec broker /opt/kafka/bin/kafka-configs.sh \ --bootstrap-server localhost:9092 --entity-type topics \ --entity-name day24.minisr --describe

관찰: Replicas, Isr, topic min ISR을 한 화면에 적고 producer의 acks를 별도 기록한다. 셋 중 하나라도 빠지면 write 결과를 재현할 수 없다.

자주 나는 오류와 해결: Startup 직후 connection 오류는 make status가 healthy가 될 때까지 기다린다. Console producer가 몇 초 재시도하는 것은 retriable 오류이기 때문이다. Topic이 이전 실행에서 남았다면 config describe로 현재 값을 확인한다. Managed Kafka가 RF<min ISR을 미리 거부한다면 engine guardrail 차이이며, RF=3 test cluster에서 ISR을 1로 줄여 같은 원리를 검증한다.

Cleanup:

docker compose exec broker /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server localhost:9092 --delete --topic day24.minisr make down

8. 놓치기 쉬운 함정

  • all ≠ all assigned replicas: 현재 ISR 전체다. Out-of-sync replica까지 무조건 기다리는 것은 아니다.
  • min ISR ≠ ack 개수: 쓰기를 허용할 ISR 하한이며, ISR이 더 크면 acks=all은 그 전체를 기다린다.
  • RF ≠ 현재 copy 수: RF는 assignment, ISR은 runtime health다.
  • acks=1 + min ISR2 ≠ 같은 보호: min ISR의 producer 쓰기 거부 계약은 acks=all과 함께 쓸 때 성립한다.
  • Timeout ≠ 확정 실패: append·commit 후 response만 유실될 수 있다. Idempotent retry와 event ID 대사가 필요하다.
  • 두 replicas ≠ 두 AZ: Rack-aware 배치 없이 failure-domain 내구성을 보장하지 못한다.
  • Min ISR 하향은 성능 튜닝이 아님: 장애 중 RPO를 바꾸는 위험 승인이다.

9. 대기업 기술 면접 질문 3개

Q1. RF=3, min ISR=2, acks=all의 장애별 결과를 설명하세요.
좋은 답변 구조: failure domain 가정 → ISR3에서 세 replica 대기 → ISR2에서 두 replica로 성공 → ISR1에서 pre/post append 오류와 write 중단 → HW·visibility → 한 replica 복구 → durability/availability·latency 비용.

Q2. min ISR=2면 왜 acks=all이 ISR 세 개를 기다리나요?
좋은 답변 구조: acks는 완료 조건, min ISR은 admission floor로 상태 소유자 분리 → 공식 4.3 의미 → 느린 ISR이 latency에 미치는 영향 → ISR shrink가 2 이상이면 계속 → 2 미만이면 거부 → min ISR 개수만 기다리는 미채택 제안과 구분.

Q3. Producer timeout 뒤 같은 event를 재시도해도 되나요?
좋은 답변 구조: unknown outcome 선언 → error·correlation timeline·HW/LEO 수집 → idempotence PID/sequence 범위 → 같은 producer session retry → 외부 side effect는 event ID·unique key·transactional outbox → delivery timeout과 backpressure → 대사·replay 계획.

10. 복습과 정답

어제 내용 회상 3문제

  1. Offsets 0~9가 있는 replica의 LEO는?
  2. HW와 consumer committed offset의 차이는?
  3. Old leader가 돌아왔을 때 leader epoch가 하는 일은?

짧은 정답: ① 다음 append 위치 10. ② HW는 broker 복제 안전 공개 경계, committed offset은 group 재시작 위치. ③ stale epoch를 fencing하고 epoch end를 비교해 divergent tail을 truncate한 뒤 새 leader history로 수렴시킨다.

오늘 확인 3문제

  1. ISR=3, min ISR=2에서 acks=all은 몇 replica를 기다리는가?
  2. NotEnoughReplicas와 AfterAppend 오류의 결과 확실성 차이는?
  3. RF=3·min ISR=2가 보장하지 않는 두 가지는?

채점 기준: ① 현재 ISR 전체 3개, min ISR은 하한임을 설명(3점). ② append 전 거부와 append 뒤 unknown outcome·idempotent retry를 구분(4점). ③ 예: 모든 assigned replica 영구 보존, 서로 다른 AZ 배치, 외부 sink exactly-once 중 두 개 제시(3점). 총 8점 이상 통과.
