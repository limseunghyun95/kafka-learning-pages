sequence number

응답 유실 뒤 같은 batch를 다시 보내도 한 번만 append되는 상태 기계 · 예상 이론 50분 + 실습 35분

한 줄 요약
Idempotent producer는 record batch에 producer ID(PID)·producer epoch·partition별 sequence number를 넣고, broker가 마지막으로 수락한 순서를 기억하게 한다. 같은 identity와 sequence의 retry는 중복으로 알아보고 다시 append하지 않지만, 이 보장은 producer session·Kafka log 범위이지 업무 event나 외부 DB까지의 exactly-once가 아니다.

1. 선수 용어 사전

Idempotent같은 연산을 여러 번 적용해도 최종 효과가 한 번 적용한 것과 같은 성질. “요청이 한 번만 전송된다”가 아니라 “중복 적용을 알아본다”에 가깝다.
Producer ID (PID)Kafka가 producer instance를 구별하기 위해 발급하는 내부 identity. business user ID나 client.id가 아니다.
Producer epoch같은 PID 계열에서 더 새로운 producer incarnation을 나타내는 세대 번호. 오래된 epoch의 write를 차단하는 fencing에 쓰인다.
Sequence number한 PID·epoch가 특정 topic-partition으로 보내는 record 순번. 전역 번호가 아니라 partition마다 0부터 독립적으로 증가한다.
Record batch여러 record를 묶은 protocol·compression·append 단위. PID·epoch·base sequence는 record마다가 아니라 batch header에 있어 비용을 나눠 낸다.
Base sequencebatch 첫 record의 sequence. 각 record의 offset delta를 더해 batch의 마지막 sequence와 다음 expected sequence를 계산한다.
In-flight requestnetwork로 보냈지만 아직 response를 받지 않은 request. 여러 개를 허용하면 throughput은 늘지만 retry ordering 상태가 복잡해진다.
Deduplication이미 처리한 identity를 기억해 같은 효과를 다시 적용하지 않는 것. 여기서는 broker의 PID·epoch·sequence 기반 중복 억제다.
Fencing동일 logical owner의 오래된 instance가 계속 쓰지 못하게 막는 것. epoch가 lease token처럼 오래된 writer를 구분한다.
Out-of-orderbroker가 기대한 다음 sequence보다 큰 값을 받는 gap. 중간 batch가 사라졌거나 순서 상태가 깨졌음을 뜻한다.
Producer sessionPID와 sequence 상태가 이어지는 producer instance의 생명주기. process 재시작·새 producer 생성은 다른 session이 될 수 있다.
Business event ID주문 생성처럼 업무 사건을 재시도·재처리 사이에도 동일하게 식별하는 application key. PID를 대신할 수 없고 PID도 이를 대신하지 않는다.

2. 왜 중요한가

어제 본 가장 위험한 failure window는 broker append 성공 → ProduceResponse 유실이었다. client는 timeout 뒤 retry해야 실제 미기록을 복구할 수 있지만, 첫 요청이 이미 기록됐다면 같은 batch가 두 번 append될 수 있다. Idempotence는 이 모순을 “다시 보내되 broker가 같은 시도를 알아본다”로 해결한다.

면접에서 “enable.idempotence=true면 exactly-once입니다”라고 답하면 범위가 빠졌다. 강한 답은 PID·epoch·partition-local sequence의 owner와 broker 검증 state transition을 설명하고, 왜 acks=all·retries>0·max.in.flight≤5가 묶이는지, process 재시작·새 event ID·외부 DB에서는 무엇이 남는지까지 방어한다.

3. Architecture: retry를 한 번의 append로 접는 흐름

1 · Identityproducer가 InitProducerId protocol로 PID·epoch 획득
↓ partition별 next sequence state 생성
2 · BatchTopic-A/P0 batch에 PID=41, epoch=2, baseSeq=10 기록
↓ ProduceRequest → partition leader
3 · Verifybroker의 expectedSeq=10과 비교
↓ 같음: append·state 전진 · 낮음: duplicate · 높음: gap/error
4 · Lost ackappend는 성공했지만 response가 유실되어 client가 같은 batch retry
↓ PID=41, epoch=2, baseSeq=10 그대로
5 · Dedupbroker가 이미 수락한 sequence임을 확인 → 새 append 없이 이전 결과 반환

각 번호에서 누가 무엇을 기억하는가

  1. Producer identity: client가 내부 PID·epoch를 얻는다. 사용자가 PID를 business ID처럼 직접 배정하지 않는다.
  2. Sequence assignment: producer는 topic-partition별 next sequence를 관리하고 batch 생성 시 그 범위를 영구 배정한다.
  3. Leader validation: broker는 PID·epoch·partition마다 최근 수락한 sequence와 batch metadata를 기억한다.
  4. Retry: response 유실 뒤 새 record를 만드는 게 아니라 동일 batch identity로 다시 보낸다.
  5. Dedup result: 낮은 sequence의 알려진 batch는 중복으로 처리해 log를 늘리지 않는다. 기대값보다 큰 gap은 데이터 유실 가능성을 알리는 오류다.

Sequence는 왜 partition별인가

Kafka의 ordering 단위가 partition이기 때문이다. P0과 P1은 서로 다른 leader·log·network queue를 가질 수 있어 하나의 전역 sequence를 강제하면 독립 partition까지 직렬화된다. 대신 상태 key는 개념적으로 (PID, epoch, topic, partition)이고 각 partition에서만 단조 증가한다. 이 선택이 병렬성과 ordering scope를 동시에 만든다.

Batch header와 공간 비용

Record batch에는 producerId, producerEpoch, baseSequence가 한 번 들어가고 각 record는 relative offset을 사용한다. identity를 record마다 반복하지 않으므로 metadata 비용이 batch에 amortize된다. Broker는 batch의 last offset delta로 마지막 sequence와 다음 expected sequence를 계산할 수 있어 압축된 record를 모두 풀지 않고도 순서 범위를 판단한다.

왜 max.in.flight ≤ 5인가

Kafka 4.3 Java producer에서 idempotence는 acks=all, retries>0, max.in.flight.requests.per.connection≤5를 요구한다. Broker가 producer마다 최근 batch를 최대 5개까지 보존해 retry 결과와 ordering을 판정하는 경계와 맞추기 때문이다. 값 5는 “동시에 record 다섯 개”가 아니라 connection당 미응답 request 다섯 개이며, request 하나에는 여러 batch가 들어갈 수 있다.

5. 실무 설계 판단

판단권장이유
기본 producer 설정idempotence를 명시하고 필수 config도 함께 ADR에 기록충돌 설정이 암묵적으로 idempotence를 꺼버리는 upgrade·client 차이를 방지한다.
업무 중복 비용 높음Kafka idempotence + event ID + sink unique keyproducer session 내부와 외부 side effect 두 범위를 모두 닫는다.
여러 topic 원자 writetransactional.id와 transaction protocol 검토idempotence만으로 partial success를 숨길 수 없다.
fatal sequence error영향 partition 격리, producer 재생성 전 결과·event ID 확인무조건 continue하면 ordering·duplication 위험이 남을 수 있다.

Best Practice

  • enable.idempotence=true를 명시하고 acks=all, retries, max.in.flight, delivery timeout을 config test로 함께 검증한다.
  • producer는 application lifecycle 동안 재사용한다. record마다 새 producer를 만들면 connection·batch·PID session 이점을 모두 잃는다.
  • callback에는 event ID, topic·partition, offset 또는 exception class, elapsed time을 남기고 payload·개인정보는 기록하지 않는다.
  • timeout 뒤 application retry는 동일 business event ID를 사용하고, sink에 unique constraint 또는 atomic upsert를 둔다.
  • client library·broker upgrade 때 idempotence 기본값과 conflict validation을 공식 문서·integration test로 확인한다.

Anti-pattern·edge case·version 경계

  • Anti-pattern: client.id를 PID로 설명한다. client.id는 관측용 문자열이고 PID는 dedup protocol identity다.
  • Anti-pattern: callback failure 뒤 새 UUID로 record를 다시 만든다. session-level dedup을 우회해 업무 중복을 만든다.
  • Anti-pattern: idempotence만 켜고 외부 DB exactly-once를 선언한다. transaction domain이 다르다.
  • Edge case: log retention·DeleteRecords·leader change 과정에서 broker producer state가 없는 UNKNOWN_PRODUCER_ID 경로가 생길 수 있다. sequence를 임의로 0으로 되돌리는 것은 안전하지 않다.
  • Edge case: fatal batch 뒤 후속 sequence가 이미 배정됐다면 일부만 계속 보내 ordering을 복구했다고 단정할 수 없다.
  • Version: Kafka 4.3 Java producer는 충돌 설정이 없으면 idempotence 기본값이 true다. 다른 언어 client·구버전은 기능과 기본값이 다를 수 있어 각 공식 client 문서를 확인한다.

7. 35분 실습: batch header와 retry 후 중복 억제 관찰

사전 조건: 저장소 루트, Docker, terminal 두 개. 공식 apache/kafka:4.3.1 image와 Compose network를 사용한다. 단일 broker라 replication 내구성은 검증하지 않는다.

실행 전 예측: 같은 producer process가 broker pause 동안 retry하면 consumer에는 logical record가 몇 개 보일까? Idempotence가 유지되고 delivery deadline 전에 복구되면 각 입력은 한 번이어야 한다. 단, pause timing이 response 유실 창을 정확히 만들지는 않으므로 retry log도 함께 본다.

1단계 · topic 생성

make up

docker compose exec broker /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --create \
  --topic day16-idempotent --partitions 1 --replication-factor 1

2단계 · Terminal A에서 한 producer session 유지

{ printf 'event-01\n'; sleep 2; printf 'event-02\n'; \
  sleep 6; printf 'event-03\n'; } | \
docker run -i --rm --network kafka-learning_default \
  apache/kafka:4.3.1 \
  /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server broker:9092 --topic day16-idempotent \
  --producer-property enable.idempotence=true \
  --producer-property acks=all \
  --producer-property retries=2147483647 \
  --producer-property max.in.flight.requests.per.connection=5 \
  --producer-property request.timeout.ms=1000 \
  --producer-property delivery.timeout.ms=15000 \
  --producer-property retry.backoff.ms=200

3단계 · Terminal B에서 failure injection

sleep 1
docker pause kafka-learning-broker
sleep 4
docker unpause kafka-learning-broker

예상 관찰: producer에 disconnect·timeout·retry log가 보일 수 있지만 15초 delivery deadline 안에 broker가 돌아오면 session은 계속될 수 있다. 실패가 전혀 보이지 않으면 timing이 retry window를 비껴간 것이므로 같은 실행에서 무리하게 반복하지 말고 다음 dump 증거를 확인한다.

4단계 · consumer count와 batch identity 확인

docker compose exec broker \
  /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 \
  --topic day16-idempotent --from-beginning \
  --timeout-ms 5000 --property print.offset=true

docker compose exec broker bash -lc \
  'LOG=$(find /tmp/kraft-combined-logs \
  -path "*day16-idempotent-0*.log" | head -1); \
  /opt/kafka/bin/kafka-dump-log.sh \
  --files "$LOG" --print-data-log | head -45'

예상 관찰: input 세 개는 offset 세 개로 보이고, dump의 batch metadata에서 producerId, producerEpoch, baseSequence를 찾을 수 있다. 여러 record가 한 batch면 sequence 범위는 batch 안에서 연속이다. 출력 형식은 Kafka 버전에 따라 이름이 달라질 수 있다.

자주 나는 오류와 해결

  • network kafka-learning_default not found: make up 뒤 docker network ls에서 실제 Compose network 이름을 확인한다.
  • ConfigException: acks=all, retries>0, max.in.flight≤5 조합인지 확인한다.
  • 세 record가 한 batch가 아님: sleep 때문에 batch가 나뉠 수 있다. PID·epoch가 같고 base sequence가 전진하는지를 본다.
  • Broken pipe: head가 dump 출력을 먼저 닫은 결과일 수 있으며 broker log 손상은 아니다.
  • duplicate가 보임: producer process가 재시작됐는지, console input이 두 번 실행됐는지, effective idempotence config를 확인한다.
  • broker가 계속 paused: 즉시 docker unpause kafka-learning-broker 후 health를 확인한다.

Cleanup

docker unpause kafka-learning-broker

docker compose exec broker /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --delete \
  --topic day16-idempotent

9. 대기업 기술 면접 질문

  1. Idempotent producer가 response 유실 뒤 중복을 막는 과정을 설명하라.
    좋은 답은 append→response 유실→동일 batch retry timeline을 먼저 그린다. PID·epoch·partition별 base sequence, broker expected sequence 비교와 accept/duplicate/gap state transition, acks·retry·deadline을 연결하고 session 밖 event ID 대안을 말한다.
  2. 왜 idempotence에서 max.in.flight.requests.per.connection≤5가 필요한가?
    throughput을 위한 동시 미응답 request와 retry ordering 문제를 설명한다. Broker가 producer별 최근 batch를 최대 5개 유지하는 dedup window, Kafka 4.3의 default 5, idempotence off일 때 앞 batch retry가 뒷 batch 뒤에 append될 위험을 비교한다.
  3. “exactly-once 주문 처리” 요구를 idempotent producer만으로 만족시킬 수 있는가?
    Kafka log append, multi-partition atomicity, consume-process-produce, 외부 DB·결제 API의 transaction domain을 분리한다. stable event ID, outbox, sink unique constraint, Kafka transaction·read_committed, 보상 transaction의 적용 범위와 비용을 제시한다.

10. 복습과 정답

어제 내용 회상 3문제

  1. Produce timeout이 record 미기록을 증명하지 못하는 failure window는?
  2. request.timeout.ms와 delivery.timeout.ms의 범위 차이는?
  3. retry storm을 줄이려면 retry 횟수 외에 어떤 제어가 필요한가?

채점 기준: ① append 후 response 유실, ② 한 request 응답 대 batch queue·ack·retry 전체 deadline, ③ exponential backoff+jitter·bounded deadline·rate limit/circuit breaker를 말하면 통과.

오늘 내용 확인 3문제

  1. PID, epoch, sequence number의 역할과 상태 owner를 각각 설명하라.
  2. broker expected sequence가 20일 때 incoming 20, 18, 22는 각각 어떤 의미인가?
  3. idempotent producer만으로 process 재시작 뒤 업무 중복과 외부 DB 중복을 막지 못하는 이유는?

짧은 정답: ① PID는 session identity, epoch는 incarnation fencing, sequence는 partition별 순서다. ② 20은 정상 append, 알려진 18은 duplicate 후보, 22는 gap/out-of-order다. ③ 새 session·새 logical record와 외부 side effect는 PID sequence state 밖이므로 stable event ID와 sink 멱등성이 필요하다.
