APACHE KAFKA 4.3 · WEEK 6 / DAY 39 · CDC CONSISTENCY

CDC ordering, snapshot, tombstone

DB의 현재 상태와 변경 로그를 손실 없이 이어 붙이는 법 · 이론 80분 + 실습 30분

한 줄 요약
CDC의 정확성은 “변경 event를 보냈다”가 아니라 snapshot 기준점과 transaction log 위치를 일관되게 연결하고, 같은 business key는 같은 Kafka partition으로 보내며, delete event와 null tombstone의 서로 다른 책임을 끝까지 지키는 데서 나온다.

1. 선수 용어 사전

CDCChange Data Capture. Application이 DB를 다시 polling하지 않고 transaction log를 읽어 INSERT·UPDATE·DELETE 변화를 event로 만드는 방식이다.
Transaction logDB가 복구·복제를 위해 쓰는 변경 기록. MySQL은 binlog, PostgreSQL은 WAL이라 부른다. Log의 위치가 CDC source offset이 된다.
Log position변경 로그에서 읽은 지점. Binlog file+position, GTID, LSN처럼 engine마다 표현이 다르며 단순 timestamp가 아니다.
SnapshotCDC 시작 시 이미 DB에 존재하는 row를 기준 상태로 읽는 과정. 이후 log streaming과 이어져야 누락 없는 전체 상태가 된다.
Consistent snapshotSnapshot의 모든 row가 하나의 논리 시점에서 읽힌 것처럼 보이는 상태. 격리 수준·lock·MVCC에 의해 만든다.
MVCCMulti-Version Concurrency Control. Reader가 writer를 오래 막지 않고 특정 transaction 시점의 version을 읽게 하는 DB 기법이다.
Envelope변경 event의 포장 구조. 보통 before, after, op, source position, transaction metadata를 담는다.
TombstoneKey는 있고 value가 null인 Kafka record. Compacted topic에서 그 key의 과거 value를 제거해도 된다는 표식이다.
Log compactionPartition 안에서 key별 최신 value를 남기도록 오래된 record를 background cleaner가 정리하는 정책. 즉시 실행되는 delete가 아니다.
ProjectionCDC event를 적용해 만든 검색 index·cache·warehouse table 같은 읽기 모델. Replay 시 동일한 최종 상태가 되어야 한다.

2. 왜 중요한가

CDC는 DB의 현재 row를 Kafka로 복사하는 작업이 아니다. 기준 상태(snapshot) + 기준점 이후의 모든 변화(log)를 합치는 작업이다. 기준점을 잘못 잡으면 snapshot 중 수정된 row가 빠지거나, 오래된 snapshot row가 더 최신 update를 덮어쓴다.

Ordering도 범위를 붙여 말해야 한다. DB binlog가 commit 순서를 기록해도 Kafka topic이 여러 partition이면 전체 event의 단일 순서는 없다. 동일 primary key를 같은 partition에 보내면 그 key에 대한 순서는 지킬 수 있지만, 한 DB transaction이 여러 key를 바꾸면 consumer는 여러 partition에서 서로 다른 시간에 볼 수 있다.

삭제는 더 까다롭다. Delete envelope는 consumer에게 before 값과 삭제 이유를 알려준다. Tombstone은 compacted log cleaner에게 그 key의 최종 value도 없애라고 알린다. 하나를 다른 하나로 대체하면 audit·sink delete·state 복구 중 하나가 깨질 수 있다.

Snapshot race를 집합으로 보기

Snapshot 기준점 L0 이전에 commit된 row 집합을 S, L0 이후 log event 집합을 Δ라 하자. 목표 상태는 apply(S, Δ)다. 단순 arrival order로 적용하면 Δ의 update가 먼저 도착한 뒤 S의 오래된 row가 도착해 최신 값을 덮을 수 있다. 따라서 connector가 stream event를 buffer/deduplicate하거나 consumer가 source position과 snapshot flag를 이해해야 한다.

Incremental snapshot은 table을 primary key chunk로 나눠 streaming과 병행할 수 있다. Debezium은 snapshot window 동안 buffered READ key와 incoming streamed event key를 비교한다. 이 동작은 connector별 구현 세부이므로 “모든 CDC engine이 같은 방식”이라고 일반화하지 않는다.

Ordering은 partial order다

분산 pipeline에는 하나의 wall-clock total order보다 여러 순서가 있다. DB commit order, source log position order, Kafka partition offset order, consumer processing completion order가 서로 다르다. 같은 key에서는 partition order로 state transition을 직렬화할 수 있지만, 여러 key의 causal relation을 보존하려면 transaction ID·event sequence·aggregate version 같은 metadata가 필요하다.

Compaction의 정확한 의미

cleanup.policy=compact는 key별 최신 value를 보존하도록 오래된 segment를 background에서 정리한다. Consumer는 cleaner 전에는 여러 version과 tombstone을 모두 볼 수 있다. Tombstone도 delete.retention.ms 이후 제거될 수 있으므로 offset 0부터 full scan하는 consumer가 그 시간 안에 head에 도달하지 못하면 삭제 표식을 놓칠 수 있다.

compact,delete를 함께 쓰면 key별 최신값이라도 time/size retention 조건으로 segment가 삭제될 수 있다. “Compacted topic이면 최신 state가 영원히 보존된다”는 문장은 이 조합에서는 틀릴 수 있다.

5. 실무 설계 판단

  • Ordering SLO를 문장으로: “한 customer_id의 event는 순서 보장”인지 “한 DB transaction의 모든 row가 원자적으로 보임”인지 구분한다. 후자는 훨씬 비싸다.
  • Primary key를 Kafka key로: Keyless event나 random key는 같은 row가 여러 partition으로 흩어져 compaction·ordering·upsert가 깨진다. Primary key 변경은 old key delete+tombstone+new key create로 볼 수 있다.
  • Snapshot 전 capacity: Table row 수·평균 row bytes·DB read IOPS·Kafka throughput·예상 시간·binlog retention을 계산한다. Snapshot 동안 log가 purge되면 streaming 기준점을 잃을 수 있다.
  • Offset와 schema history 보호: Connector offset만 backup하고 schema history를 잃으면 과거 log를 올바른 schema로 decode하지 못할 수 있다. DR에 둘을 함께 넣는다.
  • Downstream idempotency: Primary key+source position 또는 event ID로 dedup하고, upsert 시 aggregate version/position이 뒤로 가지 않게 compare-and-set한다.
  • Tombstone retention: 가장 느린 full-rebuild consumer가 offset 0부터 head까지 도달하는 p99 시간보다 delete.retention.ms를 충분히 크게 잡고 alert한다.
  • Schema evolution: DDL rollout, schema history, connector parsing, converter/registry compatibility, downstream migration 순서를 하나의 change plan으로 관리한다.
  • PII와 before image: CDC envelope는 삭제된 row의 before 값까지 보존할 수 있다. Topic ACL·retention·masking·right-to-erasure 범위를 함께 설계한다.

Engine/version 차이: MySQL binlog, PostgreSQL WAL, SQL Server transaction log는 position·transaction metadata·lock·snapshot semantics가 다르다. 여기서는 Debezium 3.7 MySQL connector의 initial/incremental snapshot과 tombstone 설명을 구체 예로 사용한다. 다른 connector에 설정명과 재개 semantics를 그대로 복사하지 않는다.

Anti-pattern: Event timestamp로 commit order 추정, partition을 늘리면서 key ordering 영향 미검토, snapshot 완료 전에 downstream cutover, binlog retention보다 긴 outage 허용, tombstone을 “빈 JSON”으로 대체, compaction을 즉시 삭제로 오해, offset을 미래로 강제 이동해 gap 숨기기.

0) 실행 전 예측

  1. A의 live update가 먼저 도착하고 옛 snapshot A가 나중에 도착하면 단순 upsert의 최종 값은?
  2. 한 DB transaction이 A와 B를 바꾸면 key partitioning 후 두 event가 같은 Kafka partition에 있을까?
  3. Delete envelope만 있고 null tombstone이 없으면 compacted log에서 그 key는 완전히 사라질까?

1) 모델 실행

python3 - <<'PY'
from zlib import crc32

snapshot = [
    {"key":"A","kind":"snapshot","pos":100,"value":"new"},
    {"key":"B","kind":"snapshot","pos":100,"value":"open"},
]
stream = [
    {"key":"A","kind":"update","pos":101,"value":"paid"},
    {"key":"B","kind":"delete","pos":102,"value":None},
]

def apply(events):
    state={}
    for e in events:
        if e["value"] is None:
            state.pop(e["key"],None)
        else:
            state[e["key"]]=e["value"]
    return state

bad_arrival=[stream[0],snapshot[0],snapshot[1],stream[1]]
naive=apply(bad_arrival)
correct=apply(snapshot+sorted(stream,key=lambda e:e["pos"]))
print("NAIVE arrival-order =",naive)
print("POSITION-AWARE     =",correct)
assert naive["A"]=="new" and correct["A"]=="paid"

partition=lambda key: crc32(key.encode())%3
print("TX T9 partitions   =",
      {"A":partition("A"),"B":partition("B")})
assert partition("A") != partition("B")

delete_envelope={"op":"d","before":{"id":"B","status":"open"}}
with_tombstone=[("B",{"op":"c"}),("B",delete_envelope),("B",None)]
without_tombstone=with_tombstone[:-1]

def compact(log):
    latest={}
    for key,value in log:
        latest[key]=value
    return {k:v for k,v in latest.items() if v is not None}

print("COMPACT with null  =",compact(with_tombstone))
print("COMPACT no null    =",compact(without_tombstone))
assert "B" not in compact(with_tombstone)
assert compact(without_tombstone)["B"]["op"]=="d"
print("ALL ASSERTIONS PASSED")

2) 예상 관찰과 해석

Snapshot race: Arrival-order upsert는 A를 new로 되돌리지만, 기준 snapshot을 먼저 적용하고 L0 이후 source position 순서로 stream을 적용하면 paid가 된다.

Partition: 예제 hash에서 A와 B는 서로 다른 partition이다. 같은 DB transaction이라는 사실만으로 Kafka consumer가 두 key를 동시에 보지는 않는다.

Tombstone: Null이 있으면 compacted final map에서 B가 사라진다. Delete envelope만 있으면 B의 최신 value는 “op=d인 일반 record”이므로 compactor는 그것을 남긴다.

3) 실패 주입

실패 A: correct 계산을 apply(stream+snapshot)으로 바꾸고 assertion을 실행한다. Stale snapshot이 live update를 덮어 assertion이 실패한다.

실패 B: with_tombstone의 마지막 ("B",None)을 제거한다. B가 compacted state에 남아 assertion이 실패한다.

복구 판단: Production에서는 단순 timestamp가 아니라 connector의 source position·snapshot flag·transaction metadata를 보존하고, authoritative DB와 key별 reconciliation을 수행한다.

8. 놓치기 쉬운 함정

  • Commit time ≠ processing time: Event timestamp로 DB commit order를 복원하지 않는다.
  • Global ordering 환상: Kafka ordering은 partition-local이다. 요구사항이 key-local이면 global order를 비싸게 만들지 않는다.
  • Snapshot flag 무시: op=read를 일반 create와 구분하지 않으면 늦은 snapshot row가 최신 state를 덮을 수 있다.
  • Primary key update: 하나의 update가 old key delete+tombstone+new key create로 나타날 수 있다.
  • Tombstone 변형: SMT나 converter가 null record를 drop/변형하면 compaction과 sink delete semantics가 달라진다.
  • Compaction 즉시성: Cleaner 전에는 모든 version이 존재하며 consumer는 중복·delete·tombstone을 볼 수 있다.
  • Retention 이중 정책: compact,delete는 최신 key도 time/size에 따라 잃을 수 있다.
  • Binlog/WAL purge: Outage RTO보다 source log retention이 짧으면 resnapshot 외 선택지가 사라진다.
  • Schema history 손실: Data offset만 살아 있어도 과거 DDL 순서를 잃으면 decode가 실패할 수 있다.

9. 대기업 기술 면접 질문

Q1. 10억 row table을 무중단 CDC로 bootstrap하라.

좋은 답변 구조: DB engine·MVCC·허용 lock·RPO/RTO·throughput 수치화 → consistent snapshot 기준점 L0 → chunk/parallelism과 DB 부하 → L0 이후 log retention 계산 → snapshot/live merge와 dedup → schema history·offset DR → validation·cutover·rollback까지 답한다.

Q2. DB transaction 하나가 여러 Kafka partition으로 갈 때 원자성을 어떻게 다룰까?

좋은 답변 구조: Key-local order와 global atomicity 구분 → transaction metadata·expected event count 확인 → consumer-side buffer/timeout 또는 aggregate 재설계 → Kafka transaction 가능 범위 → memory·latency·stuck transaction trade-off → reconciliation 대안을 제시한다.

Q3. Delete event와 tombstone을 둘 다 보내는 이유는?

좋은 답변 구조: Delete envelope의 domain/audit 정보 → null tombstone의 compaction protocol → asynchronous cleaner와 delete.retention.ms → slow rebuild consumer failure window → sink null handling·PII·replay 정책까지 방어한다.

10. 복습/정답

어제 내용 회상 3문제

  1. Connector와 Task의 책임은 어떻게 다른가?
  2. Source offset과 sink Kafka consumer offset은 각각 무엇을 뜻하는가?
  3. Sink external write 후 offset commit 전 crash의 결과는?
어제 정답/채점: ① Connector는 작업 분할·재구성, Task는 실제 data I/O(3점). ② Source offset은 외부 source 위치, sink offset은 Kafka progress(3점). ③ Replay와 중복 side effect가 가능하므로 idempotency·dedup·reconciliation 필요(3점).

오늘 확인 문제 3개

  1. Initial snapshot 기준점 L0는 왜 row scan 전에 잡아야 하는가?
  2. 같은 DB transaction의 A·B event가 Kafka에서 원자적으로 보이지 않을 수 있는 이유는?
  3. Delete envelope와 tombstone의 책임을 각각 말하라.
오늘 정답/채점: ① L0 이전 consistent state와 이후 log를 gap 없이 합치기 위해서(3점). ② Key partitioning으로 서로 다른 partition에 append·소비될 수 있기 때문(3점). ③ Delete envelope는 업무 삭제 정보, tombstone은 compactor용 null marker(3점). 총 9점 중 7점 이상이면 통과.
