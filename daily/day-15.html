APACHE KAFKA 4.3 · WEEK 3 / DAY 15 · PRODUCER FAILURE SEMANTICS

acks, retry, timeout의
상호작용

“실패를 받았다”와 “기록되지 않았다”를 분리하는 producer deadline 모델 · 예상 이론 50분 + 실습 30분

한 줄 요약
acks는 성공 응답에 필요한 broker 상태, retry는 일시 실패 뒤 재시도 정책, timeout은 얼마나 기다린 뒤 결과를 확정할지다. 응답이 유실되면 broker에는 기록됐지만 client는 실패로 볼 수 있으므로, timeout은 “미기록 증명”이 아니라 결과 불명확(ambiguous outcome)일 수 있다.

1. 선수 용어 사전

Acknowledgment줄여서 ack. 요청을 받은 쪽이 “요구된 조건까지 처리했다”고 돌려주는 응답이다. 업무 처리 완료와는 별개다.
acksproducer가 ProduceRequest를 성공으로 보기 전에 leader가 확인해야 하는 수준. 0, 1, all이 있다.
Retry일시적이라고 분류된 실패 뒤 같은 batch 전송을 다시 시도하는 것. 재시도 가능하다고 반드시 결과가 미기록이라는 뜻은 아니다.
Retriable errorleader 이동·일시 네트워크 오류처럼 시간이 지나거나 metadata가 갱신되면 성공할 가능성이 있는 오류.
Fatal error인증 실패·잘못된 설정처럼 같은 입력을 그대로 반복해도 해결되지 않는 오류. 무한 retry 대상이 아니다.
Deadline / timeoutdeadline은 “이 시각까지”, timeout은 “이 기간만” 기다린다는 한계. 시간 초과는 상태를 rollback하지 않는다.
request.timeout.ms보낸 한 request의 응답을 기다리는 상한. 지나면 필요한 경우 retry하거나 retry가 끝났다면 실패한다.
delivery.timeout.mssend()가 반환한 뒤 record가 batch에서 기다리는 시간, broker ack 대기, retriable failure 재시도를 합친 전체 전달 상한.
max.block.mssend()가 metadata나 buffer를 기다리며 application thread를 막을 수 있는 상한. delivery timeout과 다른 clock이다.
Backoff / jitterretry 사이를 쉬는 시간과 무작위 흔들림. 장애 때 모든 client가 동시에 재시도하는 thundering herd를 줄인다.
ISRIn-Sync Replicas. leader를 충분히 따라가고 있다고 Kafka가 판단한 replica 집합. acks=all의 “all”은 고정된 모든 replica가 아니라 현재 ISR과 연관된다.
Ambiguous outcomeclient가 최종 결과를 모르는 상태. 예: leader append는 성공했지만 ProduceResponse가 network에서 유실됐다.

2. 왜 중요한가

분산 시스템에서 timeout은 오류 종류가 아니라 관측의 한계다. client는 response를 못 받았을 뿐, server가 실행하지 않았다는 증거를 받은 것이 아니다. 이 차이를 놓치면 application이 callback timeout 뒤 새 event ID로 다시 보내 중복을 만들거나, 반대로 retry를 막아 실제 미기록 record를 유실한다.

대기업 면접의 좋은 답은 acks=all을 외우는 데서 끝나지 않는다. “leader append 후 response 유실” failure window를 그리고, automatic retry와 idempotence의 범위, 전체 delivery deadline, upstream HTTP deadline, downstream 업무 멱등성까지 연결한다. 실무에서는 이 모델이 retry storm, 장애 장기화, 처리량 붕괴를 막는 runbook이 된다.

3. Architecture: 성공 응답과 결과 불명확의 갈림길

1 · send()serialize → partition 선택 → accumulator batch에 적재; Future를 빠르게 반환
↓ linger/batch ready · delivery deadline은 이미 흐름
2 · Requestsender thread가 partition leader에 ProduceRequest 전송
↓ leader append · follower replication · acks 조건 평가
3A · ResponseProduceResponse 도착 → Future/callback 성공 → offset·timestamp 관찰
또는 response 유실 / leader 이동 / request timeout
3B · Unknownbroker 기록 여부를 client가 모름 → retriable이면 backoff 후 같은 batch retry
↓ 성공 · non-retriable error · retries 소진 · delivery timeout 중 먼저 도달
4 · Completioncallback success/failure. 실패는 broker log에서 자동 삭제를 뜻하지 않음

번호별 상태 변화

  1. Application→producer: send() 호출은 동기 delivery 완료가 아니다. metadata·buffer가 부족하면 max.block.ms까지 application thread가 막힐 수 있다.
  2. Producer→leader: 한 request 안에 여러 partition batch가 실릴 수 있다. 각 batch의 delivery clock은 batch 생성 시점부터 흐른다.
  3. Leader/replica: leader는 append하고 acks 조건을 만족시키려 한다. client가 response를 받기 전 network가 끊기면 server와 client의 지식이 갈라진다.
  4. Retry: retriable error면 backoff를 두고 재전송한다. idempotence가 꺼져 있으면 이미 기록된 batch가 다시 append되어 중복될 수 있다.
  5. Deadline: delivery timeout은 accumulator 대기+request 대기+retry를 합친 상한이다. 만료 뒤 callback failure가 나도 이미 append된 record의 보상 삭제는 없다.

4. CS 내부 동작

acks는 “몇 대”보다 “무슨 상태”인가

설정client 성공 조건실패 창·비용
acks=0server ack를 기다리지 않고 socket buffer에 넣은 뒤 성공처럼 진행broker 수신도 보장 못하며 client가 오류를 몰라 retries가 실질적으로 작동하지 않는다. offset은 -1.
acks=1leader local log write 후 응답follower 복제 전 leader가 죽으면 record 유실 가능. latency는 낮아질 수 있다.
acks=all현재 in-sync replica 집합이 요구 조건을 만족가장 강한 producer ack 보장이나 latency·가용성 비용이 있다. replication factor 1이면 복제 안전성이 생기지 않는다.

중요: acks=all만으로 필요한 replica 수를 결정하지 않는다. min.insync.replicas, replication factor, ISR 상태와 함께 해석해야 하며 이 조합은 Week 4에서 깊게 다룬다.

Kafka 4.3 공식 문서는 delivery.timeout.ms ≥ request.timeout.ms + linger.ms를 요구한다. 기본값은 각각 120초, 30초, 5ms이며 retries 기본은 매우 큰 값이다. 실무에서는 retry 횟수를 세는 대신 delivery deadline으로 전체 시간을 제한하고, application의 상위 deadline과 맞춘다.

실패 창 네 가지

  1. 전송 전 만료: metadata·buffer·batch queue에서 delivery deadline 소진 → broker 미기록 가능성이 높지만 증거를 로그로 확인한다.
  2. 전송 중 단절: request 일부 또는 전부가 broker에 도달했는지 모름 → retry가 필요하지만 중복 가능성이 생긴다.
  3. append 후 response 유실: 가장 중요한 ambiguous window. retry 없는 포기는 실제 record를 남기고 failure를 보고할 수 있다.
  4. callback success 후 caller crash: upstream이 응답을 못 받아 application-level 재호출할 수 있다. producer idempotence만으로 새 session·새 event 재생성을 모두 막지 못한다.

Best Practice

  • producer config는 acks 하나가 아니라 enable.idempotence, delivery.timeout.ms, request.timeout.ms, backoff, max.in.flight, topic replication 정책을 하나의 ADR로 관리한다.
  • callback에서 exception class, topic·partition, event ID, attempt가 아닌 최종 elapsed time을 기록하되 payload·개인정보는 남기지 않는다.
  • application-level 재시도는 동일한 business event ID를 재사용하고 sink가 dedup/upsert할 수 있게 한다.
  • service deadline, queue wait, Kafka delivery deadline, downstream 처리 SLO를 시간 예산 표로 맞춘다.
  • retry 증가 전 broker request queue·ISR·network·producer buffer 지표를 확인하고 재시도가 원인을 증폭하는지 판단한다.

Anti-pattern·edge case·version 경계

  • Anti-pattern: timeout callback이면 무조건 새 UUID로 다시 보낸다. 첫 record가 이미 append됐다면 업무 중복이 된다.
  • Anti-pattern: retries=0으로 중복을 없앤다. ambiguous failure에서 유실 가능성을 키울 뿐 end-to-end 중복을 해결하지 않는다.
  • Anti-pattern: 모든 오류를 retry한다. 인증·권한·serialization·record-too-large 같은 영구 오류는 격리·수정해야 한다.
  • Edge case: acks=all이어도 replication factor 1이면 leader 한 대만 있다.
  • Edge case: idempotence가 켜져 있어도 application이 새 producer session에서 새 logical record로 재생성하면 업무 중복 방지는 별도다.
  • Version: Kafka 4.3 Java producer는 충돌 설정이 없으면 idempotence 기본 활성, acks=all, 큰 retries 기본을 사용한다. 다른 client 언어·구버전은 기본값과 지원 범위를 공식 문서로 확인한다.

7. 30분 실습: response를 못 받은 record의 결과 관찰

사전 조건: 저장소 루트, Docker, 두 개 terminal. 공식 apache/kafka:4.3.1 image가 준비되어 있어야 한다. 이 실험은 단일 broker이므로 replication 내구성을 증명하지 않고 timeout·retry 관측만 다룬다.

실행 전 예측: broker를 6초 멈추고 delivery timeout을 5초로 두면 during record는 반드시 없는가? 정답은 “실행 전 단정할 수 없다”다. pause 전에 append됐지만 response를 못 받았을 수도, 전송 전에 만료됐을 수도 있다.

1단계 · topic과 network 확인

make up

docker compose exec broker /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --create \
  --topic day15-timeout --partitions 1 --replication-factor 1

docker network inspect kafka-learning_default \
  --format '{{.Name}}'

2단계 · Terminal A에서 bounded producer 실행

{ printf 'before\n'; sleep 2; printf 'during\n'; \
  sleep 7; printf 'after\n'; } | \
docker run -i --rm --network kafka-learning_default \
  apache/kafka:4.3.1 \
  /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server broker:9092 --topic day15-timeout \
  --producer-property acks=all \
  --producer-property enable.idempotence=true \
  --producer-property retries=2147483647 \
  --producer-property request.timeout.ms=1000 \
  --producer-property delivery.timeout.ms=5000 \
  --producer-property retry.backoff.ms=200

3단계 · Terminal B에서 failure injection

sleep 1
docker pause kafka-learning-broker
sleep 6
docker unpause kafka-learning-broker

예상 관찰: Terminal A에 timeout·retry 관련 오류가 보일 수 있다. 정확한 결과는 scheduling에 따라 달라지며 이 비결정성이 학습 포인트다. 같은 실행에서 producer 명령을 자동 반복하지 말고 먼저 log를 확인한다.

4단계 · 최종 log를 증거로 판정

docker compose exec broker \
  /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 \
  --topic day15-timeout --from-beginning \
  --timeout-ms 5000 \
  --property print.offset=true

판정: during이 있으면 “client가 성공을 확정하지 못해도 broker append는 가능”하다는 증거다. 없으면 이번 실행에서는 deadline 전에 append되지 않은 것이다. 어느 결과든 callback·broker log·event ID를 함께 봐야 하며, 한 번의 결과를 일반 법칙으로 만들지 않는다.

자주 나는 오류와 해결

  • network ... not found: make up 뒤 docker network ls에서 Compose network 이름을 확인한다.
  • delivery.timeout.ms 설정 오류: 값이 request.timeout.ms + linger.ms 이상인지 확인한다.
  • producer가 곧바로 끝남: pipe의 중괄호·sleep과 -i가 그대로 들어갔는지 확인한다.
  • broker가 계속 paused: 반드시 docker unpause kafka-learning-broker 후 health를 확인한다.
  • during 결과가 예상과 다름: ambiguous window의 timing 결과다. 오류가 아니라 이번 실행의 증거로 기록한다.

Cleanup

docker unpause kafka-learning-broker

docker compose exec broker /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --delete \
  --topic day15-timeout

9. 대기업 기술 면접 질문

  1. Produce timeout을 받으면 record가 Kafka에 없다고 말할 수 있는가?
    좋은 답은 결론부터 “없다고 단정할 수 없다”고 말하고, leader append→response 유실 timeline을 그린다. retriable error, automatic retry, idempotence, stable event ID, broker log·callback 증거와 업무 dedup 대안까지 범위를 방어한다.
  2. acks=0/1/all을 latency·durability·availability 관점에서 비교하라.
    요구사항과 failure domain부터 정의한 뒤 각 성공 조건을 상태로 설명한다. acks=all과 ISR·min ISR·RF의 관계, RF1 edge case, replica 지연 때 latency/availability trade-off를 수치 가정과 함께 말한다.
  3. HTTP p99 2초 서비스의 Kafka producer timeout을 설계하라.
    동기 경로인지 outbox 비동기 경로인지 먼저 결정한다. serialization·queue·linger·request·retry·response 예산을 합산하고 delivery timeout을 상위 deadline보다 무작정 길게 두지 않는다. timeout 후 late success와 재호출 중복을 event ID·outbox·status query로 처리한다.

  2. zero-copy가 TLS 경로에서도 항상 성립한다고 말할 수 없는 이유는?

채점 기준: ① sequential append·batch·page cache, ② Kafka 공식 문서상 SSL에서는 sendfile 미사용과 user-space 암호화 비용, ③ page cache hit 대 cold storage read·cache pressure를 말하면 통과.

오늘 내용 확인 3문제

  1. request.timeout.ms와 delivery.timeout.ms의 포함 범위를 구분하라.
  2. append 후 response 유실에서 idempotence를 끄고 retry하면 어떤 일이 가능한가?
  3. 왜 retry 횟수보다 deadline·backoff·jitter·stable event ID를 함께 설계해야 하는가?

짧은 정답: ① 전자는 한 request 응답, 후자는 batch queue부터 retry까지 전체 전달 상한이다. ② 같은 batch가 다시 append되어 중복될 수 있다. ③ 장애 지속 시간을 제한하고 retry storm을 분산하며 client session 밖 업무 중복도 식별해야 하기 때문이다.
