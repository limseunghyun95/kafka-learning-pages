APACHE KAFKA 4.3 · WEEK 6 / DAY 36 · SCHEMA & DATA CONTRACT

serialization과 schema contract

객체가 바이트가 되는 순간부터 호환성·partition·복구 책임을 설계하기 · 이론 70분 + 실습 30분

한 줄 요약
Kafka broker는 업무 객체나 필드 의미가 아니라 key/value 바이트 배열을 저장한다. 따라서 serializer와 schema contract는 단순 변환 코드가 아니라 partition 안정성, producer/consumer 독립 배포, 장애 격리, replay 가능성을 결정하는 분산 시스템 경계다.

1. 선수 용어 사전

Serialization메모리의 객체를 저장·전송 가능한 결정적 byte sequence로 바꾸는 과정. 포장 규칙이라고 생각하면 쉽다.
Deserialization바이트를 독자가 이해하는 타입·객체로 복원하는 과정. 형식이 다르거나 손상되면 여기서 실패한다.
Schema필드 이름·타입·필수 여부·기본값·논리적 의미를 기술한 데이터 구조 명세.
Data contractSchema에 ownership, 의미, 호환성, 품질, 변경·폐기 절차, SLO까지 더한 생산자와 소비자 사이의 운영 약속.
Wire format네트워크와 log에 실제 놓이는 byte layout. JSON text, Avro binary, Protobuf binary 등이 예다.
Encoding문자를 바이트로 매핑하는 규칙. UTF-8과 UTF-16은 같은 문자열을 다른 바이트로 만든다.
Compatibility새 writer와 예전 reader 또는 예전 data와 새 reader가 함께 동작할 수 있는 성질. 방향과 시점을 반드시 명시한다.
Canonical form논리적으로 같은 값을 언제나 같은 bytes로 표현하는 정규 규칙. Hash·서명·partition key 안정성에 중요하다.
Poison pillConsumer가 해석하지 못해 같은 offset에서 반복 실패하게 만드는 record. 약이 아니라 처리 파이프라인을 멈추는 독성 record라는 비유다.
TombstoneKey는 있고 value가 null인 record. Compacted topic에서 key 삭제 의도를 나타내며 문자열 "null"이나 빈 bytes와 다르다.

2. 왜 중요한가

Producer 코드에서는 OrderCreated 객체를 보내지만 broker disk에는 Java class도 Python dict도 없다. Kafka client의 Serializer<T>가 객체를 byte[]로 만들고, broker는 그 결과를 record batch 안에 보존한다. Consumer client의 Deserializer<T>가 같은 의미 체계를 공유할 때만 다시 업무 객체가 된다.

이 경계가 깨지면 broker는 정상이고 lag도 0에 가까운데 애플리케이션은 실패할 수 있다. 예를 들어 producer가 amount를 문자열에서 정수로 바꾸고 consumer를 먼저 준비하지 않으면 deserialization exception이 발생한다. 더 위험한 경우는 parsing은 성공하지만 단위가 원에서 센트로 바뀌어 조용히 잘못된 값을 만든다. Schema validation은 구조 오류는 잡지만 의미 오류까지 자동으로 잡지는 못한다.

면접에서는 “Avro가 좋다”보다 어느 component가 어떤 bytes를 만들고, schema identity를 어디에 싣고, 어느 배포 순서가 안전하며, 실패한 offset을 어떻게 격리·재처리하는지를 설명해야 깊이가 드러난다.

Data path: 객체 → serializer → key/value bytes → partitioner → record batch → ProduceRequest → partition log → FetchResponse → deserializer → 객체다. 4. CS 내부 동작

타입은 process 안에만 있고 wire에는 bytes만 있다

Java의 generic KafkaProducer<K,V>는 compile-time API 안전성을 돕지만, broker가 K와 V의 class를 아는 것은 아니다. key.serializer와 value.serializer가 실제 bytes를 정한다. Consumer도 자기 key.deserializer와 value.deserializer로 bytes를 해석한다. 양쪽 설정이 다르면 compile은 성공해도 runtime에서 깨진다.

Serialization은 단순히 JSON 문자열을 만드는 일이 아니다. Null 표현, field order, 숫자 폭, endianness, 문자열 encoding, timestamp·decimal logical type, default value, unknown field 처리까지 포함한다. 특히 IEEE-754 floating point로 금액을 표현하면 십진 정확성 문제가 생길 수 있어 scale이 있는 decimal contract 또는 정수 최소 단위를 명시해야 한다.

Key bytes는 routing contract다

Key가 있을 때 기본 partition 선택은 serialized key bytes의 hash와 연결된다. 논리적으로 같은 고객 ID라도 "42", UTF-8 integer text, 8-byte big-endian long은 다른 bytes이므로 다른 partition으로 갈 수 있다. Serializer 교체는 value 형식 변경을 넘어 key ordering·co-location·state store locality를 바꾸는 migration이다.

불변식: 같은 business key에 partition-local ordering이 필요하다면 migration 전후의 canonical key bytes 또는 명시적 partition mapping이 안정적이어야 한다.

Null, empty, 문자열 "null"은 세 상태다

표현Bytes의미
null valuenull byte arrayCompacted topic에서 tombstone 의미 가능
empty string길이 0 byte array존재하지만 내용이 빈 값
"null"UTF-8 4 bytesn-u-l-l 문자 데이터

Kafka 공식 Serializer/Deserializer API는 null data를 null byte array/object로 다루는 것을 권장한다. Custom serializer가 null을 빈 bytes로 바꾸면 tombstone contract와 downstream 의미가 깨질 수 있다.

성공 확정 시점은 단계마다 다르다

  • serialize 반환: bytes 생성만 성공했다. Broker 저장은 아직 아니다.
  • send Future 성공: 설정된 ack 기준으로 해당 bytes append가 성공했다. Consumer 해석 성공은 아니다.
  • deserialize 반환: 구조 복원은 성공했다. Domain invariant와 side effect 성공은 아니다.
  • business commit + offset commit: 처리 semantics에 따른 end-to-end 성공 지점이다. 두 commit 사이 failure window는 별도 설계가 필요하다.

Edge case: Unicode 정규화가 다른 같은 문자열, JSON number의 53-bit 정밀도, timestamp millisecond/microsecond 혼용, decimal scale 변화, duplicated JSON key, unknown enum, null vs absent, compression bomb, oversized record, schema service 일시 장애, cache miss 폭증을 테스트해야 한다.

7. 20~40분 실습: 같은 논리 key가 다른 bytes가 되는 순간

목표: String과 8-byte integer encoding을 직접 비교하고, 같은 topic에 서로 다른 value contract를 넣었을 때 독자가 실패하는 과정을 관찰한다. 별도 library 없이 Python 3와 Kafka CLI만 사용한다.

사전 조건: 저장소 root, Docker, Python 3, 공식 Apache Kafka 4.3.1 compose 환경. 약 30분.

0) 실행 전 예측

  1. 논리 key 42의 UTF-8 문자열과 signed 64-bit big-endian bytes는 같은가?
  2. JSON field가 없을 때 default를 넣는 reader는 null과 absent를 구분할 수 있는가?
  3. Consumer가 poison pill을 skip하면 처리량은 회복되지만 어떤 증거를 잃을 수 있는가?

1) Key bytes와 hash 입력 비교

python3 -c 'import struct; a="42".encode("utf-8"); b=struct.pack(">q",42); print("string",a.hex(),len(a)); print("long",b.hex(),len(b)); print("same?",a==b)'
python3 -c 'import unicodedata; a="é"; b="e\u0301"; print(a==b,a.encode().hex(),b.encode().hex()); print(unicodedata.normalize("NFC",a).encode()==unicodedata.normalize("NFC",b).encode())'

예상: 42의 두 encoding은 길이와 bytes가 다르다. 화면상 같은 Unicode도 normalization 전 bytes가 다를 수 있다. Hash 함수가 같아도 입력 bytes가 달라지므로 partition contract가 바뀔 수 있다.

2) Topic 준비와 versioned payload 전송

docker compose up -d
docker compose exec broker bash -lc 'bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --if-not-exists --topic day36-contract --partitions 1 --replication-factor 1'
printf 'order-42:{"version":1,"order_id":"order-42","amount_won":12000}\norder-43:{"version":2,"order_id":"order-43","amount_won":"12000"}\n' | docker compose exec -T broker bash -lc 'bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic day36-contract --property parse.key=true --property key.separator=:'

실패 주입: v2는 amount_won을 integer에서 string으로 바꿨다. Kafka broker는 두 records를 모두 정상 append한다.

3) 엄격한 reader로 poison pill 관찰

docker compose exec broker bash -lc 'bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic day36-contract --from-beginning --timeout-ms 5000 --property print.key=true --property key.separator=:' | python3 -c 'import sys,json; lines=[x.rstrip("\n") for x in sys.stdin if x.strip()];
for line in lines:
 key,raw=line.split(":",1); obj=json.loads(raw); assert type(obj["amount_won"]) is int, (key,"amount_won must be int",type(obj["amount_won"]).__name__); print("OK",key,obj["amount_won"])'

예상: order-42는 통과하고 order-43에서 assertion이 난다. 이는 broker 장애가 아니라 writer/reader contract 불일치다. 실제 consumer poll에서는 deserialization 단계가 실패하면 business handler에 도달하기 전 같은 offset에서 진행이 멈출 수 있다.

4) 안전한 reader migration을 작은 코드로 확인

docker compose exec broker bash -lc 'bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic day36-contract --from-beginning --timeout-ms 5000 --property print.key=true --property key.separator=:' | python3 -c 'import sys,json; lines=[x.rstrip("\n") for x in sys.stdin if x.strip()];
for line in lines:
 key,raw=line.split(":",1); obj=json.loads(raw); value=obj["amount_won"]; assert isinstance(value,(int,str)); won=int(value); assert won>=0; print("MIGRATED",key,won)'

예상: 두 version 모두 읽힌다. 실제 배포에서는 먼저 이중 reader를 배포하고 consumer fleet가 준비된 것을 확인한 뒤 writer를 전환한다. 이 코드는 문자열이면 모두 안전하다는 뜻이 아니므로 숫자 형식·범위·통화 invariant도 검증해야 한다.

8. 놓치기 쉬운 함정

  • Broker가 schema를 이해한다고 가정: Kafka core는 payload field 의미를 validation하지 않는다.
  • Value만 contract라고 생각: Key encoding 변경은 partition·ordering·join을 흔든다.
  • Parsing 성공=의미 호환: 단위·timezone·enum 의미 변화는 구조 검사만으로 놓칠 수 있다.
  • Null 혼동: Null bytes, empty bytes, 문자열 null은 다르며 tombstone semantics에 영향을 준다.
  • Consumer-first가 언제나 안전하다고 단순화: 새 reader가 old+new 모두 읽는지 fixture와 real sample로 검증해야 한다.
  • DLQ만 있으면 해결: DLQ는 격리일 뿐 contract 수정·replay·side effect 순서·SLO owner가 필요하다.
  • 원본 evidence 유실: Topic/partition/offset, headers, schema ID, bytes hash가 없으면 재현이 어려워진다.
  • 민감정보 노출: Poison payload 전체를 log·DLQ에 저장하면 PII와 credential이 복제될 수 있다.

9. 대기업 기술 면접 질문

Q1. Kafka broker는 schema를 알고 있는가? Schema 변경은 누가 막는가?

좋은 답변 구조: Broker는 record bytes·metadata를 저장한다는 경계 → serializer/deserializer의 process 책임 → 별도 schema system과 CI gate → mixed-version rollout 순서 → poison pill의 증거·격리·replay → contract owner까지 말한다.

Q2. Key serializer를 String에서 Long으로 바꾸면 무슨 일이 생기는가?

좋은 답변 구조: 논리 key와 serialized bytes 분리 → hash 입력 변화 → partition 이동과 per-key ordering 단절 → stateful join/compaction 영향 → old/new dual-read 또는 새 topic/repartition migration → 검증 지표를 제시한다.

Q3. 500개 consumer 중 하나가 새 schema에서 실패한다. 안전하게 복구하라.

좋은 답변 구조: 영향 topic/partition/offset과 writer version 고정 → exception·schema ID·bytes hash 수집 → writer rollout 중지 → PII-safe quarantine → backward-capable reader hotfix/rollback → offset replay와 side effect idempotency → contract test·canary·alert 개선으로 마무리한다.

  1. 같은 논리 key라도 serializer 변경이 ordering을 깨뜨릴 수 있는 이유는?
  2. Schema와 data contract의 차이를 amount 필드 예로 설명하라.
  3. Deserialization poison pill 대응 시 최소한 어떤 evidence를 보존해야 하는가?
오늘 정답/채점: ① Partition 선택은 serialized key bytes의 hash와 연결되어 encoding 변경 시 partition이 달라질 수 있음(3점). ② Schema는 long 구조를 말하지만 contract는 통화·단위·scale·범위·owner·변경 절차까지 말함(3점). ③ Topic/partition/offset, key, schema ID/version, exception, 안전하게 보관한 원본 bytes 또는 hash(3점). 총 9점 중 7점 이상이면 통과.
