APACHE KAFKA 4.3 · WEEK 5 / DAY 31 · REBALANCE COST

eager/cooperative assignment와 pause 비용

Stop-the-world와 incremental handoff · 이론 75분 + 실습 30분

한 줄 요약
Eager는 assignment가 바뀌면 모든 partition을 먼저 반납해 단순한 global barrier를 만든다. Cooperative는 실제 이동 대상만 revoke하고 이전 owner의 반납을 확인한 뒤 다음 rebalance에서 새 owner에게 넘겨, 완료 단계는 늘 수 있어도 전체 처리 중단 범위를 줄인다.

1. 선수 용어 사전

Assignment어떤 consumer가 어떤 topic-partition을 소유할지 나타낸 대응표. 한 partition의 active owner는 group 안에서 하나여야 한다.
AssignorMembers·subscription·partitions를 입력받아 assignment를 계산하는 알고리즘. Range, RoundRobin, Sticky, CooperativeSticky 등이 있다.
Eager새 assignment를 받기 전에 각 member가 현재 가진 모든 partitions를 포기하는 재조정 방식. 먼저 방을 모두 비운 뒤 좌석을 다시 배치하는 것과 같다.
Cooperative기존 owner가 유지할 partition은 계속 처리하고, 이동할 subset만 단계적으로 반납·획득하는 방식.
Sticky균형을 맞추면서 기존 owner를 가능한 한 유지하는 성질. Cooperative의 이득은 이동 partition 수가 작을수록 커진다.
RevocationConsumer가 partition 처리를 중지하고 offset·cache·resource를 정리해 소유권을 반납하는 절차.
Lost정상 revoke 기회를 얻지 못한 채 소유권이 사라진 상태. Session timeout 뒤에는 새 owner가 이미 처리 중일 수 있다.
Handoff이전 owner가 놓은 뒤 새 owner가 잡는 소유권 전달. 겹치면 중복 side effect, 비는 시간이 길면 lag가 커진다.
Stop-the-world변경 대상이 아닌 작업까지 함께 멈추는 global pause. JVM GC 용어를 빌린 비유이며 Kafka process 전체가 정지한다는 뜻은 아니다.
Warm-up새 owner가 connection·deserializer·local cache·state store를 준비해 정상 처리량에 도달하는 시간.
Blackout특정 partition 또는 group의 결과 출력이 멈춘 관찰 구간. Rebalance latency와 같지 않을 수 있다.
Blast radius장애나 변경의 영향 범위. Cooperative의 목적은 주로 이 범위를 이동 partitions로 제한하는 것이다.

2. 왜 중요한가

Consumer를 한 대 추가하는 평범한 autoscaling도 assignment를 바꾼다. Eager에서는 이동하지 않을 partitions까지 revoke되어 fetch가 멈추고, revoke callback에서 commit·flush·connection close를 수행한 뒤 assignment callback에서 cache를 다시 데운다. 트래픽이 많은 서비스라면 짧은 pause도 lag spike와 downstream burst로 확대된다.

Cooperative는 “rebalance를 제거”하지 않는다. 오히려 안전한 handoff 때문에 연속된 두 번의 rebalance가 필요할 수 있다. 대신 P개 중 M개만 이동한다면 P-M개는 계속 처리할 수 있다. 실무에서는 단일 latency보다 영향 partition 수 × 멈춘 시간인 처리량 손실 면적을 같이 봐야 한다.

면접에서 좋은 답은 “cooperative가 무조건 빠르다”가 아니라 ownership 불변식, revoke subset, follow-up rebalance, callback side effect, crash 예외, migration protocol까지 연결한다.

핵심 불변식: P3가 B의 ownedPartitions에 남아 있는 동안 C에게 P3를 assign하지 않는다. 1차 결과에서 P3를 비워 두고 B가 revoke한 뒤, 2차 rebalance에서 C에게 준다.

Data path와 control path: Fetch·처리·commit은 data path다. JoinGroup·SyncGroup·assignment callback은 control path다. Eager control event는 모든 data path를 멈추지만 cooperative는 ownership이 유지된 partitions의 data path를 살려 둔다.

4. CS 내부 동작과 비용 모델

집합 연산으로 보는 state transition

Member i의 현재 소유 집합을 Oi, assignor가 만든 목표 집합을 Ti라 하자. 유지 집합은 O∩T, revoke 집합은 O-T, acquire 후보는 T-O다. Eager는 실제 차집합과 무관하게 O 전체를 revoke한다. Cooperative는 O-T만 revoke하고, 다른 member가 아직 소유한다고 보고한 T-O는 이번 round에서 제외한다.

예시로 coordinator 왕복·계산이 round당 700ms, partition별 revoke flush가 300ms, 새 owner warm-up이 2초라고 하자. Eager는 한 round로 끝날 수 있지만 4개 모두 약 3초간 생산성이 떨어진다. Cooperative는 P3가 두 round를 거쳐 약 3.7초 늦게 재개할 수 있으나 P0~P2는 계속 처리한다.

따라서 p99 pause, revoked partition count, lag 증가 면적, callback latency, warm-up 처리량을 함께 측정한다. Cooperative가 한 partition의 tail latency를 반드시 줄인다고 약속하면 틀린 답이다.

Callback과 성공 확정 시점

  • Eager: Classic group에서 onPartitionsRevoked는 full assignment로 호출되고, 새 assignment를 받은 뒤 onPartitionsAssigned도 full set을 본다.
  • Cooperative: Revoke·assign subset이 비어 있으면 callback이 생략될 수 있다. 단 onPartitionsAssigned는 rebalance 완료 시 빈 집합으로도 호출된다.
  • Thread: Callback은 application의 consumer thread가 poll() 안에서 실행한다. 느린 DB flush는 heartbeat thread와 별개여도 poll progress·완료 시간을 지연시킨다.
  • Exception: Callback 예외는 assignment를 거부하는 투표가 아니다. 예외는 poll로 전달되지만 Kafka는 callback side effect가 성공했다고 가정하고 자동 재시도하지 않는다.
  • Crash: Session timeout으로 소유권을 잃으면 graceful revoke가 없을 수 있고 onPartitionsLost가 호출된다. 이때 old owner의 commit을 안전하다고 가정하면 안 된다.

Kafka 4.3 기본값 함정: Java consumer의 partition.assignment.strategy 기본 목록은 [RangeAssignor, CooperativeStickyAssignor]이고 첫 번째 Range가 선택된다. 목록에 CooperativeSticky가 보인다고 cooperative가 활성화된 것은 아니다. 공식 문서는 Range를 제거하는 한 번의 rolling bounce로 전환할 수 있게 이 목록을 제공한다.

Best practice: 먼저 canary group에서 현재 assignment 대비 이동률 M/P를 기록한다. Revoke callback에 deadline과 처리 개수 metric을 넣고, cache는 partition 단위로 분리해 유지 partition을 건드리지 않는다. State store가 크면 warm-up 완료 전 fetch rate를 점진적으로 올려 downstream burst를 막는다.

Rollback: Assignor 전환은 단순 class-name rollback이 아니다. 모든 member의 supported protocol 합의, rolling order, rebalance 횟수, offset 연속성을 확인한다. 전환 중 오류가 나면 추가 배포를 멈추고 현재 group의 assignor·generation·members를 보존한 채 공식 upgrade path의 이전 단계로 돌아간다.

7. 30분 실습: scale-out blackout 비교

실행 전 예측
Eager group에 세 번째 member를 넣으면 기존 두 member 모두 full revoke를 거쳐 로그 도착 간격이 함께 벌어진다. Cooperative group은 이동 partition의 owner만 revoke하고 유지 partitions는 계속 출력한다. 단, local single broker와 console consumer에서는 절대 시간보다 revoked 범위와 최대 출력 간격의 상대 차이를 본다.

사전 조건: Docker, 저장소의 Kafka 4.3.1 KRaft broker, 터미널 2개. 아래 process·topic·group은 day31- prefix로 격리한다.

Step 1 · 6 partitions와 timestamp stream

make up docker compose exec broker /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server localhost:9092 --create --if-not-exists \ --topic day31.pause --partitions 6 --replication-factor 1 docker compose exec -T broker bash -lc ' nohup bash -c "i=0; while true; do printf \"event-%08d\\n\" \"\$i\"; i=\$((i+1)); sleep 0.1 done | /opt/kafka/bin/kafka-console-producer.sh \ --bootstrap-server localhost:9092 --topic day31.pause" \ >/tmp/day31-producer.log 2>&1 & echo $! >/tmp/day31-producer.pid'

예상: 초당 약 10 records가 생성된다. Producer의 값이 아니라 consumer가 stdout에 기록한 도착 시각으로 blackout을 계산한다.

Step 2 · Member 시작 함수를 준비

start_member () { group="$1"; member="$2"; assignor="$3" docker compose exec -T broker bash -lc " nohup bash -c '/opt/kafka/bin/kafka-console-consumer.sh \ --bootstrap-server localhost:9092 --topic day31.pause \ --group $group --consumer-property group.protocol=classic \ --consumer-property partition.assignment.strategy=$assignor \ --property print.partition=true | while IFS= read -r line; do printf \"%s %s\\n\" \"\$(date +%s%3N)\" \"\$line\" done' >/tmp/$group-$member.log 2>&1 & echo \$! >/tmp/$group-$member.pid" } RANGE=org.apache.kafka.clients.consumer.RangeAssignor COOP=org.apache.kafka.clients.consumer.CooperativeStickyAssignor

이 함수는 consumer 출력 한 줄마다 epoch milliseconds를 붙인다. 터미널 shell에 그대로 정의해야 다음 명령에서 사용할 수 있다.

Step 3 · Eager scale-out

start_member day31-eager a "$RANGE" start_member day31-eager b "$RANGE" sleep 8 start_member day31-eager c "$RANGE" sleep 12 docker compose exec broker /opt/kafka/bin/kafka-consumer-groups.sh \ --bootstrap-server localhost:9092 --describe \ --group day31-eager --members --verbose

예상: 최종적으로 3 members가 각 2 partitions를 가진다. A·B의 log에서 C join 시점 전후 출력 간격이 함께 벌어지는지 기록한다.

Step 4 · Cooperative scale-out

start_member day31-coop a "$COOP" start_member day31-coop b "$COOP" sleep 8 start_member day31-coop c "$COOP" sleep 12 docker compose exec broker /opt/kafka/bin/kafka-consumer-groups.sh \ --bootstrap-server localhost:9092 --describe \ --group day31-coop --members --verbose

예상: 최종 분배는 2개씩이지만 이동 partitions만 단계적으로 넘어간다. Assignment가 두 round에 걸쳐 수렴할 수 있으며, 유지 partition 출력은 이어져야 한다.

Step 5 · 최대 출력 간격과 실패 주입

docker compose exec broker bash -lc ' for f in /tmp/day31-eager-?.log /tmp/day31-coop-?.log; do printf "%s " "$f" awk "\$1 ~ /^[0-9]+$/ {if(p){d=\$1-p;if(d>m)m=d}p=\$1} END{print \"max_gap_ms=\",m+0}" "$f" done' docker compose exec broker bash -lc \ 'kill -KILL $(cat /tmp/day31-coop-b.pid)' sleep 15 docker compose exec broker /opt/kafka/bin/kafka-consumer-groups.sh \ --bootstrap-server localhost:9092 --describe \ --group day31-coop --members --verbose

해석: 최대 간격은 scheduling·buffering도 포함하므로 절대 성능 benchmark가 아니다. 여러 runs의 median과 partition별 결과를 비교한다. B를 KILL한 경로에는 graceful revoke가 없으므로 cooperative도 session detection 전까지 즉시 handoff하지 못한다.

8. 놓치기 쉬운 함정

  • 두 round = 성능 퇴보: 단일 partition 완료 시간은 늘 수 있지만 유지 partitions의 처리량 손실을 크게 줄일 수 있다.
  • Cooperative = no pause: 이동 partition은 반드시 비는 구간이 있고 callback·warm-up 비용도 남는다.
  • Sticky = 완전 고정: 균형·subscription·member 변화가 요구하면 partition은 이동한다.
  • 목록에 CooperativeSticky가 있으니 활성: Kafka 4.3 기본 목록의 첫 번째 Range가 선택되므로 기본은 eager다.
  • Callback 예외면 assignment rollback: Callback은 notification이며 예외가 assignment를 취소하지 않는다.
  • 모든 revoke에서 전체 offset commit: Cooperative에서는 받은 subset과 관련 상태만 bounded commit해야 pause 이득을 보존한다.
  • Crash도 graceful revoke: Session timeout·fatal fencing은 onPartitionsLost 경로이며 old owner commit이 실패할 수 있다.
  • Classic/Consumer protocol과 eager/cooperative가 같은 축: Consumer protocol은 server-driven이고, Classic+CooperativeSticky는 client leader 기반이다.
  • Group lag 하나로 판단: Partition별 blackout과 callback latency 없이는 영향 범위를 숨긴다.

9. 대기업 기술 면접 질문 3개

Q1. Cooperative가 eager보다 항상 빠른가요?
좋은 답변 구조: P partitions·M moved 가정 → eager full revoke와 1 round → cooperative subset revoke와 follow-up round → single-partition tail latency 대 partition-seconds 손실 → callback·warm-up 비용 → M/P가 높거나 non-sticky면 이득 축소.

Q2. Cooperative handoff가 동시에 두 owner를 막는 과정을 설명하세요.
좋은 답변 구조: owned O와 target T → old owner의 O-T revoke → new owner의 T-O를 첫 round에서 제외 → old owner가 새 owned set으로 rejoin → 두 번째 round에서 assign → generation/member epoch fencing → crash 시 lost와 idempotent side effect.

Q3. Eager production group을 CooperativeSticky로 무중단 전환하려면?
좋은 답변 구조: Client version·현재 assignor 목록·custom listener inventory → default multi-assignor 목록과 공통 supported protocol → 공식 rolling upgrade path → canary의 revoked count·blackout·lag baseline → wave rollout → inconsistent protocol·storm rollback 조건 → offset·sink 중복 검증.

10. 복습과 정답

어제 내용 회상 3문제

  1. Classic과 Consumer protocol의 assignment 계산 주체는 각각 누구인가?
  2. Consumer protocol에서 target assignment, pending partition, member epoch의 관계는?
  3. Consumer protocol에서 client의 session timeout 설정이 기대대로 적용되지 않을 수 있는 이유는?

짧은 정답: ① Classic은 group leader client, Consumer는 broker coordinator의 server assignor. ② Target은 desired state, 이전 owner가 revoke하기 전 새 owner의 partition은 pending, member epoch는 각 member의 적용 버전이며 target으로 수렴한다. ③ Consumer protocol의 heartbeat·session 정책은 broker/group 설정이 소유한다.

오늘 확인 3문제

  1. P=12, M=2일 때 eager와 cooperative의 revoke 범위와 round 수를 비교하라.
  2. onPartitionsRevoked, onPartitionsAssigned, onPartitionsLost를 정상 handoff와 crash에 배치하라.
  3. Cooperative 전환 효과를 검증할 metric 여섯 가지는?

채점 기준: ① Eager 12 full revoke·보통 1 round, cooperative 2 subset revoke·follow-up 가능과 나머지 10 지속(3점). ② Revoke→assign 정상 순서, crash/fencing은 lost이며 commit 안전성 차이(3점). ③ Revoked count, rebalance latency/rate, failed rebalance, callback max, partition blackout, lag 증가 면적, 이동률 M/P, warm-up 처리량 중 여섯 가지(4점). 총 8점 이상 통과.
