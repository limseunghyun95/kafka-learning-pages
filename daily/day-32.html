APACHE KAFKA 4.3 · WEEK 5 / DAY 32 · MEMBER LIVENESS

static membership, heartbeat, max poll interval

정적 신원과 두 개의 실패 감지 시계 · 이론 80분 + 실습 30분

한 줄 요약
Heartbeat는 process가 group coordinator와 통신 가능한지, max poll interval은 application이 다음 poll()까지 처리 진척을 내는지 보는 서로 다른 시계다. Static membership은 재시작 때 신원을 유지해 불필요한 rebalance를 줄이지만, 죽은 member의 partition을 session timeout까지 붙잡는 가용성 비용을 만든다.

1. 선수 용어 사전

MembershipConsumer group의 구성원으로 등록된 상태. Coordinator가 member의 신원·subscription·assignment·생존 여부를 관리한다.
Dynamic member재접속할 때 일시적인 member identity를 새로 받는 기본 방식. 짧은 재시작도 구성원 교체로 보일 수 있다.
Static membergroup.instance.id라는 사용자가 정한 안정적인 신원을 가진 member. 같은 group 안에서 그 ID를 동시에 쓰는 instance는 하나만 허용된다.
Heartbeat“나는 아직 살아 있고 group에 참여 중이다”라고 coordinator에 주기적으로 알리는 control-path 메시지. Record를 가져오는 Fetch와는 다르다.
Session timeout마지막 heartbeat 뒤 coordinator가 member를 실패로 판정하기까지 기다리는 시간. 짧으면 빠른 failover, 길면 일시 장애 흡수라는 trade-off가 있다.
Poll looppoll() → deserialize → 처리 → commit → 다시 poll()을 반복하는 application thread의 흐름.
max.poll.interval.msConsumer group을 사용할 때 연속된 poll() 호출 사이에 허용하는 최대 시간. 기본값은 Kafka 4.3 기준 300,000ms(5분)다.
Fencing오래된 process나 중복 신원이 더 이상 상태를 바꾸지 못하도록 coordinator가 거부하는 안전장치. Static ID 충돌은 FencedInstanceIdException으로 드러날 수 있다.
Liveness시스템이 결국 계속 진행하는 성질. Partition owner가 살아 보이지만 업무 처리를 못 하면 process liveness와 processing liveness가 갈라진다.
RTORecovery Time Objective. 장애 후 서비스를 다시 처리 가능한 상태로 만들기까지 허용하는 목표 시간.

2. 왜 중요한가

Consumer process가 살아 있다는 사실과 record 처리가 진척된다는 사실은 같지 않다. 네트워크 thread는 heartbeat를 계속 보내는데 application thread가 DB lock, 긴 GC, 무한 retry에 막힐 수 있다. Heartbeat만 보면 “정상”, 실제 data path는 “정지”다. 그래서 Kafka는 session timeout과 max poll interval이라는 두 감시축을 둔다.

반대로 rolling deployment에서 process가 10초 만에 같은 자리로 돌아오는데 매번 전체 group을 재조정하면 cache warm-up, state restore, commit callback이 반복된다. Static membership은 replica의 논리적 신원을 안정화해 이런 churn을 줄인다. 하지만 장애 process도 session timeout 전까지는 자기 자리의 owner로 남을 수 있다. 즉 rebalance 감소와 장애 회복 지연을 교환한다.

면접에서 “heartbeat가 있는데 왜 max poll이 필요한가?”에 답하려면 thread 분리, 상태 소유자, 실패 판정 시점, static member의 예외 경로, Classic/Consumer protocol의 설정 주체까지 연결해야 한다.

Data path: Fetch → local buffer → poll() 반환 → 업무 처리 → offset commit. Control path: Join·heartbeat·assignment·member fencing. Heartbeat가 성공해도 DB write나 commit이 성공했다는 뜻은 아니다.

상태의 소유자: Application은 마지막 poll 시각과 처리 중인 batch를 안다. Consumer client는 coordinator 통신과 max-poll 만료를 관리한다. Coordinator는 member identity·session·assignment를 소유한다. group.instance.id 값의 유일성과 배포 수명주기는 운영자가 책임진다.

분산 시스템의 failure detector는 완벽하지 않다. Timeout을 줄이면 진짜 장애를 빨리 감지하지만 GC pause·packet loss를 장애로 오인하는 false positive가 늘어난다. 늘리면 불필요한 rebalance는 줄지만 진짜 장애 때 partition이 오래 멈춘다.

Static identity의 불변식과 fencing

  • 불변식 1: 한 group 안에서 non-null group.instance.id는 동시에 하나의 active instance만 대표해야 한다.
  • 불변식 2: 같은 논리 replica는 재시작 뒤에도 같은 ID를 써야 static membership의 이득이 난다.
  • 불변식 3: 서로 다른 replica가 같은 ID를 공유하면 coordinator가 중복 instance를 fence한다.
  • 성공 확정: 재시작 process가 같은 static ID로 coordinator에 다시 합류하고 유효한 assignment/epoch를 받은 시점부터 group 참여가 확정된다. 단순히 process가 떴거나 TCP가 연결된 시점이 아니다.

Kubernetes에서는 Deployment의 무작위 Pod 이름보다 StatefulSet ordinal처럼 replica와 1:1로 안정된 값을 ID에 넣는 편이 자연스럽다. 단, Pod를 동시에 중복 실행하는 rollout 전략이면 이전 Pod가 완전히 fencing·종료되기 전 새 Pod가 충돌할 수 있다.

Kafka 4.0부터 Consumer protocol은 GA지만 4.3 client 기본은 여전히 Classic이다. “Kafka 4.x니까 heartbeat가 무조건 broker 설정”이라고 단정하면 틀리다. 먼저 group.protocol을 확인해야 한다.

처리량으로 max poll을 산정하기

한 번의 poll이 최대 R개 record를 주고, record당 p99 처리 시간이 S초이며 직렬 처리한다면 거친 상한은 R × S + commit + GC/network 여유다. R=500, p99=40ms면 처리만 20초다. 여기에 DB retry 10초, commit 2초, 50% 여유를 주면 약 48초가 된다.

그렇다고 timeout을 무조건 크게 잡으면 장애 감지가 늦어진다. 먼저 max.poll.records를 줄이거나 worker pool으로 처리하되, consumer thread의 offset frontier·pause/resume·shutdown을 명시적으로 관리한다. Consumer 객체 자체는 thread-safe가 아니므로 여러 worker가 같은 consumer를 직접 호출하면 안 된다.

Best practice: Static membership은 “항상 켜는 안정성 옵션”이 아니라 restart churn이 크고 replica identity를 안정적으로 만들 수 있을 때 선택한다. Canary group에서 rolling restart 중 rebalance count·partition blackout·session-timeout failover를 수치로 비교한다.

Anti-pattern: 모든 Pod에 group.instance.id=consumer-1을 넣기, max-poll 경고를 timeout 증가로만 숨기기, heartbeat 정상만 보고 건강하다고 판단하기, 처리 thread가 끝나기 전에 offset을 commit하기, static member를 graceful close하지 않고 오래 방치하기.

Edge case: Network는 살아 있어 heartbeat가 성공하지만 DB만 느릴 수 있다. 반대로 application 처리는 빠르지만 coordinator 경로만 단절될 수 있다. 또 old Pod가 zombie 상태로 살아난 뒤 동일 static ID의 새 Pod와 충돌할 수 있으므로 process-level fencing과 idempotent sink가 필요하다.

7. 20~40분 실습: static ID와 session failure window 관찰

목표: 동일 static ID 충돌이 fence되는지, process 전체를 멈췄을 때 session timeout 전후 assignment가 어떻게 달라지는지 관찰한다. 이 랩은 heartbeat/session failure를 주입한다. SIGSTOP은 application과 heartbeat를 함께 멈추므로 max-poll만 단독으로 재현하는 실험은 아니라는 점까지 설명할 수 있어야 한다.

사전 조건: 저장소 root, Docker 실행, local Kafka 4.3.1 compose 환경. Lab은 Classic protocol을 명시적으로 사용해 client timeout의 주체를 눈으로 확인한다.

예상 관찰: 8초 정지는 15초 session 안이므로 static-a가 복귀할 여지가 있다. 18초 정지는 coordinator가 static-a를 실패 처리하고 B 쪽으로 partition을 재할당할 수 있다. 시계 오차와 조회 순간 때문에 정확히 15.000초에 전이한다고 기대하지 말고 group state·member·assignment를 함께 본다.

4) Fencing 확인

A가 정상 실행 중일 때 Terminal D에서 A와 완전히 같은 설정·ID로 두 번째 consumer를 시작한다. 둘 다 오래 active로 남는 것이 아니라 중복 static instance가 거부되는 로그를 예상한다.

해석: Static membership이 외부 DB side effect까지 fencing하는 것은 아니다. 이 실험은 coordinator가 동일 group identity의 중복 참여를 막는 범위만 보여준다.

8. 놓치기 쉬운 함정

  • Heartbeat 성공 ≠ 업무 성공: Background control path가 살아도 processing thread는 멈출 수 있다.
  • max poll 초과 ≠ 즉시 process 종료: Group 소유권을 잃어도 old task나 외부 write는 계속 실행될 수 있다.
  • Static ≠ rebalance 없음: Subscription 변경, session 만료, scale-out, coordinator 전이 등은 여전히 assignment를 바꾼다.
  • ID를 UUID로 생성: 매 시작마다 바뀌면 dynamic member와 다를 바 없다.
  • ID를 상수로 공유: 모든 replica가 같은 ID면 fencing storm이 난다.
  • Consumer protocol 혼동: Kafka 4.3에서 group.protocol=consumer이면 client의 heartbeat/session 설정은 적용 대상이 아니다.
  • Timeout 단위: 설정은 milliseconds다. 30초 의도로 30을 넣으면 거의 즉시 장애 판정될 수 있다.
  • 평균 처리 시간 사용: max poll은 tail batch와 retry까지 버텨야 하므로 p95/p99와 최악의 bounded retry를 본다.

9. 대기업 기술 면접 질문

Q1. Heartbeat가 별도 thread에서 정상인데 왜 max.poll.interval.ms가 필요한가?

좋은 답변 구조: 요구사항(살아 있음과 처리 진척 분리) → 두 state owner(coordinator session vs client poll clock) → DB lock 예시 timeline → dynamic/static 만료 차이 → false positive와 failover trade-off → last-poll·heartbeat·lag의 조합 관측 순서로 답한다.

Q2. Kubernetes consumer에 static membership을 도입해도 되는지 설계해 보라.

좋은 답변 구조: Rebalance churn과 restart p99 수치 가정 → StatefulSet ordinal 기반 unique ID → rollout 중 duplicate fencing → session timeout과 RTO 예산 → canary/rollback → DB side effect idempotency까지 말한다. “켜면 안정적”이라는 한 문장으로 끝내지 않는다.

Q3. 처리 p99가 800ms, max.poll.records=500, RTO 60초인 consumer를 튜닝하라.

좋은 답변 구조: 직렬 최악 400초 계산 → 60초 RTO와 충돌 명시 → batch 축소/제한된 병렬성/pause-resume 대안 → 완료 offset frontier와 thread-safety → max poll·session을 독립 결정 → load test에서 tail·rebalance·duplicate side effect 검증으로 마무리한다.

10. 복습과 정답

어제 내용 회상 3문제

  1. Eager와 cooperative에서 P개 중 M개만 이동할 때 revoke 범위를 집합으로 설명하라.
  2. Cooperative가 두 번 이상의 rebalance를 거칠 수 있는데도 처리량 면에서 유리한 이유는?
  3. Cooperative handoff의 핵심 ownership 불변식은?
어제 정답/채점: ① Eager는 기존 O 전체, cooperative는 O-T만 revoke(2점). ② 이동하지 않는 P-M partitions의 data path가 계속 살아 partition-seconds 손실이 작아짐(2점). ③ 이전 owner가 소유를 보고하는 동안 새 owner에 동시에 assign하지 않음(2점).

오늘 확인 문제 3개

  1. Heartbeat와 max poll이 각각 감시하는 liveness를 구분하라.
  2. Static member가 max poll을 넘겼을 때 즉시 partition을 재할당하지 않는 이유와 비용은?
  3. Kafka 4.3에서 Classic과 Consumer protocol의 heartbeat/session 설정 주체는 누구인가?
오늘 정답/채점: ① Coordinator 통신/세션 생존 대 application poll progress(2점). ② 짧은 재시작에서 stable identity·assignment를 보존하려 session timeout까지 기다리며, 그만큼 crash failover/partition blackout이 길어질 수 있음(3점). ③ Classic은 client의 heartbeat.interval.ms/session.timeout.ms, Consumer protocol은 broker의 group.consumer.heartbeat.interval.ms/group.consumer.session.timeout.ms(3점). 총 8점 중 6점 이상이면 통과.
