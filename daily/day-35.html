회상: exactly-once가 외부 DB까지 자동 확장되지 않는 이유

원자성 경계·dual-write 실패 창·outbox/inbox를 설계 언어로 방어하기 · 이론 70분 + 실습 30분

한 줄 요약
Kafka transaction coordinator는 Kafka topic-partition과 __consumer_offsets의 commit만 원자적으로 조정한다. 외부 DB의 WAL·lock·commit 결과는 알지 못하므로, DB side effect까지 exactly-once로 만들려면 outbox·inbox·unique key·CDC 같은 별도 application protocol이 필요하다.

1. 선수 용어 사전

Exactly-once관찰 가능한 결과가 논리 작업당 한 번만 반영되는 성질. 전 세계 모든 side effect가 한 번이라는 뜻이 아니며, 시스템·operation·observer의 범위를 먼저 말해야 한다.
Idempotence같은 operation을 여러 번 실행해도 최종 상태가 한 번 실행한 것과 같은 성질. 중복 요청을 안전하게 흡수하는 도구이지 요청이 한 번만 도착한다는 보장은 아니다.
Atomicity한 경계 안의 여러 변경이 모두 commit되거나 모두 abort되는 성질. Kafka transaction과 DB transaction은 각각 다른 atomicity domain이다.
Dual write하나의 업무 요청에서 DB와 Kafka처럼 독립된 두 시스템에 쓰는 것. 두 번째 write 전후 crash가 부분 성공 상태를 만든다.
WALWrite-Ahead Log. DB가 data page보다 먼저 변경 의도를 기록해 crash recovery에 쓰는 로그. Kafka transaction log와 별도이며 서로 자동 복제되지 않는다.
Transactional outboxBusiness row와 발행할 event row를 같은 DB transaction에 저장하고, 별도 relay/CDC가 outbox를 Kafka로 전달하는 패턴.
Inbox / dedup keyConsumer가 처리한 event_id를 sink transaction 안에 기록해 재전달을 감지하는 패턴. Unique constraint나 conditional update가 원자적 gate가 된다.
CDCChange Data Capture. DB transaction log의 확정된 변경을 읽어 event stream으로 전달한다. Snapshot·ordering·schema·offset 책임은 별도로 설계해야 한다.
2PC / XACoordinator가 여러 resource에 prepare 후 commit/abort를 지시하는 분산 transaction 방식. 참여 시스템 지원, lock 시간, coordinator 장애, 운영 복잡성의 비용이 있다.
Unknown outcomeTimeout으로 caller는 실패를 받았지만 server commit 여부는 아직 모르는 상태. “오류 응답=미반영”으로 가정하면 중복 또는 누락을 만든다.

2. 왜 중요한가

주문 DB row를 저장한 뒤 order-created event를 Kafka에 보낸다고 하자. DB commit 뒤 process가 죽으면 event가 없다. 반대로 Kafka publish 뒤 DB commit 전에 죽으면 downstream은 존재하지 않는 주문을 본다. 순서만 바꾸면 실패 창의 방향만 바뀐다.

Kafka의 commitTransaction()은 Kafka 내부에서는 강한 의미를 갖는다. 여러 Kafka partitions의 records와 consumer offsets를 같은 transaction에 넣을 수 있다. 그러나 transaction coordinator가 보유한 참여 집합에는 PostgreSQL transaction ID, MySQL binlog position, REST 결제 승인 번호가 없다. 모르는 resource를 commit하거나 rollback할 수는 없다.

면접에서 “Kafka는 exactly-once를 지원한다”라고만 답하면 범위를 놓친다. 좋은 답은 무엇이 한 번인지, 누가 commit을 결정하는지, 어느 log가 source of truth인지, crash가 어느 두 operation 사이에 가능한지, 재시도를 어떻게 멱등하게 만드는지를 차례로 명시한다.

Data path: Kafka Fetch/Produce와 DB query/commit이 별도 connection·protocol·storage engine을 탄다. Control path: Kafka coordinator와 DB transaction manager가 각자의 state machine을 진행한다. 공통 coordinator나 합의 protocol을 명시적으로 도입하지 않는 한 두 결정 사이에는 atomic cut이 없다.

상태의 소유자: Kafka coordinator는 transactional.id, PID/epoch, Kafka 참여 partitions, commit/abort를 소유한다. Group coordinator는 input offset을 소유한다. DB는 row·constraint·WAL commit을 소유한다. Application은 두 결과를 연결하는 business key와 retry policy를 소유한다.

핵심 불변식: Kafka-only EOS에서는 output record와 다음 input offset이 같은 Kafka transaction에 있어야 한다. External sink에서는 event_id당 business mutation이 최대 한 번 반영되도록 dedup record와 mutation을 같은 DB transaction에 넣어야 한다.

왜 “정확히 한 번 전달”보다 “효과적으로 한 번”인가

Network에서는 response가 유실될 수 있다. Sender는 server가 commit했는지 모른 채 retry해야 한다. Retry를 막으면 누락, retry하면 중복 가능성이 생긴다. 그래서 실무 end-to-end 목표는 보통 at-least-once transport + idempotent effect다. 동일 event_id의 재전달을 허용하되 sink transaction이 한 번만 business state를 바꾸게 한다.

Dedup key는 payload hash보다 domain identity가 좋다. 같은 payload라도 서로 다른 주문일 수 있고, timestamp·serialization 차이로 hash가 달라질 수 있다. Producer가 stable event ID를 만들고 consumer가 unique constraint 또는 conditional write로 원자 검증한다.

Outbox가 닫는 창과 남기는 창

Business row와 outbox row를 같은 DB transaction에 넣으면 “DB는 성공했는데 발행할 정보가 영원히 없음”을 막는다. Relay는 commit된 outbox를 반복 읽어 Kafka에 publish할 수 있다. 하지만 Kafka ack 후 published=true 전에 relay가 죽으면 같은 event를 다시 publish한다. 따라서 outbox는 보통 누락 방지에 강하고, downstream inbox/idempotency와 함께 써야 중복 효과까지 막는다.

CDC relay는 polling race를 줄이고 DB log ordering을 활용하지만 만능은 아니다. Snapshot과 streaming 전환, schema evolution, partition key, 재시작 offset, poison event, tombstone 정책이 새 책임이 된다.

2PC를 기본 답으로 쓰기 어려운 이유

2PC는 참여 resource가 prepare/commit protocol을 지원하고 coordinator recovery가 정확해야 한다. Prepared transaction은 lock과 resource를 오래 잡을 수 있고 network partition 때 availability를 희생할 수 있다. Kafka와 일반 application DB 사이에 “설정 하나”로 생기는 기능이 아니다. 강한 원자성이 실제 business requirement이고 모든 participant·driver·운영 절차가 검증된 경우에만 비용과 함께 선택한다.

성공 확정 시점과 unknown outcome

  • DB commit 정상 반환: DB transaction의 durability만 확정한다. Kafka event 존재는 확정하지 않는다.
  • Kafka commitTransaction 정상 반환: Kafka transaction의 records·offsets commit을 확정한다. DB row는 확정하지 않는다.
  • Timeout: 미실행이 아니라 결과 미확인일 수 있다. Stable operation ID로 상태 조회·retry해야 한다.
  • Outbox row commit: 발행 의도가 durable해진다. Kafka 전달·downstream 처리는 아직 미확정이다.
  • Inbox+business commit: 해당 event ID의 sink 효과가 한 번 반영됐음을 sink DB가 증명한다.

Best practice: Design document 첫 줄에 보장 범위를 쓴다. 예: “Kafka input offset과 output topic은 atomic, PostgreSQL effect는 event_id unique constraint로 effectively-once.” Event ID 생성 주체·retention·dedup TTL·replay 정책·schema compatibility·reconciliation owner까지 명시한다.

Anti-pattern: Producer idempotence를 consumer EOS로 오해하기, DB write 뒤 Kafka send만 하고 retry policy 없음, offset을 DB보다 먼저 commit하기, outbox row를 business transaction 밖에서 insert하기, payload hash를 영구 idempotency key로 사용하기, DLQ로 보내면 일관성이 해결됐다고 보기.

Edge case: Dedup row TTL이 replay 보존 기간보다 짧으면 오래된 event가 다시 효과를 낸다. Business transaction은 rollback됐는데 outbox만 남으면 phantom event가 된다. CDC snapshot과 live log가 겹치면 중복이 가능하다. Compaction topic은 “transaction의 모든 record를 한꺼번에 영원히 관찰”하는 보장이 아니다.

7. 20~40분 실습: DB-first crash와 outbox 중복 발행

목표: SQLite를 외부 DB로 보고 DB commit 뒤 Kafka publish 전 crash를 재현한다. 이어 outbox가 누락 창을 닫지만 relay crash 때문에 중복 publish는 남긴다는 사실을 직접 관찰한다.

사전 조건: 저장소 root, Docker, Python 3 표준 라이브러리. Apache Kafka 4.3.1 compose 환경. 약 30분.

0) 실행 전 예측

  1. DB commit 뒤 publish 전에 process가 죽으면 어느 시스템이 진실을 갖는가?
  2. Outbox relay가 Kafka ack 뒤 published 표시 전에 죽으면 몇 번 publish될 수 있는가?
  3. Kafka에 중복 event가 있어도 DB 효과를 한 번으로 만들 최소 constraint는 무엇인가?

1) Topic과 SQLite 준비

docker compose up -d
docker compose exec broker bash -lc 'bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --if-not-exists --topic day35-order-events --partitions 1 --replication-factor 1'
python3 -c 'import sqlite3; c=sqlite3.connect("/tmp/day35.db"); c.executescript("CREATE TABLE IF NOT EXISTS orders(order_id TEXT PRIMARY KEY,status TEXT); CREATE TABLE IF NOT EXISTS outbox(event_id TEXT PRIMARY KEY,payload TEXT,published INTEGER DEFAULT 0);"); c.commit()'

2) 실패 주입 A: DB-first 뒤 의도적으로 중단

python3 -c 'import sqlite3; c=sqlite3.connect("/tmp/day35.db"); c.execute("INSERT INTO orders VALUES(?,?)",("order-42","CREATED")); c.commit(); print("DB_COMMIT_OK; crash before Kafka publish")'
python3 -c 'import sqlite3; print(sqlite3.connect("/tmp/day35.db").execute("SELECT * FROM orders").fetchall())'
docker compose exec broker bash -lc 'bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic day35-order-events --from-beginning --timeout-ms 3000'

예상: DB에는 order-42가 있지만 topic은 비어 있다. DB commit 성공이 Kafka event 성공을 뜻하지 않는다는 가장 작은 반례다.

3) Outbox로 missing-event window 닫기

python3 -c 'import sqlite3; c=sqlite3.connect("/tmp/day35.db"); c.execute("BEGIN"); c.execute("INSERT OR IGNORE INTO orders VALUES(?,?)",("order-43","CREATED")); c.execute("INSERT INTO outbox(event_id,payload) VALUES(?,?)",("evt-order-43","order-43|CREATED")); c.commit(); print("BUSINESS_AND_OUTBOX_COMMITTED")'
python3 -c 'import sqlite3; c=sqlite3.connect("/tmp/day35.db"); print(c.execute("SELECT * FROM orders").fetchall()); print(c.execute("SELECT * FROM outbox").fetchall())'

예상: Business row와 발행 의도가 함께 존재한다. 둘 중 하나만 남는 DB 내부 실패 창은 사라졌다.

4) 실패 주입 B: relay ack 뒤 published 표시 전 crash

printf 'evt-order-43|order-43|CREATED\n' | docker compose exec -T broker bash -lc 'bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic day35-order-events'
# ACK 뒤 crash를 가정해 outbox.published는 0으로 둔다.
printf 'evt-order-43|order-43|CREATED\n' | docker compose exec -T broker bash -lc 'bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic day35-order-events'
docker compose exec broker bash -lc 'bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic day35-order-events --from-beginning --timeout-ms 5000'

예상: 같은 event ID가 두 번 보인다. Outbox는 누락 가능한 의도를 durable하게 만들었지만 transport를 exactly-once로 만들지는 않았다. Downstream은 event_id를 unique inbox key로 사용해야 한다.

5) Inbox의 atomic gate 확인

python3 -c 'import sqlite3; c=sqlite3.connect("/tmp/day35.db"); c.executescript("CREATE TABLE IF NOT EXISTS inbox(event_id TEXT PRIMARY KEY); CREATE TABLE IF NOT EXISTS shipments(order_id TEXT PRIMARY KEY,status TEXT);"); c.execute("BEGIN"); cur=c.execute("INSERT OR IGNORE INTO inbox VALUES(?)",("evt-order-43",)); (c.execute("INSERT OR IGNORE INTO shipments VALUES(?,?)",("order-43","READY")) if cur.rowcount else None); c.commit(); print("first",c.execute("SELECT * FROM shipments").fetchall())'
python3 -c 'import sqlite3; c=sqlite3.connect("/tmp/day35.db"); c.execute("BEGIN"); cur=c.execute("INSERT OR IGNORE INTO inbox VALUES(?)",("evt-order-43",)); (c.execute("INSERT OR IGNORE INTO shipments VALUES(?,?)",("order-43","READY")) if cur.rowcount else None); c.commit(); print("retry",c.execute("SELECT * FROM shipments").fetchall())'

예상: 두 번째 실행에서도 shipment row는 하나다. 중요한 점은 inbox insert와 business mutation이 같은 DB transaction 안에 있다는 것이다.

6) 자주 나는 오류와 해결

UNIQUE constraint failed이 실험에서 중복 operation의 증거다. ID를 바꿔 숨기지 말고 INSERT OR IGNORE 또는 명시적 upsert 정책을 사용한다.
Consumer timeout 메시지실험용 --timeout-ms 종료는 정상이다. 출력된 records와 개수를 본다.
Topic에 이전 데이터가 있음새 topic 이름을 사용하거나 cleanup 후 재생성한다. 기존 evidence를 임의 삭제하지 않는다.
Python 조건식이 낯섦cur.rowcount가 1일 때만 shipment insert를 실행해 inbox unique gate를 표현한 것이다.

8. 놓치기 쉬운 함정

  • Exactly-once는 형용사가 아니다: Operation 집합과 observer를 명시해야 검증 가능한 요구사항이 된다.
  • Producer idempotence ≠ application idempotence: 새 producer 호출로 같은 payload를 다시 보내는 것은 protocol retry dedup 범위 밖일 수 있다.
  • read_committed ≠ 외부 DB commit: Kafka aborted records를 숨길 뿐 DB side effect를 rollback하지 않는다.
  • Outbox ≠ 중복 없음: Relay publish와 published 표시 사이 crash 때문에 at-least-once가 일반적이다.
  • Inbox TTL: Kafka replay 가능 기간보다 짧으면 오래된 duplicate가 다시 효과를 낸다.
  • Offset-first commit: DB write 전에 offset을 commit하면 crash 시 record가 영구 누락될 수 있다.
  • DB-first commit: Offset 전 crash는 재처리되므로 unique event ID가 없으면 duplicate가 난다.
  • Reconciliation 없는 설계: Online path가 아무리 강해도 unknown outcome과 수동 운영 실수는 남는다.

9. 대기업 기술 면접 질문

Q1. Kafka exactly-once가 PostgreSQL까지 보장되는가?

좋은 답변 구조: 먼저 보장 범위 질문 → Kafka transaction 참여 resource(topic partitions·offsets) → DB WAL이 coordinator에 없음을 설명 → DB-first/Kafka-first crash timeline → outbox/inbox 대안 → 중복·지연·운영 trade-off까지 말한다.

Q2. 주문 생성과 event 발행의 누락·중복을 모두 줄이는 설계를 하라.

좋은 답변 구조: Order ID와 event ID 정의 → orders+outbox 단일 DB transaction → CDC/relay at-least-once → Kafka key/partition ordering → downstream inbox unique transaction → retry·DLQ·replay·reconciliation → SLO와 소유팀으로 마무리한다.

Q3. 왜 2PC 대신 outbox를 선택했는가?

좋은 답변 구조: 원자성 요구 강도와 참여 resource 지원 여부 → 2PC lock·availability·coordinator recovery 비용 → outbox의 local atomicity와 eventual delivery → 남는 duplicate·latency → inbox와 reconciliation 보완 → 2PC가 필요한 예외 조건을 제시한다.
