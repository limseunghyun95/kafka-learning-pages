auto/manual commit과
중복·유실 window

업무 side effect와 복구 checkpoint 사이의 원자성 부재를 crash timeline으로 설계하기 · 이론 60분 + 실습 35분

한 줄 요약
Offset commit은 “이 record의 처리가 성공했다”는 Kafka의 판정이 아니라 이 consumer group이 장애 후 어디서 다시 시작할지 저장하는 checkpoint다. 처리 전에 next offset을 commit하면 유실 window, 처리 후 commit하면 중복 window가 생긴다. 일반 외부 sink에서는 둘을 동시에 0으로 만들 수 없으므로 at-least-once + idempotent sink, transaction/outbox 같은 경계 설계가 필요하다.

1. 선수 용어 사전

Offset commitconsumer group의 partition별 재시작 위치를 저장하는 작업. record 삭제나 broker log 이동이 아니다.
Next offsetcommit해야 하는 값은 마지막 완료 record의 offset이 아니라 다음에 읽을 offset이다. offset 41까지 완료했다면 42를 저장한다.
Auto commitenable.auto.commit=true일 때 client가 auto.commit.interval.ms 주기에 맞춰 position을 자동 commit하는 정책. 업무 처리 성공을 관찰하지 않는다.
Manual commitapplication이 처리 완료 frontier를 계산해 commitSync 또는 commitAsync를 호출하는 방식.
Failure window두 상태 변경 사이 crash가 나면 보장이 달라지는 시간 구간. 여기서는 sink side effect와 offset commit 사이가 핵심이다.
At-most-once중복 처리는 피하지만 일부 event가 처리되지 않을 수 있는 전달 의미. 보통 처리 전에 checkpoint를 전진시킨다.
At-least-once성공한 event를 놓치지 않도록 재처리할 수 있지만 crash 경계에서 중복 side effect가 생길 수 있는 의미.
Idempotent sink같은 business event ID를 다시 적용해도 최종 결과가 한 번 처리한 것과 같은 DB/API 저장소.
Completed frontierpartition에서 offset 0부터 연속으로 처리가 끝난 가장 먼 지점. 뒤 offset이 끝나도 앞에 gap이 있으면 frontier를 넘겨 commit하면 안 된다.
Group coordinatorgroup membership과 offset commit을 담당하는 broker 역할. commit을 __consumer_offsets compacted topic에 기록한다.
Generationrebalance로 갱신되는 group 세대. 늦은 옛 member의 commit을 막는 fencing 정보다.

2. 왜 중요한가

DB 업데이트는 성공했지만 commit response 전에 process가 죽으면 재시작 후 같은 record를 다시 읽는다. 반대로 commit이 먼저 성공하고 DB 업데이트 전에 죽으면 그 record는 기본 재시작 경로에서 건너뛴다. Kafka가 어느 쪽을 선택해주는 것이 아니라 application이 작업 순서를 선택한다.

면접에서 “manual commit이면 exactly-once”라고 말하면 부족하다. 강한 답은 상태 소유자(Kafka coordinator vs 외부 sink), 성공 확정 시점, crash 지점, replay identity, rollback을 말하고, 왜 두 독립 시스템의 원자성에는 transaction protocol이나 idempotency가 필요한지 설명한다.

3. Architecture: 같은 record가 중복 또는 유실되는 두 timeline

1 · pollP0 offset 41 반환, consumer position은 42로 전진
↓ 선택 A: commit 42 먼저
2A · Commitcoordinator가 P0=42를 offsets log에 저장
↓ CRASH — DB 처리 전
3A · Loss재시작은 42부터 → offset 41 side effect가 빠질 수 있음
──────── 또는 선택 B: DB 처리 먼저 ────────
2B · Processorder-900 상태를 DB에 반영
↓ CRASH — commit 42 전
3B · Duplicate재시작은 41부터 → 같은 side effect 재실행 가능
↓ business event ID로 idempotent upsert
4 · Converge재처리돼도 최종 DB 상태는 한 번 적용한 것과 같음
  1. poll: P0의 position 42는 client memory 상태이고 아직 복구 checkpoint가 아니다.
  2. commit path: OffsetCommitRequest는 data partition leader가 아니라 group coordinator로 간다.
  3. coordinator: group generation·member 권한을 검증하고 __consumer_offsets에 group/P0=42를 append한다.
  4. success: commit response 성공은 checkpoint 내구성의 확정이지 DB 처리 성공의 확정이 아니다.
  5. restart: 새 member가 committed 42를 읽고 그 위치부터 fetch한다. commit되지 않은 position은 process와 함께 사라진다.

OffsetCommit protocol

Consumer는 group ID를 hash해 배정된 offsets topic partition의 leader, 즉 group coordinator를 찾는다. coordinator는 현재 generation/member가 그 partition을 소유하는지 검증한 후 OffsetCommitRequest를 compacted __consumer_offsets에 기록한다. 성공 response 뒤에는 다른 member가 OffsetFetch로 최신 checkpoint를 복구할 수 있다. compacted topic이므로 과거 모든 commit을 업무 audit log로 의존하면 안 된다.

Auto commit의 정확한 경계

enable.auto.commit=true는 client가 주기적으로 offset을 commit하지만 application의 DB transaction이나 worker 완료 신호를 알지 못한다. 단일 poll thread가 받은 batch를 모두 처리한 뒤 다음 poll로 돌아오는 단순 구조에서는 주로 처리 후 commit에 가까워 중복 window가 남는다. 반면 poll thread가 record를 worker queue에 넘기고 곧바로 다음 poll을 호출하면 아직 처리되지 않은 position까지 자동 commit되어 유실 window가 생길 수 있다.

commitSync vs commitAsync

방식장점비용·주의
commitSync성공·예외를 호출 지점에서 확인, 종료·revoke 경계가 단순coordinator RTT 동안 poll thread block, timeout·rebalance 예외 처리 필요
commitAsynccommit latency를 pipeline과 겹쳐 throughput 개선callback 실패를 관측해야 하며 오래된 offset을 임의 재시도하면 최신 checkpoint를 뒤로 덮을 위험

실무 패턴은 steady state에 async commit을 쓰되 callback에서 offset·generation·error를 기록하고, shutdown이나 partition revoke 전에 completed frontier를 sync commit하는 방식이다. 다만 framework가 제공하는 ack/rebalance lifecycle과 중복되지 않게 소유권을 한 곳에 둔다.

병렬 worker의 contiguous frontier

P0의 40, 41, 42를 동시에 처리해 42와 40이 끝났지만 41이 진행 중이라면 43을 commit하면 안 된다. crash 후 43부터 시작해 41을 잃기 때문이다. 안전한 next offset은 41이다. partition별 bitmap/ordered set으로 완료를 추적하고 앞에서부터 연속 완료된 지점만 commit한다. 이 자료구조는 처리량을 주지만 memory·timeout·poison pill 정책이라는 비용을 만든다.

5. 실무 설계 판단

손실 허용 telemetry단순 auto commit도 가능하되 loss budget 명시운영 복잡도 감소와 정확성 비용을 의식적으로 교환한다.
고비용 side effectinbox/dedup table, 상태 machine, retry budgetAPI가 비멱등이면 Kafka commit만으로 중복 청구를 막을 수 없다.

Best practice: commit 기준을 코드 주석이 아니라 ADR로 남긴다. partition별 processed_offset·committed_offset·commit latency/error·duplicate suppression count를 관측한다. graceful shutdown과 rebalance revoke에서는 새 작업 수락을 중지하고 bounded time 안에 완료 frontier만 commit한다.

Anti-pattern: poll 직후 전체 batch의 next offset을 먼저 commit, async callback 무시, 실패한 오래된 async commit을 무조건 재시도, 여러 worker 중 최대 완료 offset을 commit, DLQ에 보냈다는 이유로 원본과 복구 근거 없이 offset 전진.

Edge case: commit response가 유실되면 client는 성공 여부를 모를 수 있다. 같은 또는 더 높은 안전 frontier를 재commit하는 것은 괜찮지만, generation이 바뀌었거나 partition 소유권이 사라졌다면 늦은 commit을 강행하지 말아야 한다. commit metadata와 leader epoch는 진단·log truncation 탐지에 도움을 줄 수 있다.

Version/engine 차이: Kafka 4.3 Java consumer의 enable.auto.commit 기본값은 true다. Spring Kafka의 ack mode, Kafka Connect의 task offset, Flink checkpoint는 서로 다른 상위 state machine이므로 raw KafkaConsumer 설정만 보고 의미를 추측하지 않는다.

7. 35분 실습: checkpoint와 처리 증거를 분리해 관찰

실행 전 예측
P0 offset 0과 1을 읽은 뒤 checkpoint가 2라면 재시작 시 어디서 시작할까? offset 1의 업무 처리가 끝나지 않았는데 2를 저장했다면 어떤 유실이 생기는지, 반대로 처리 후 checkpoint 1에서 죽으면 무엇이 중복되는지 적는다.

사전 조건: 저장소 루트, Docker 실행 가능, local Kafka 4.3.1 단일 broker. 아래 offset reset은 실습 전용 group/topic에만 실행한다.

  1. 환경·1 partition topic:
    make up docker compose exec broker /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server localhost:9092 --create --if-not-exists \ --topic day19.commit --partitions 1 --replication-factor 1
  2. 5개 event 입력:
    make produce TOPIC=day19.commitorder-0부터 order-4까지 한 줄씩 넣고 종료한다.
  3. auto commit 관찰:
    docker compose exec broker /opt/kafka/bin/kafka-console-consumer.sh \ --bootstrap-server localhost:9092 --topic day19.commit \ --group day19-auto --from-beginning --max-messages 2 \ --consumer-property enable.auto.commit=true \ --consumer-property auto.commit.interval.ms=1000 \ --property print.offset=true정상 종료 후 group describe로 committed offset을 확인한다.
  4. 실패 주입: 새 group day19-crash로 같은 명령을 실행하되 record가 보인 직후 Ctrl+C로 종료한다. 아래 describe를 즉시 실행해 출력된 record 수와 committed offset이 일치하는지 비교한다.
    docker compose exec broker /opt/kafka/bin/kafka-consumer-groups.sh \ --bootstrap-server localhost:9092 --describe --group day19-crash
  5. manual 경계 모사: 실습 group이 inactive임을 확인한 뒤 checkpoint를 1로 명시해 재시작 위치를 관찰한다.
    docker compose exec broker /opt/kafka/bin/kafka-consumer-groups.sh \ --bootstrap-server localhost:9092 --group day19-manual \ --topic day19.commit --reset-offsets --to-offset 1 --execute그 group으로 consume하면 offset 1부터 보이는지 확인한다. 이 CLI reset은 application commitSync 구현이 아니라 checkpoint 의미만 분리해 보는 도구다.

예상 관찰: committed offset N은 N부터 다시 읽게 한다. crash 타이밍에 따라 출력된 마지막 record와 checkpoint 사이가 다를 수 있다. 한 번의 결과로 auto commit의 보장을 일반화하지 말고 timeline과 설정을 함께 기록한다.

자주 나는 오류와 해결: group이 active면 reset이 거부되므로 consumer를 종료하고 재확인한다. group이 처음이라 offset entry가 없으면 먼저 한 번 소비하거나 --to-earliest로 초기화한다. 출력 offset과 committed offset을 혼동하지 않는다. production group에는 reset 명령을 쓰지 않는다.

Cleanup:
docker compose exec broker /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server localhost:9092 --delete --topic day19.commit make down

8. 놓치기 쉬운 함정

  • commit 값은 next offset: 완료 offset 자체를 저장하면 정상 재시작마다 마지막 record를 다시 읽는다.
  • auto commit은 처리 성공 감지기가 아니다: worker queue 사용 시 특히 위험하다.
  • manual commit ≠ exactly-once: 두 독립 상태 저장소 사이 crash window는 남는다.
  • max completed offset ≠ contiguous frontier: 앞 gap을 넘기면 유실된다.
  • lag 0 ≠ sink 완료: committed offset을 일찍 전진시키면 lag는 좋아 보여도 DB는 비어 있을 수 있다.
  • rebalance는 ownership 변경: revoke 뒤 옛 worker가 side effect·commit을 계속하지 않도록 fencing해야 한다.

9. 대기업 기술 면접 질문 3개

Q1. 처리와 commit 순서에 따른 delivery semantics를 timeline으로 설명하세요.
좋은 답변 구조: offset 41/next 42 예시 → commit-before-process crash는 loss → process-before-commit crash는 duplicate → 외부 sink 원자성 부재 → 요구사항에 따라 at-least-once+idempotency 또는 transaction 대안 → 관측·복구.

Q2. 8개 worker가 partition 하나를 병렬 처리할 때 무엇을 commit합니까?
좋은 답변 구조: partition ordering 요구 확인 → offset별 완료 set → contiguous frontier만 next offset으로 commit → 앞 record 지연/poison pill → bounded buffer·pause → rebalance revoke drain/fence → memory와 throughput trade-off.

Q3. Kafka→DB exactly-once를 설계해보세요.
좋은 답변 구조: 정확히 한 번의 범위 정의 → Kafka commit과 DB transaction은 독립임을 명시 → business event ID unique constraint/inbox table → DB transaction으로 side effect+dedup 기록 → 처리 후 Kafka commit → crash별 replay 수렴 → 대안으로 outbox/CDC 또는 Kafka 내부 transaction, RPO/RTO와 운영 비용.
