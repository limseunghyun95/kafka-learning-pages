분산 로그 정신 모델을 3분 답변과 장애 추론으로 압축하기 · 예상 회상 35분 + 실습 30분

한 줄 요약
Kafka를 제대로 설명하려면 구성요소 이름보다 누가 상태를 소유하고, 요청이 어디로 가며, 언제 성공이 확정되고, 실패하면 어느 위치에서 재개하는지를 시간순으로 말해야 한다.

1. 선수 용어 사전

Data path실제 record bytes가 producer→partition leader→consumer로 이동하는 경로.
Control pathtopic metadata, leader, group membership·assignment처럼 data path를 가능하게 하는 제어 상태와 요청 경로.
Metadatatopic·partition·leader·broker 위치 같은 “어디로 요청할지”에 관한 정보. record payload 자체가 아니다.
Record batchproducer가 여러 record를 묶은 전송·압축 단위. 요청 수와 syscall 비용을 나눠 내는 amortization 수단이다.
Partition leader해당 partition의 append와 client read/write를 담당하는 replica. producer와 consumer는 leader를 찾아 직접 요청한다.
Offsetpartition log 안의 위치. 전역 message ID도, 업무 처리 완료 flag도 아니다.
Position / Commitposition은 현재 process가 읽을 다음 위치, commit은 group이 장애 후 재개할 checkpoint다.
Invariant상태가 바뀌어도 지켜야 하는 규칙. 예: 같은 group 안의 한 partition에는 한 시점에 active owner가 하나다.
Failure window두 상태 변경 사이 crash가 나면 보장이 달라지는 구간. 처리와 offset commit 사이가 대표적이다.

2. 왜 중요한가

면접에서 “producer가 broker에 보내고 consumer가 읽습니다”는 기능 목록일 뿐이다. 좋은 답은 bootstrap이 모든 요청을 중계하지 않는 이유, key가 순서 범위를 어떻게 정하는지, broker append 성공과 외부 DB 처리 성공이 왜 다른지까지 이어진다.

실무 장애도 같은 정신 모델로 푼다. produce timeout이면 metadata·partition leader·broker request·ISR 중 어디서 멈췄는지 좁히고, lag 증가면 log-end 상승과 committed offset 정체를 분리한다. 흐름을 말하지 못하면 지표 이름을 알아도 원인과 조치를 연결하기 어렵다.

3. Architecture: 먼저 보고, 마지막에는 가리고 말하기

1 · Bootstrapclient가 임의 broker에 연결해 topic·partition leader metadata 획득
↓ key 직렬화·partition 선택·batch 축적
2 · Produceproducer가 선택한 partition leader에 ProduceRequest 전송
↓ leader append · replication 조건 · ProduceResponse
3 · Durable logpartition-local offset이 부여되고 retention 동안 record 보존
↓ FindCoordinator · join · partition assignment
4 · Fetchconsumer가 assignment와 position으로 partition leader에 FetchRequest
↓ deserialize · process · external side effect
5 · Commit처리 정책에 따라 group coordinator에 다음 재개 offset 저장
crash → 새 owner가 committed offset부터 재개 → 중복 또는 유실 창 추론

Control path를 따로 말하라: KRaft controller quorum은 topic·partition·broker·leader 같은 cluster metadata를 replicated log로 합의한다. group coordinator는 group membership·assignment·offset을 다룬다. 둘 다 모든 record payload가 거쳐 가는 중앙 router는 아니다.

4. CS 내부 동작: 3분 답변의 뼈대

단계상태 소유자성공 의미·불변식
Partition 선택producer같은 key는 partition 수와 partitioner가 같다는 조건에서 같은 partition으로 간다.
Append/offsetpartition leader순서는 topic 전체가 아니라 한 partition log 안에서 정의된다.
Produce ackleader와 replica 조건acks 정책을 만족한 Kafka write 성공이며 consumer·sink 성공은 아니다.
Assignmentgroup coordinator/protocol같은 group의 한 partition에는 active owner 하나. 병렬성은 partition 수가 상한이다.
Fetch positionconsumer memorypoll로 전진하지만 아직 durable recovery checkpoint가 아닐 수 있다.
Committed offsetgroup별 coordinator-backed state보통 다음 처리할 위치. 다른 group과 독립이며 replay로 이동할 수 있다.
Business resultapplication/sinkKafka commit과 외부 DB write는 기본적으로 하나의 atomic transaction이 아니다.

OS·network 관점까지 한 문단 덧붙이기

Producer batching은 여러 record가 request·TCP·syscall 비용을 나눠 내게 하고 compression ratio를 높인다. Broker는 append-only segment와 OS page cache를 활용해 locality를 얻는다. Consumer는 offset을 명시한 pull/fetch로 처리 속도를 조절한다. 그래서 Kafka의 처리량은 “메모리 queue라서”가 아니라 sequential I/O, batching, cache, zero-copy 가능한 경로, backpressure 가능한 pull 모델이 함께 만든 결과다.

틀린 설명을 교정하는 기술 리뷰

위험한 한 문장교정할 경계
Kafka는 queue라 읽으면 삭제된다.record 보존은 retention 정책, 읽기 진도는 group별 offset이다.
offset은 message ID다.partition-local position이라 topic·partition 없이 유일하지 않다.
consumer를 늘리면 항상 빨라진다.같은 group의 active 병렬성은 partition 수 이하이며 hot key·sink가 병목일 수 있다.
acks=all이면 end-to-end exactly-once다.Kafka append durability와 consumer 처리·외부 side effect의 보장 범위를 분리한다.
controller가 모든 메시지를 전달한다.controller는 cluster metadata control plane, record는 partition leader data path다.

Best Practice

  • 설계 문서에 data path와 control path를 별도 색·표로 기록하고 각 상태의 owner를 적는다.
  • topic·partition 수는 peak throughput뿐 아니라 ordering key cardinality, skew, replay 시간, 운영 비용으로 결정한다.
  • producer 성공, Kafka visibility, consumer 처리, sink commit을 서로 다른 성공 시점과 SLI로 관측한다.
  • consumer는 event ID를 로그에 남기되 partition·offset·group과 함께 correlation하여 중복과 누락을 추적한다.
  • replay·reset은 대상 group·범위·rate limit·idempotency·rollback offset을 승인한 runbook으로 수행한다.

Anti-pattern·edge case·version 경계

  • Anti-pattern: bootstrap.servers의 broker 한 대가 모든 traffic을 중계한다고 설명한다. 실제 leader metadata를 받은 뒤 해당 broker로 직접 연결한다.
  • Anti-pattern: lag 0을 업무 완료로 정의한다. commit-before-process 또는 sink 실패면 lag 0이어도 유실처럼 보일 수 있다.
  • Edge case: partition 수를 늘리면 key hash의 나머지 연산 대상이 바뀌어 같은 key의 과거·미래 record가 다른 partition에 존재할 수 있다.
  • Edge case: producer callback 실패 뒤 application이 새 producer session으로 재전송하면 broker idempotence 범위 밖 중복을 고려해야 한다.
  • Version: Kafka 4.x는 KRaft가 기본 운영 모델이다. ZooKeeper 기반 consumer·controller 설명은 레거시 비교로만 사용한다.

7. 30분 회상 실습: 보지 않고 trace를 재구성하라

사전 조건: 저장소 루트, Docker, 종이 한 장 또는 빈 문서. 실행 전에 다음을 예측한다. 같은 key의 세 record는 어디에 모이는가? 두 group은 몇 번 읽는가? Group A만 마지막 offset에서 한 칸 뒤로 reset하면 어느 상태만 바뀌는가?

1단계 · 최소 데이터 만들기

make up

docker compose exec broker /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --create \
  --topic day07-recall --partitions 3 --replication-factor 1

printf 'order-42:first\norder-42:paid\norder-42:shipped\n' | \
docker compose exec -T broker /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic day07-recall \
  --property parse.key=true --property key.separator=:

2단계 · 두 group으로 독립 소비

for g in day07-primary day07-audit; do
  docker compose exec broker /opt/kafka/bin/kafka-console-consumer.sh \
    --bootstrap-server localhost:9092 --topic day07-recall \
    --group "$g" --from-beginning --max-messages 3 \
    --property print.key=true --property print.partition=true \
    --property print.offset=true
done

예상 관찰: 두 group이 각각 세 record를 읽고, 같은 key라 세 record가 같은 partition에 있으며 그 partition 안 offset 순서가 증가한다.

3단계 · 실패 주입과 상태 ledger

두 consumer가 종료된 inactive 상태에서 Group A만 한 offset 뒤로 이동한다. 먼저 --execute 없는 plan을 보고, 그 다음 한 번만 실행한다.

docker compose exec broker /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --group day07-primary \
  --topic day07-recall --reset-offsets --shift-by -1

docker compose exec broker /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --group day07-primary \
  --topic day07-recall --reset-offsets --shift-by -1 --execute

종이에 log bytes / partition LEO / Group A committed offset / Group B committed offset / external side effect 다섯 줄을 만들고 “변함/불변”을 적는다. 정답은 A offset만 뒤로 이동하며, log·LEO·B offset·기존 side effect는 그대로다.

4단계 · 화면을 가리고 3분 설명

이 메일을 닫고 다음 7개 단어만 보고 말한다: bootstrap → metadata → partition → leader append → assignment → fetch/process → commit/replay. 각 단계마다 owner, request/response, 성공 시점, crash 결과를 한 문장씩 붙인다.

채점: 0~2개 경계면 Level 1, data/control path와 position/commit을 분리하면 Level 2, 수치 가정·failure window·sink idempotency·대안까지 말하면 Level 3.

자주 나는 오류와 해결

  • record가 같은 partition이 아니다: parse.key=true와 key.separator=:가 producer에 적용됐는지 확인한다.
  • reset이 거부된다: 두 group consumer가 종료됐는지 --describe --state로 확인한다.
  • offset이 없는 partition도 -1 되는 줄 알았다: shift는 현재 committed offset과 사용 가능한 log 경계에 따라 조정된다.
  • 설명이 broker에서 시작한다: client는 먼저 bootstrap과 metadata를 거쳐 leader를 찾아야 한다.
  • commit을 처리 성공과 동일시한다: 외부 sink 상태와 Kafka checkpoint의 transaction 경계를 다시 그린다.

Cleanup

docker compose exec broker /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --delete \
  --group day07-primary --group day07-audit

docker compose exec broker /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --delete --topic day07-recall

8. 놓치기 쉬운 함정

  • bootstrap broker = master: 시작점일 뿐이며 metadata를 얻은 client가 partition leader에 직접 요청한다.
  • topic-wide ordering: Kafka의 기본 순서 보장은 partition-local이다.
  • offset = 처리 결과: checkpoint와 external side effect는 별도 상태다.
  • group = consumer process: group은 논리적 subscriber이고 여러 process가 partition을 분담한다.
  • replay = log 수정: group offset을 바꾸며 broker log와 다른 group offset은 유지된다.
  • fast disk 하나로 설명: batching·sequential I/O·page cache·network amortization·pull을 함께 말해야 한다.

9. 대기업 기술 면접 질문

  1. 한 주문 event가 Kafka를 거쳐 DB에 반영되는 전 과정을 설명하라.
    좋은 답은 order_id ordering 요구, metadata·partitioner·leader append·ack·group assignment·fetch/process·commit을 시간순으로 말한다. process→DB write→commit failure window, idempotency와 outbox/inbox 대안까지 범위를 방어한다.
  2. 12 partitions, 6 consumers인데 lag가 계속 증가한다. 무엇을 볼 것인가?
    peak input과 partition별 lag slope, consumer 처리 rate·CPU, member assignment, key skew, sink p99를 수집한다. 병렬성 ceiling은 아직 12이지만 worker 증설보다 hot partition·sink 병목 여부를 먼저 판단하고 회복 시간 식을 제시한다.
  3. acks=all과 consumer commit이 모두 성공했는데 중복이 가능한가?
    producer append durability와 consumer checkpoint를 구분한다. sink write 후 commit response가 application에 도달하기 전 crash·retry, application-level 재전송을 설명하고 event ID dedup, transaction 범위, 보상 처리 대안을 비교한다.

10. 복습과 정답

어제 내용 회상 3문제

  1. Group A offset을 reset해도 Group B offset이 바뀌지 않는 이유는?
  2. offset reset 전에 consumer를 inactive로 만들고 plan을 확인해야 하는 이유는?
  3. Kafka replay 성공만으로 업무 복구 완료라 말할 수 없는 이유는?

채점 기준: ① (group, topic, partition)별 독립 checkpoint, ② in-memory position·후속 commit 경합 방지와 scope 검증, ③ 외부 sink side effect가 별도 transaction domain이라 ID·checksum 검증이 필요함을 말하면 통과.

오늘 내용 확인 3문제

  1. KRaft controller, group coordinator, partition leader의 상태와 요청 책임을 각각 구분하라.
  2. position, committed offset, business completion이 서로 다른 이유는?
  3. “Kafka는 디스크인데 왜 빠른가?”를 네 가지 CS 근거로 답하라.

짧은 정답: ① controller는 cluster metadata, coordinator는 membership·assignment·group offset, leader는 record append/fetch를 담당한다. ② process memory·durable recovery checkpoint·외부 sink 결과의 owner와 실패 시점이 다르다. ③ sequential append/locality, batch amortization·compression, OS page cache, 효율적 network 전송과 pull 기반 흐름 제어를 들면 통과.
