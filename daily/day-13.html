APACHE KAFKA 4.3 · WEEK 2 / DAY 13 · INTEGRATION LAB

segment·index·batch 크기 관찰

논리 offset이 실제 file position과 record batch가 되는 증거 체인 · 예상 이론 35분 + 실습 40분

한 줄 요약
Partition의 record는 record batch로 active .log 끝에 append되고, 누적 bytes·시간 조건이 차면 새 base offset의 segment로 roll된다. Sparse .index는 모든 record가 아니라 일부 relative offset→file position만 보관하므로, lookup은 index로 근처에 점프한 뒤 log batch를 순차 scan한다. 오늘은 이 관계를 설정→생산→파일→dump→조회 결과로 직접 증명한다.

1. 선수 용어 사전

Partition log한 partition의 ordered record sequence. 논리적으로 하나지만 물리적으로 여러 segment다.
SegmentLog를 관리 가능한 크기로 자른 파일 묶음. 보통 같은 base offset의 .log, .index, .timeindex가 한 조다.
Active segment현재 append되는 마지막 segment. 과거 closed segment와 운영 제약이 다르다.
Segment roll크기·시간 조건으로 active segment를 닫고 다음 record offset을 base offset으로 새 segment를 여는 전이.
Base offsetSegment 파일명과 record batch header에 쓰이는 기준 offset. Index에는 이 값과의 차이인 relative offset이 들어간다.
Sparse index모든 record가 아니라 일정 log bytes 간격으로만 저장하는 드문드문한 색인.
File position해당 .log 파일 시작에서 몇 번째 byte인지 나타내는 위치.
Record batch같은 partition record와 공통 header를 묶은 전송·저장 단위. 한 batch만 있어도 records count는 여러 개일 수 있다.
Compression ratio원본 bytes÷압축 bytes. 같은 record 수라도 codec·내용에 따라 segment 증가 속도가 달라진다.
PreallocationIndex가 최대 크기 공간을 미리 잡는 동작. Active index의 apparent size와 실제 entry 수를 혼동하면 안 된다.
Page cacheOS가 file page를 RAM에 cache하는 영역. File size는 디스크 구조이지 현재 RAM residency를 직접 뜻하지 않는다.
Invariant상태가 바뀌어도 반드시 지켜야 하는 조건. 예: segment 안 offset 순서와 index position의 유효성.

2. 왜 중요한가

운영에서 “disk가 빨리 찬다”, “retention이 늦다”, “cold read가 느리다”를 해결하려면 topic byte rate만 봐서는 부족하다. Partition별 segment 수, active segment age, codec, batch fill ratio, sparse index 밀도를 연결해야 원인을 설명할 수 있다. Segment가 너무 작으면 file·open/close·index·retention 작업 수가 늘고, 너무 크면 retention/compaction 단위와 장애 복구 scan 비용이 커진다.

면접에서도 “Kafka는 sequential I/O라 빠릅니다”에서 멈추면 약하다. 어떤 bytes가 append되고, index가 무엇을 생략하며, lookup이 어디부터 scan하고, 압축이 roll 시점을 어떻게 바꾸는지를 실제 artifact로 방어해야 실무 경험이 드러난다.

3. Architecture: produce부터 lookup까지의 증거 체인

1 · BatchProducer가 같은 partition의 record를 모아 header·CRC·codec을 가진 batch 생성
↓ ProduceRequest → partition leader
2 · ValidateLeader가 size·CRC·sequence를 검증하고 batch에 partition offset 범위 부여
↓ active .log 끝에 append
3 · Index누적 bytes가 index.interval.bytes 경계를 넘으면 relative offset→position entry 추가
↓ segment size/time 조건
4 · Roll기존 segment close·index trim → 다음 offset 이름의 새 log/index/timeindex 생성
↓ Fetch/ListOffsets(offset X)
5 · LocateBase offset으로 segment 선택 → sparse index binary search → floor entry position으로 점프
↓ exact record는 batch decode·sequential scan
6 · TransferPage cache/disk에서 batch bytes를 읽고 FetchResponse로 consumer에 전달

Control path: KRaft controller는 topic config와 partition leadership을 관리하지만 record batch의 append·index entry 작성은 partition leader broker의 data path다. Controller quorum log와 user topic segment를 같은 “Kafka log”라는 말만으로 섞지 않는다.

Sparse index의 공간·시간 trade-off

index.interval.bytes를 I, segment log size를 S라고 단순화하면 offset index entry 수는 대략 S÷I 방향으로 증가한다. I를 작게 하면 exact offset 근처로 더 가까이 점프하지만 index memory/disk와 update 비용이 늘어난다. I를 크게 하면 index는 작지만 floor entry 뒤 scan bytes가 커진다. “더 촘촘할수록 무조건 좋다”가 아닌 locality와 memory의 교환이다.

Batch와 segment size를 분리하기

Producer batch.size는 보내기 전 memory buffer의 목표 상한이고 topic segment.bytes는 broker log file roll 기준이다. 압축 가능한 payload는 같은 record 수라도 적은 on-disk bytes를 사용하므로 roll이 늦어진다. 공식 형식에서 record batch의 disk 크기는 batchLength + 12 bytes다. Record 수만 세어 segment 크기를 예측하면 틀린다.

성공 확정과 failure window

Producer ack 성공은 설정된 replication 조건의 완료이지 index file이 물리 disk에 fsync됐다는 뜻은 아니다. Log append 후 process crash, page cache writeback 전 host failure, index corruption은 서로 다른 창이다. Kafka는 log가 원본이고 index는 파생 구조라 복구 시 재구성할 수 있지만, 운영자가 live file을 직접 수정하면 offset 불변식을 깨뜨릴 수 있다.

7. 40분 통합 랩

사전 조건: 저장소 root, Docker Desktop, apache/kafka:4.3.1. Single broker라 replication durability는 측정하지 않는다.
산출물: config → segment 파일 목록 → batch dump → end offset의 네 증거를 같은 topic에 연결한다.

실행 전 예측

  1. 1MiB segment에 약 1.3MiB의 압축이 잘 안 되는 payload를 쓰면 .log는 몇 개 이상 생길까?
  2. index.interval.bytes=1024면 기본 4096보다 index entry가 대략 어느 방향으로 변할까?
  3. Producer가 2,000 record를 보내도 dump의 batch 수가 반드시 2,000일까?

Step 1 · 관찰하기 쉬운 topic

make up
docker compose exec broker /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --create \
  --topic day13.storage --partitions 1 --replication-factor 1 \
  --config segment.bytes=1048576 \
  --config index.interval.bytes=1024 \
  --config compression.type=producer
docker compose exec broker /opt/kafka/bin/kafka-configs.sh \
  --bootstrap-server localhost:9092 --entity-type topics \
  --entity-name day13.storage --describe

예상: 세 override가 보인다. Topic config는 KRaft metadata에 기록되고 broker log의 다음 판단에 적용된다.

Step 2 · Batch를 만들며 약 1.3MiB 생산

docker compose exec broker bash -lc \
  "for i in \$(seq 1 2200); do \
  printf '%s|%0600d\n' \"\$i\" \"\$i\"; done | \
  /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic day13.storage \
  --producer-property batch.size=65536 \
  --producer-property linger.ms=20 \
  --producer-property compression.type=none"

예상: Record별 호출이 batch로 합쳐지고 1MiB 경계 근처에서 새 segment가 열린다. Exact 개수는 header·batch 경계와 producer timing 때문에 계산치와 다를 수 있다.

Step 3 · 물리 파일과 논리 offset 연결

docker compose exec broker bash -lc \
  "find /tmp/kraft-combined-logs/day13.storage-0 \
  -maxdepth 1 -type f \
  \( -name '*.log' -o -name '*.index' -o -name '*.timeindex' \) \
  -exec ls -ln {} + | sort -k9"
docker compose exec broker /opt/kafka/bin/kafka-get-offsets.sh \
  --bootstrap-server localhost:9092 \
  --topic day13.storage --time -1

관찰: 파일명의 20자리 숫자는 base offset이다. End offset은 “다음에 쓸 offset”이므로 마지막 record offset보다 1 크다. Active index의 preallocated size가 entry 수와 같다고 해석하지 않는다.

Step 4 · Batch header와 index dump

docker compose exec broker bash -lc \
  "f=\$(find /tmp/kraft-combined-logs/day13.storage-0 \
  -name '*.log' | sort | head -1); \
  /opt/kafka/bin/kafka-dump-log.sh \
  --files \"\$f\" --print-data-log=false | head -80"
docker compose exec broker bash -lc \
  "f=\$(find /tmp/kraft-combined-logs/day13.storage-0 \
  -name '*.index' | sort | head -1); \
  /opt/kafka/bin/kafka-dump-log.sh \
  --files \"\$f\" | head -50"

확인할 것: BaseOffset·lastOffset·count·compression·size와 index의 relative offset/position. Record count가 batch count보다 큰지, index position이 증가하는지 말로 설명한다. CLI 출력 field는 version별로 조금 다를 수 있다.

Step 5 · 실패 주입: 과도한 flush의 비용

먼저 예측한다: flush.messages=1은 segment/batch 수를 직접 1:1로 만들까, 아니면 fsync 빈도를 바꿀까?

docker compose exec broker /opt/kafka/bin/kafka-configs.sh \
  --bootstrap-server localhost:9092 --entity-type topics \
  --entity-name day13.storage --alter \
  --add-config flush.messages=1
time docker compose exec broker bash -lc \
  "seq 1 500 | /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic day13.storage"
docker compose exec broker /opt/kafka/bin/kafka-configs.sh \
  --bootstrap-server localhost:9092 --entity-type topics \
  --entity-name day13.storage --alter \
  --delete-config flush.messages

예상: 강제 fsync 빈도가 증가해 latency/throughput 비용이 생길 수 있지만 segment roll·record batch와 같은 개념은 아니다. Laptop cache·background I/O 때문에 한 번의 wall time만으로 일반화하지 말고 반복 측정한다.

8. 놓치기 쉬운 함정

  • Topic offset은 file byte position이 아니다. Index가 둘 사이를 연결한다.
  • .index와 .timeindex는 목적이 다르다. 후자는 timestamp→offset 근처 탐색이다.
  • File size 합계에 replicas와 partition 수를 곱하지 않으면 cluster capacity를 과소평가한다.
  • Compression ratio가 좋아진 뒤 segment 수가 줄어도 record 유입량이 줄었다는 뜻은 아니다.
  • Retention은 active segment 일부 record만 잘라 삭제하지 않는다. Segment roll 정책이 삭제 정밀도에 영향을 준다.
  • Dump tool은 forensic 증거다. Production hot path 전체 파일을 반복 dump하면 I/O와 CPU를 만든다.

9. 대기업 기술 면접 질문 3개

Q1. Kafka가 offset으로 빠르게 찾는 내부 경로를 설계 수준으로 설명하세요.
좋은 답변: 요구 offset→base offset으로 segment 선택→relative offset sparse index binary search→floor position→record batch scan→page cache/cold disk 비용→index interval trade-off까지 말한다.
Q2. Segment를 1GiB에서 64MiB로 줄이자는 제안을 어떻게 검토합니까?
좋은 답변: Partition byte rate·retention 정밀도·file/FD/roll rate·recovery·compaction·cold read 수치를 가정하고 실험, rollback, tiered storage 대안을 방어한다.
Q3. Record count는 그대로인데 disk 증가율이 두 배가 됐습니다. 진단 순서는?
좋은 답변: Raw/compressed bytes→batch fill·codec/schema/payload entropy→replica/partition 변화→retention lag→filesystem 증거를 보고 안전한 설정 rollback과 data loss 없는 대응을 제시한다.

10. 복습과 정답

어제 Day 12 회상 3문제

  1. Bootstrap server는 왜 영구 proxy가 아닌가?
    정답: Metadata 획득용 seed이며 이후 client가 partition leader broker에 직접 연결한다.
  2. Correlation ID의 역할은?
    정답: Connection의 미완료 request와 response를 연결한다. Record 전역 ID나 중복 제거 기능은 아니다.
  3. Bootstrap은 되는데 produce가 실패하는 대표 원인은?
    정답: Metadata의 advertised.listeners endpoint가 client network에서 해석·접속 불가능한 경우다.

오늘 확인 3문제

  1. Offset lookup이 index 하나로 exact record를 바로 반환하지 않는 이유는?
    정답: Sparse index는 floor entry만 제공해 그 position부터 log batch를 scan해야 한다.
  2. Batch size와 segment size의 차이는?
    정답: 전자는 producer가 record를 묶는 memory/전송 단위 설정, 후자는 broker log file roll 기준이다.
  3. 왜 live index file을 직접 고치면 안 되는가?
    정답: Log의 offset·position 불변식을 깨고 corruption/recovery 위험을 만든다. Index는 broker가 log에서 재구성해야 한다.
