APACHE KAFKA 4.3 · WEEK 4 / DAY 28 · RECALL & TECHNICAL REVIEW

회상: 장애 시 durability/availability 표 작성

처음 보는 장애 조건을 3분 안에 판정하는 프레임 · 리뷰 70분 + 드릴 30분

한 줄 요약
Kafka 장애표는 “broker 몇 대가 죽었나”가 아니라 요구 보장 → 설정 → 현재 data state → control state → 성공 확정 시점 → 안전한 복구 순서로 작성한다. Durability는 성공 응답을 받은 record와 가정한 failure model에 대한 약속이고, availability는 지금 요청을 완료할 수 있는가라는 별도 질문이다.

1. 선수 용어 사전

Durability성공으로 확정한 data가 정의된 장애 뒤에도 보존되는 성질. “절대 안 잃음”이 아니라 ack 정책·replica·failure domain 가정에 묶인다.
Availability요청이 제한 시간 안에 성공 응답을 받을 수 있는 성질. Read·write·admin availability를 따로 본다.
RPO / RTORecovery Point Objective는 허용 data loss 시점, Recovery Time Objective는 허용 복구 시간. RF와 min ISR 선택의 입력이다.
RF / ISRRF는 배치된 replica 총수, ISR은 현재 충분히 따라온 동적 집합이다. RF=3·ISR=1은 가능하다.
LEO / HWLEO는 replica별 local append 끝, HW는 consumer에 공개 가능한 committed 경계. LEO 전진만으로 성공을 확정하지 않는다.
Leader epochPartition leader 세대 번호. Failover 때 증가하고 stale leader를 fencing하며 divergent tail 정리의 기준이 된다.
acks=all현재 ISR 전체가 batch를 복제할 때 producer 성공을 반환하는 조건. “과반만 받는다”와 다르다.
min ISRacks=all 쓰기를 허용할 최소 ISR 크기. Durability를 위해 write availability를 닫는 안전선이다.
Data quorum엄밀한 Raft quorum 명칭은 아니며 여기서는 partition record 복제에 참여하는 leader·ISR 관계를 뜻한다.
Controller quorumKRaft metadata log를 합의하는 controller voters. Leader·ISR·broker registration 변경을 commit한다.
ELREligible Leader Replicas. ISR 밖이지만 HW까지의 data 보유가 입증돼 clean election 후보가 될 수 있는 Kafka 4.x 상태다.
Unknown outcomeTimeout 뒤 server commit 여부를 client가 모르는 상태. 재시도·idempotence·business key 조정이 필요하다.

2. 왜 중요한가

대규모 장애에서는 같은 “2대 down”도 결과가 다르다. 죽은 node가 topic replica인지 controller인지, leader인지 follower인지, 장애 전 ISR이 몇 개였는지, 안전 후보가 남았는지에 따라 write·read·election 결과가 갈린다. 숫자만 세면 잘못된 복구 순서를 선택한다.

실무에서 표는 의사소통 도구다. Incident commander·application owner·platform engineer가 “읽기는 되지만 쓰기는 막혔다”, “기존 leader data path는 살아 있지만 새 election은 불가하다”, “timeout은 유실이 아니라 결과 불명”을 같은 언어로 공유하게 한다.

면접관은 암기보다 경계를 본다. 성공의 정의, 상태 소유자, 불변식, control/data path, failure window, 비용 trade-off를 순서대로 설명하면 처음 보는 수치에도 답할 수 있다.

3. Architecture: 3분 장애표 작성 알고리즘

1 · ContractRPO/RTO, ack 성공의 범위, read isolation
↓ 어떤 실패를 견뎌야 하는가?
2 · ConfigRF, min ISR, acks, unclean election, rack placement
↓ 고정 설정과 현재 상태를 분리
3 · Data stateLeader·epoch, Replicas, ISR/ELR, LEO/HW
↓ 누가 record와 authority를 보유하는가?
4 · Control stateActive controller, voter 과반, metadata HW·lag
↓ 상태 전이를 commit할 수 있는가?
5 · VerdictWrite / read / election / admin 각각 Yes·No·조건부
↓ 증거와 failure window를 붙인다
6 · ActionHealthy majority 보호 → 최신 replica 복구 → ISR catch-up → canary
  1. 계약: “성공 응답을 받은 event의 RPO=0, write RTO=5분”처럼 먼저 요구사항을 고정한다.
  2. 설정: RF와 min ISR, producer acks, election 정책, rack placement를 적는다. 기본값을 추측하지 않는다.
  3. Data state: Topic describe와 replica lag에서 leader·ISR·ELR·epoch·HW를 적는다. Process status만 보지 않는다.
  4. Control state: KRaft active controller와 voter majority를 확인한다. Partition data가 있어도 새 leader metadata를 commit하지 못할 수 있다.
  5. 판정: Write·read·election·admin을 한 칸에 “Kafka 됨/안 됨”으로 뭉치지 않는다.
  6. 복구: Data loss를 키울 수 있는 설정 변경보다 healthy majority와 최신 committed prefix를 먼저 보호한다.

중요: 마지막 행을 “무조건 가능”으로 답하면 안 된다. 기존 connection·leader·ISR이 안정적일 때 data path가 계속될 수 있다는 뜻이며, 추가 broker failure나 metadata refresh가 필요해지면 곧 막힌다. 상태 전이가 필요한지까지 적어야 한다.

불변식에서 답을 유도한다

  • Committed prefix: Clean leader는 acknowledged record의 committed prefix를 뒤로 돌리지 않아야 한다.
  • Single authority: Leader epoch와 controller epoch는 stale authority가 동시에 쓰지 못하게 fencing한다.
  • Write admission: acks=all은 현재 ISR 전체 복제, min ISR은 append 허용의 최소 안전선이다.
  • Recovery: Process restart가 아니라 follower catch-up·ISR 재가입·HW 보존이 완료 조건이다.
  • Scope: Kafka 내부 exactly-once나 idempotence를 외부 DB transaction으로 자동 확장하지 않는다.

Best practice: Topic별 “failure matrix”를 운영 전 ADR에 넣는다. 행은 실패 조합, 열은 leader·ISR·controller quorum·write/read/admin·RPO·첫 조치다. 실제 장애 때 채우기 시작하지 말고 배포 전 canary와 game day로 검증한다.

Evidence order: Client error·latency → topic describe → controller quorum → replica lag/ISR metric → broker disk/network/GC → config 변경 이력 순으로 수집한다. 로그 한 줄만 보고 결론을 내리지 않는다.

Anti-pattern: RF와 ISR을 같은 값으로 말하기, acks=all을 과반 ack로 설명하기, controller quorum loss를 전체 cluster 즉시 down으로 단정하기, timeout을 유실로 단정하기, 복구를 “재시작 성공”으로 끝내기.

Edge/version: Kafka 4.3.1 KRaft에서 ELR이 활성화되면 ISR 밖이라도 HW까지 안전성이 입증된 replica가 clean election 후보가 될 수 있다. ELR은 arbitrary unclean replica가 아니며 feature level·ELR field·min ISR을 함께 본다. Managed service는 동등한 provider metric과 SLA 경계를 명시한다.

7. 30분 실습: evidence-first 장애표 드릴

명령보다 먼저 3분 예측
RF=3, replicas={1,2,3}, leader=1, ISR={1,2,3}, min ISR=2, acks=all, controller voters=5라고 적는다. B3 follower stop 뒤 B1 leader stop 시 write·read·election·admin availability와 첫 복구 대상을 먼저 표로 작성한다.

사전 조건: Docker와 공식 Kafka 4.3.1 image. Day 27의 Step 1~2로 k27-b1~k27-b5와 day27.isr topic을 baseline 상태로 만든다. Topic replicas는 B1·B2·B3, controller voters는 B1~B5다.

Step 1 · 추측 전에 baseline 증거 고정

docker exec k27-b1 /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server k27-b1:19092 --describe --topic day27.isr docker exec k27-b1 /opt/kafka/bin/kafka-metadata-quorum.sh \ --bootstrap-server k27-b1:19092 describe --status

예상: Leader=1, Replicas=1,2,3, ISR=1,2,3과 controller CurrentLeader·HighWatermark가 보인다. 출력과 예측표의 시작 상태가 다르면 실습을 진행하지 말고 baseline부터 복구한다.

Step 2 · 실패 주입 A: follower B3 중단

docker stop k27-b3 sleep 8 docker exec k27-b1 /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server k27-b1:19092 --describe --topic day27.isr printf 'after-b3-down\n' | docker exec -i k27-b1 \ /opt/kafka/bin/kafka-console-producer.sh \ --bootstrap-server k27-b1:19092 --topic day27.isr \ --producer-property acks=all

예상: ISR={1,2}, write 성공. RF는 3 그대로이고 controller voter는 4/5로 과반이다. 장애표에 “available but degraded, failure margin 0 for write durability contract”라고 적는다.

Step 3 · 실패 주입 B: leader B1도 중단

docker stop k27-b1 sleep 8 docker exec k27-b2 /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server k27-b2:19092 --describe --topic day27.isr printf 'must-fail-under-min-isr\n' | docker exec -i k27-b2 \ /opt/kafka/bin/kafka-console-producer.sh \ --bootstrap-server k27-b2:19092 --topic day27.isr \ --producer-property acks=all \ --producer-property request.timeout.ms=5000 \ --producer-property delivery.timeout.ms=7000 docker exec k27-b2 /opt/kafka/bin/kafka-console-consumer.sh \ --bootstrap-server k27-b2:19092 --topic day27.isr \ --from-beginning --max-messages 1

예상: B2가 clean leader로 선출될 수 있지만 ISR={2}라 min ISR=2 미달이다. 새 write는 실패하고 이미 committed된 첫 record read는 가능하다. B2·B4·B5가 controller 과반 3/5를 유지하므로 leader/ISR metadata는 commit 가능하다. “leader 있음 = write 가능”이 아님을 출력으로 증명한다.

Step 4 · B3 복구와 종료 조건

docker start k27-b3 for i in 1 2 3 4 5 6; do docker exec k27-b2 /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server k27-b2:19092 --describe --topic day27.isr sleep 3 done printf 'write-after-isr-recovery\n' | docker exec -i k27-b2 \ /opt/kafka/bin/kafka-console-producer.sh \ --bootstrap-server k27-b2:19092 --topic day27.isr \ --producer-property acks=all

예상: B3가 missing offsets를 fetch한 뒤 ISR={2,3}으로 돌아오고 write가 성공한다. Process start 시점이 아니라 ISR expand와 canary 성공 시점을 RTO로 기록한다.

오류 해석과 cleanup

자주 나는 오류: B2가 아직 leader가 아니면 controller quorum과 election log를 먼저 확인한다. Consumer가 기대와 다른 record를 읽으면 이전 실습 data가 남은 것이므로 key/offset을 함께 출력해 구분한다. Producer timeout은 미기록을 뜻하지 않으므로 topic을 조회해 unknown outcome을 정리한다. ISR 복귀가 늦으면 replica LEO gap·disk·network를 확인한다.

docker rm -f k27-b1 k27-b2 k27-b3 k27-b4 k27-b5 docker volume rm k27-b1-data k27-b2-data k27-b3-data k27-b4-data k27-b5-data docker network rm k27-net

Cleanup은 k27- 전용 자원만 제거하며 저장소 기본 broker·volume은 건드리지 않는다.

8. 놓치기 쉬운 함정

  • “복제 3개니까 두 대 장애 허용”: Data 보존 가능성과 write availability는 다르다. min ISR=2라면 두 replica 상실 시 write는 닫힌다.
  • “acks=all은 과반”: 현재 ISR 전체를 기다린다. Min ISR이 과반처럼 보이는 값일 뿐 역할이 다르다.
  • “Leader가 있으니 정상”: ISR이 min ISR보다 작으면 read는 가능해도 write는 실패한다.
  • “Controller down은 즉시 data down”: 기존 state로 잠시 동작할 수 있지만 새 election·ISR mutation이 필요해지면 막힌다.
  • “Timeout은 유실”: Commit 후 response 유실일 수 있어 결과 불명으로 다룬다.
  • “Restart 성공은 복구 완료”: ISR 재가입·lag 0·HW 보존·canary를 확인한다.
  • “ELR은 unclean election”: ELR은 HW까지 data가 있음이 입증된 안전 후보이고 arbitrary replica와 다르다.
  • “모든 topic이 같은 정책”: Business RPO/RTO에 따라 RF·min ISR·retention·placement가 달라진다.

9. 대기업 기술 면접 질문 3개

Q1. RF=3·ISR=2·min ISR=2에서 leader가 죽으면 write와 read는 어떻게 됩니까?
좋은 답변 구조: 남은 ISR/ELR과 controller quorum 가정 → clean leader election·epoch 증가 → 남은 ISR 크기 계산 → 새 leader 하나만 남으면 read 조건부 가능·acks=all write 불가 → follower catch-up·ISR expand 후 write 재개 → 선출 공백과 client metadata refresh.

Q2. Controller quorum을 잃었지만 producer traffic이 정상입니다. 안전합니까?
좋은 답변 구조: 기존 partition leader·ISR로 data path가 잠시 가능 → metadata mutation·broker fencing·새 leader election은 불가 → 다음 failure에서 영향 확대 → mutation freeze·controller majority 우선 복구 → HW/lag·active controller 검증 → “정상”이 아니라 degraded control plane.

Q3. 장애 중 min ISR을 2에서 1로 낮추자는 제안을 검토하세요.
좋은 답변 구조: Business RPO/RTO와 손실 승인권자 → 현재 최신 copies·failure domain·backlog → single-copy ack 뒤 마지막 leader 상실의 failure window → traffic queueing·upstream backpressure·replica 복구 대안 → 변경 시 time-box·audit·rollback·post-condition.

10. 복습과 정답

어제 내용 회상 3문제

  1. RF=3·min ISR=2에서 follower 하나와 둘을 잃을 때 acks=all 결과는?
  2. 복귀한 broker가 process up이어도 복구 완료가 아닌 이유는?
  3. Day 27에서 5 combined nodes를 쓴 이유는?

짧은 정답: ① ISR 2까지 성공, ISR 1이면 fail closed. ② Missing log를 fetch해 ISR 재가입하기 전에는 안전 copy가 복원되지 않았다. ③ Topic replica 두 개를 내려 ISR 1을 만들면서도 B1·B4·B5 controller 과반 3/5를 유지해 data와 control failure를 분리하려고 했다.

오늘 확인 3문제

  1. 장애표 작성의 여섯 단계를 순서대로 말하라.
  2. Data leader healthy·controller 과반 상실에서 “조건부”라고 답해야 하는 이유는?
  3. Incident 종료를 승인할 최소 증거 다섯 가지는?
