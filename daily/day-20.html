처리 전/후 crash로
delivery semantics 관찰

Kafka checkpoint와 외부 side effect의 어긋남을 두 번의 실패 주입으로 증명하기 · 예상 35~40분

한 줄 요약
같은 record에서 commit → 처리 → crash 순서는 기본 재시작 경로의 누락을, 처리 → crash → commit 순서는 중복 처리를 만든다. 오늘은 Kafka log를 지우지 않고도 committed offset과 sink 증거를 나란히 기록해 이 차이를 재현한다.

1. 선수 용어 사전

Delivery semantics장애와 재시도까지 포함했을 때 record의 효과가 0회·1회·여러 번 나타날 수 있는지를 설명하는 계약이다. 단순 수신 횟수가 아니라 관찰 가능한 업무 효과의 범위를 먼저 정해야 한다.
Side effectDB 행 갱신, 결제 API 호출, 파일 append처럼 process 밖의 상태를 바꾸는 결과. 오늘은 텍스트 ledger 한 줄을 외부 sink의 축소 모형으로 쓴다.
Consumer position현재 process가 다음 poll에서 받을 partition offset. poll이 record를 반환하면 메모리에서 전진하지만, 아직 장애 복구 위치가 아닐 수 있다.
Committed offsetconsumer group이 재시작할 다음 offset으로 broker에 저장한 checkpoint. offset 0 처리를 끝냈다면 보통 1을 저장한다.
Crash window서로 다른 두 상태 변경 사이에서 process가 죽으면 결과가 달라지는 구간. sink 반영과 Kafka offset commit은 기본적으로 하나의 원자적 연산이 아니다.
Checkpoint작업 전체 결과가 아니라 “어디서 다시 시작할지”를 기록한 좌표. 책갈피를 옮겼다고 앞장을 이해했다는 보장은 없는 것과 같다.
Idempotency같은 business event를 여러 번 적용해도 최종 상태가 한 번 적용한 것과 같아지는 성질. unique key, upsert, inbox/dedup table로 구현할 수 있다.
Reset offsetsinactive group의 checkpoint를 관리 CLI로 옮기는 운영 기능. 오늘은 특정 commit 상태를 재현하는 실험 도구이며 application의 commit API 자체는 아니다.
Evidence가설을 판별하는 증거. topic/partition/offset, group checkpoint, sink의 event ID, crash 시각을 함께 묶어야 한다.

2. 왜 중요한가

운영에서 “Kafka 메시지가 사라졌다”는 신고가 들어와도 실제 Kafka log가 삭제된 것은 아닐 수 있다. group checkpoint가 처리보다 앞서 가면 기본 consume 경로에서 record를 건너뛰어 업무 결과만 빠진다. 반대로 처리 결과가 checkpoint보다 앞서면 같은 record가 다시 배달되어 중복 주문·중복 알림이 생길 수 있다.

실무자는 세 숫자를 구분해야 한다. log end offset은 broker log의 끝, committed offset은 group의 재시작 위치, sink completed offset은 업무 처리가 실제 확정된 지점이다. lag가 0이어도 세 번째 숫자가 뒤처질 수 있다. 면접에서도 설정 이름보다 이 상태들의 소유자와 실패 창을 설명해야 설계 역량이 드러난다.

Safe baseline처리 후 commit + 중복을 흡수하는 sink + replay 증거 보존
  1. Fetch path: consumer는 partition leader에서 record bytes를 받고 poll로 application에 넘긴다. position=1은 client memory 상태다.
  2. Commit path: OffsetCommitRequest는 group coordinator로 가며, 성공한 checkpoint는 __consumer_offsets에 저장된다.
  3. Sink path: DB/file/API는 Kafka coordinator와 독립된 상태 소유자다. 한쪽의 성공 response가 다른 쪽 성공을 증명하지 않는다.
  4. Crash: RAM의 position과 미전송 요청은 사라진다. 재시작 consumer는 broker의 committed offset을 기준으로 새 position을 잡는다.
  5. 복구: Kafka log가 retention 안에 남아 있으면 별도 replay group이나 검증된 offset reset으로 재처리할 수 있지만, 비멱등 side effect는 먼저 격리해야 한다.

분산 시스템 관점: dual write 문제

Kafka offset 저장과 외부 DB 갱신은 두 개의 독립 state machine이다. application이 순서를 정할 수는 있지만 일반 commit 두 번을 하나의 원자적 commit으로 만들 수는 없다. 첫 작업 뒤 두 번째 작업 전에 crash하는 구간이 언제나 생긴다. 이것이 dual write 문제다. 2-phase commit을 붙이면 조정자·blocking·복구 비용이 늘고, 모든 sink가 참여할 수도 없다.

그래서 흔한 실무 해법은 at-least-once + idempotent sink다. DB라면 event ID unique constraint와 같은 transaction 안에서 업무 갱신·inbox 기록을 확정한다. Kafka→Kafka라면 transactional producer와 input offsets를 같은 Kafka transaction에 포함하는 대안을 검토한다. 단, Kafka 내부 exactly-once가 외부 REST 결제까지 자동으로 보호하지는 않는다.

OS 관점: 출력 한 줄도 바로 내구적이지 않을 수 있다

파일 append나 DB client의 “성공”은 어느 계층까지 확정됐는지 따져야 한다. user-space buffer, kernel page cache, storage controller를 거쳐 실제 stable storage에 반영되는 시점이 다를 수 있다. 오늘 ledger는 의미를 관찰하기 위한 모형이므로 금융 내구성을 증명하지 않는다. production에서는 DB transaction commit, fsync 정책, replica quorum까지 성공 정의에 넣는다.

Network 관점: response 유실과 불확실한 결과

요청이 server에서 성공한 뒤 response packet만 유실되면 client는 timeout을 본다. “timeout=실패”로 단정하고 비멱등 요청을 재시도하면 중복 효과가 생긴다. event ID와 조회 가능한 operation ID가 필요한 이유다. commit request도 outcome이 불확실할 수 있으므로 현재 group generation과 안전한 completed frontier를 확인해 같은 또는 더 높은 offset을 재확정한다.

Best practice: event ID와 topic/partition/offset을 sink audit에 같이 남긴다. processed frontier ≤ committed frontier 같은 숫자 하나만 믿지 말고, 처리 후 commit 설계에서는 정상적으로 committed가 잠시 뒤처질 수 있음을 대시보드에 표현한다. 장애 훈련은 별도 topic/group/sink에서 자동화하고 결과 행 수·unique event 수·checkpoint를 동시에 assert한다.

Anti-pattern: lag 0을 처리 완료로 간주, Ctrl+C 한 번 결과만으로 보장 선언, active production group offset reset, sink 중복을 지우기 전에 증거 삭제, “manual commit”이라는 말만으로 exactly-once 주장.

Edge case: 한 poll batch를 병렬 처리하면 가장 큰 완료 offset이 아니라 partition별 연속 완료 frontier만 commit해야 한다. rebalance 뒤 옛 worker의 늦은 side effect도 fencing해야 한다. compacted topic·transaction marker 때문에 offset 숫자가 항상 record 개수와 같거나 연속이라고 가정하지 않는다.

Version/engine 차이: 이 랩은 Apache Kafka 4.3.1 CLI와 KRaft 단일 broker 기준이다. Spring Kafka ack mode, Kafka Connect offset, Flink checkpoint는 상위 runtime이 commit 시점과 재시작 state를 소유하므로 동일 CLI 실험을 그대로 의미 매핑하지 말고 해당 engine의 checkpoint barrier·transaction 계약을 확인한다.

7. 35~40분 통합 랩: 누락 window와 중복 window를 분리 관찰

실행 전 예측부터 적기
① checkpoint=1, sink에 order-0 없음이면 재시작 후 order-0이 보일까? ② checkpoint=0, sink에 order-0 한 줄이면 재시작 후 append 결과는 몇 줄일까? ③ Kafka log의 order-0은 두 경우 모두 남아 있을까?

사전 조건: 저장소 루트, Docker 실행 가능, 이 프로젝트의 공식 Apache Kafka 4.3.1 단일 broker KRaft 환경. 아래 명령은 day20.delivery와 day20-* 실습 group에만 실행한다.

Step 1 · 입력과 원본 증거 만들기

make up docker compose exec broker /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server localhost:9092 --create --if-not-exists \ --topic day20.delivery --partitions 1 --replication-factor 1 printf 'order-0\norder-1\norder-2\n' | docker compose exec -T broker \ /opt/kafka/bin/kafka-console-producer.sh \ --bootstrap-server localhost:9092 --topic day20.delivery

원본을 group 없이 읽어 offset을 확인한다.

docker compose exec broker /opt/kafka/bin/kafka-console-consumer.sh \ --bootstrap-server localhost:9092 --topic day20.delivery \ --partition 0 --offset earliest --max-messages 3 \ --property print.offset=true --property print.value=true

예상: Offset:0/order-0부터 Offset:2/order-2까지 보인다. 이 명령은 group checkpoint를 만들지 않는다.

Step 2 · 시나리오 A: commit 먼저, 처리 전 crash

실제 application에서 offset 0을 poll한 뒤 next offset 1을 먼저 commit한 상태를 CLI reset으로 모사한다. group이 inactive일 때만 실행한다.

docker compose exec broker /opt/kafka/bin/kafka-consumer-groups.sh \ --bootstrap-server localhost:9092 --group day20-before \ --topic day20.delivery:0 --reset-offsets --to-offset 1 --execute rm -f /tmp/day20-before-sink.log

실패 주입: sink append 명령을 실행하지 않는다. 이것이 commit 1 성공 직후, order-0 처리 전에 process가 죽은 상태다. 재시작을 모사해 같은 group으로 한 건만 읽는다.

docker compose exec broker /opt/kafka/bin/kafka-console-consumer.sh \ --bootstrap-server localhost:9092 --topic day20.delivery \ --group day20-before --max-messages 1 \ --property print.offset=true --property print.value=true

예상: 첫 출력은 offset 1/order-1이다. order-0은 Kafka log에 남지만 이 group의 기본 재시작 경로에서는 건너뛴다. 이것이 sink 관점의 at-most-once/loss window다.

Step 3 · 시나리오 B: 처리 먼저, commit 전 crash

새 group의 checkpoint를 0에 두고 order-0의 side effect를 먼저 기록한다.

docker compose exec broker /opt/kafka/bin/kafka-consumer-groups.sh \ --bootstrap-server localhost:9092 --group day20-after \ --topic day20.delivery:0 --reset-offsets --to-offset 0 --execute rm -f /tmp/day20-after-sink.log printf 'order-0\n' >> /tmp/day20-after-sink.log

실패 주입: checkpoint를 1로 전진시키지 않고 crash했다고 가정한다. 재시작 consumer에서 offset 0을 다시 확인한 뒤 동일 side effect를 한 번 더 모사한다.

docker compose exec broker /opt/kafka/bin/kafka-console-consumer.sh \ --bootstrap-server localhost:9092 --topic day20.delivery \ --group day20-after --max-messages 1 \ --property print.offset=true --property print.value=true printf 'order-0\n' >> /tmp/day20-after-sink.log nl -ba /tmp/day20-after-sink.log

예상: offset 0/order-0이 재배달되고 ledger에는 같은 event가 두 줄이다. 이것이 at-least-once의 duplicate window다. console consumer의 종료 commit 동작과 timing은 구현·종료 방식에 영향을 받을 수 있으므로, 핵심 증거는 실행 전 명시한 checkpoint와 sink 결과다.

Step 4 · 세 상태를 표로 대조

docker compose exec broker /opt/kafka/bin/kafka-consumer-groups.sh \ --bootstrap-server localhost:9092 --describe --group day20-before docker compose exec broker /opt/kafka/bin/kafka-consumer-groups.sh \ --bootstrap-server localhost:9092 --describe --group day20-after wc -l /tmp/day20-before-sink.log /tmp/day20-after-sink.log 2>/dev/null || true

자주 나는 오류와 해결: reset에서 “group active”가 나오면 해당 consumer를 완전히 종료하고 describe로 Empty를 확인한다. 처음 만든 group이 없어 reset이 실패하면 --to-earliest로 초기 checkpoint를 만든 뒤 다시 실행한다. TOPIC:PARTITION 문법은 day20.delivery:0처럼 쓴다. 실험 출력이 예상과 다르면 명령을 반복하기 전에 group committed offset과 consumer 종료 시각을 캡처한다.

8. 놓치기 쉬운 함정

  • “유실” 범위: 시나리오 A에서 record bytes가 Kafka log에서 삭제된 것이 아니라 해당 group의 기본 replay 경로가 건너뛴 것이다.
  • CLI reset의 역할: checkpoint 상태를 결정적으로 만드는 실험 도구다. application의 poll·commit 호출 순서를 대신 구현한 것은 아니다.
  • graceful shutdown ≠ crash: console consumer가 종료 중 commit할 수 있다. 강제 실패 실험은 상태를 전후에 측정해야 한다.
  • 한 partition으로 인과성 고정: 여러 partition을 섞으면 출력 순서와 checkpoint가 독립이어서 처음 관찰하기 어렵다.
  • append ledger는 비멱등: 중복을 눈에 보이게 만들기 위한 장치다. 실제 해법은 event ID unique/upsert 또는 transaction이다.
  • offset reset은 파괴적 운영 변경: production에서는 영향 record 수·sink idempotency·rollback point·승인을 먼저 확보한다.

9. 대기업 기술 면접 질문 3개

Q1. “Kafka 메시지가 유실됐다”는 신고를 어떻게 조사합니까?
좋은 답변 구조: 유실 범위를 broker log와 sink 누락으로 분리 → topic/partition/offset·retention·committed offset·sink audit 수집 → commit-first crash, deserialization/DLQ, retention 가설 → 원본 보존·별도 replay group → idempotent 보정 → 운영 group blind reset 금지.

Q2. 처리 후 commit이면 exactly-once입니까?
좋은 답변 구조: 요구하는 효과의 범위 정의 → sink 성공 후 commit 전 crash timeline → 재배달과 중복 → event ID unique/inbox로 수렴 → Kafka→Kafka transaction 대안 → 외부 API 결과 불확실성·비용·관측 설명.

Q3. 초당 10만 건, 1%가 2초 걸리는 consumer의 commit 설계를 해보세요.
좋은 답변 구조: partition 수·ordering·허용 duplicate/RPO 가정 → poll thread와 worker 분리, pause/backpressure → partition별 contiguous frontier → max.poll.interval.ms와 batch 수치 추정 → rebalance fencing → dedup TTL/용량·commit latency·복구 시간 trade-off.
