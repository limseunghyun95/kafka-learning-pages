한 줄 요약
bootstrap.servers는 모든 요청이 통과하는 proxy가 아니라 cluster를 발견하기 위한 seed다. Client는 DNS·TCP·선택적 TLS/SASL을 통과하고 ApiVersions로 호환 protocol을 고른 뒤 Metadata로 broker endpoint와 partition leader를 cache한다. 이후 Produce/Fetch는 담당 broker와의 persistent TCP connection으로 직접 보내며, response의 correlation ID와 error code를 보고 완료·갱신·재시도를 결정한다.

1. 선수 용어 사전

Wire protocol서로 다른 process가 network에서 주고받는 byte의 순서·형식·의미에 대한 약속. Kafka는 TCP 위에서 binary protocol을 쓴다.
FrameStream인 TCP에서 메시지 한 개의 경계를 표시한 byte 묶음. Kafka request/response는 앞의 길이 값으로 경계를 찾는다.
Big-endian여러 byte인 정수를 가장 큰 자릿값 byte부터 전송하는 순서. Network byte order라고도 한다.
API key / version요청 종류와 그 요청 schema의 세대. 예를 들어 Metadata는 API key 3이며 version에 따라 field 형식이 달라진다.
Correlation IDClient가 request에 넣고 broker가 response에 되돌려주는 32-bit 번호. 여러 미완료 요청 중 어느 응답인지 맞춘다.
Client IDBroker log·metric에서 호출 application을 식별하는 논리 이름. 인증 주체와는 다르다.
Bootstrap serverCluster 전체를 발견하기 위해 처음 접속하는 seed broker. 모든 broker를 적을 필요는 없지만 장애 domain이 다른 주소를 여러 개 둔다.
MetadataBroker node ID·host·port와 topic partition의 leader/replica 정보를 담은 client-side routing map.
advertised.listenersBroker가 client에게 “이 주소로 다시 접속하라”고 metadata에 광고하는 endpoint. 실제 listen 주소와 다를 수 있다.
TCP connection양 endpoint 사이의 신뢰성 있는 ordered byte stream. 연결 수립에는 SYN→SYN-ACK→ACK가 필요하다.
Persistent connectionRequest마다 새 연결을 만들지 않고 여러 request에 socket을 재사용해 handshake·TLS 비용을 분산하는 방식.
Non-blocking I/O한 socket이 준비될 때까지 thread를 묶어 두지 않고 selector/event loop가 여러 connection의 준비 상태를 처리하는 방식.
In-flight requestSocket에 보냈지만 아직 response로 완료되지 않은 요청. 많으면 throughput이 늘 수 있지만 memory·timeout·ordering 위험도 커진다.
Backoff / jitter실패 후 즉시 반복하지 않고 기다리는 시간과 그 시간에 넣는 무작위 흔들림. 동시 reconnect storm을 줄인다.
TLS / SASLTLS는 전송 암호화·인증, SASL은 application protocol 수준 인증 mechanism이다. SSL listener에서는 TLS handshake가 Kafka request보다 먼저다.

2. 왜 중요한가

Application에는 kafka-a:9092,kafka-b:9092 몇 개만 적었는데, 실제로는 수십 broker와 수천 partition에 정확히 routing된다. 이 마법의 실체가 metadata cache다. 이 지도를 이해하면 “bootstrap은 연결되는데 produce는 실패한다”, “leader election 뒤 30초 timeout이 난다”, “broker를 늘렸더니 DNS connection storm이 생긴다”를 서로 다른 장애로 분리할 수 있다.

또한 TCP 연결 성공은 Kafka 요청 성공이 아니다. DNS→TCP→TLS→SASL→API version negotiation→authorization→leader routing→broker processing→response까지 각기 다른 완료 지점과 timeout이 있다. 실무자는 어느 단계까지 성공했는지를 증거로 좁혀야 한다.

4. CS 내부 동작: framing·상태 소유권·성공 시점

API version별 schema

TCP의 한 번의 read()가 request 하나와 일치한다는 보장은 없다. Header 일부만 오거나 여러 request가 한 buffer에 함께 올 수 있다. Network thread는 먼저 4-byte length를 읽고 정확한 frame이 모일 때까지 상태를 유지한다. 길이·header·body의 integer는 big-endian이다. Flexible version에서는 compact type과 tagged fields가 쓰이므로 “모든 API header가 언제나 같은 byte 수”라고 가정하면 안 된다.

한 TCP connection에서의 ordering과 pipelining

Kafka 공식 protocol 문서는 한 connection에서 request와 response 순서가 보존된다고 설명한다. Client는 non-blocking I/O로 앞선 response를 기다리는 동안 다음 request bytes를 socket buffer에 넣을 수 있다. 이것이 pipelining이다. 다만 앞 요청 처리나 큰 response가 늦으면 뒤 요청도 기다리는 head-of-line 효과가 생길 수 있고, max.in.flight.requests.per.connection이 memory·throughput·retry ordering의 경계를 만든다.

성공이 확정되는 시점은 계층마다 다르다

DNS 성공Hostname이 IP로 해석됨. 해당 IP의 Kafka가 정상이라는 뜻은 아니다.
TCP connect 성공양쪽 kernel이 connection 상태를 가짐. TLS·인증·Kafka API는 아직일 수 있다.
Request write 성공보통 local socket buffer에 수용됨. Broker가 frame을 읽었다는 보장은 없다.
Response 수신Correlation ID·API schema를 해석하고 partition별 error code와 ack 조건을 확인해야 application 성공이다.

Best practice · anti-pattern · edge case

  • Best practice: client.id에 service·environment·instance 역할을 식별할 수 있는 안정된 이름을 넣고 broker/client metric을 함께 본다. 인증용 secret은 넣지 않는다.
  • Best practice: Load balancer를 bootstrap에 쓰더라도 metadata가 반환한 각 broker 주소로 client가 직접 갈 수 있는지 검증한다. L4 LB 하나가 data path의 영구 proxy라고 가정하지 않는다.
  • Anti-pattern: localhost가 laptop·container·Kubernetes Pod·broker에서 같은 host를 뜻한다고 생각한다. Network namespace가 다르면 완전히 다른 endpoint다.
  • Anti-pattern: 모든 Disconnected log를 장애로 paging한다. Idle connection 정리나 정상 broker rolling restart도 원인일 수 있으므로 request 실패율·복구 시간과 묶는다.
  • Edge case: DNS가 여러 IP를 반환하면 client·JVM·OS cache 정책과 IP 순회가 failover 시간을 바꾼다. 짧은 DNS TTL만 설정한다고 JVM cache가 즉시 사라지는 것은 아니다.
  • Edge case: NAT·firewall idle timeout이 client/broker의 connections.max.idle.ms보다 짧으면 양 endpoint가 다른 connection 상태를 믿는 half-open window가 생긴다.
  • Version 차이: ApiVersions가 반환한 범위에서 client와 broker가 함께 지원하는 최고 version을 쓴다. 최신 client라는 이유만으로 최신 schema를 강제하지 않는다.

7. 35분 실습: ApiVersions·metadata·TCP 상태 관찰

사전 조건: 저장소 root, Docker Desktop, 공식 apache/kafka:4.3.1 image. 이 실습은 single-broker KRaft라 replication 장애를 검증하지 않는다.
목표: 같은 bootstrap-server를 사용해도 ApiVersions·Metadata·Produce/Fetch가 서로 다른 protocol request임을 관찰한다.

실행 전에 결과 예측

  1. kafka-broker-api-versions 출력에는 topic record가 아니라 API별 version 범위가 나오는가?
  2. Topic describe 결과에서 partition 0~2의 leader는 single broker의 같은 node ID인가?
  3. 9092 대신 닫힌 19092를 주면 Kafka error response를 받을까, TCP connection 단계에서 막힐까?

Step 1 · Cluster와 topic 준비

make up
make topic-create TOPIC=day12.protocol
make topic-describe TOPIC=day12.protocol

예상: 3개 partition과 leader/replica/ISR node ID가 보인다. 이는 application이 정적으로 갖고 있던 정보가 아니라 metadata request로 받은 routing 정보다.

Step 2 · Protocol version negotiation 관찰

docker compose exec broker \
  /opt/kafka/bin/kafka-broker-api-versions.sh \
  --bootstrap-server localhost:9092

예상: Broker node와 Produce·Fetch·Metadata·ApiVersions 등 API별 지원 version 범위가 길게 출력된다. 이것은 “Kafka 4.3” 한 숫자로 모든 request schema를 정하는 게 아니라 API마다 공통 지원 범위를 고른다는 증거다.

Step 3 · Persistent connection과 kernel 상태

Terminal A에서 consumer를 열어 둔다.

make consume TOPIC=day12.protocol GROUP=day12-observer

Terminal B에서 Linux TCP table을 본다. 9092의 16진수 port는 2384, state 01은 ESTABLISHED, 0A는 LISTEN이다.

docker compose exec broker bash -lc \
  "awk 'NR>1 && ($2 ~ /:2384$/ || $3 ~ /:2384$/) \
  {print $2, $3, $4}' /proc/net/tcp"

예상: Listener 외에 consumer와 broker 사이 ESTABLISHED entry가 보인다. Poll할 record가 없어도 connection은 재사용을 위해 남을 수 있다.

Step 4 · 실패 주입: 닫힌 bootstrap port

먼저 예측한다: DNS는 성공하지만 TCP RST/refused가 나면 ApiVersionsRequest가 broker에 도착할 수 있는가?

docker compose exec broker bash -lc \
  "timeout 12s /opt/kafka/bin/kafka-broker-api-versions.sh \
  --bootstrap-server localhost:19092"

예상: Connection 실패·bootstrap broker unavailable 경고 뒤 timeout된다. 이 경우 Kafka error code가 아니라 TCP 연결 전 단계 실패다. timeout command가 없다면 실행 후 경고 한두 번을 확인하고 Ctrl+C로 종료한다.

자주 나는 오류와 해결

Connection to node -1 failed-1은 bootstrap 전 임시 node 표기일 수 있다. Broker health·port·DNS부터 본다.
Bootstrap 뒤 실제 node만 실패Metadata에 담긴 advertised.listeners가 client namespace에서 접근 가능한지 확인한다.
UnsupportedVersionExceptionClient/broker 공통 API version이 없는지 확인하고 지원 조합으로 client를 맞춘다.
TCP entry가 안 보임Terminal A consumer가 종료되지 않았는지 확인한다. /proc/net/tcp6도 확인한다.
Port는 열렸지만 SSL errorPLAINTEXT/SSL listener 선택, truststore, hostname verification을 분리해 확인한다.

Cleanup

Terminal A를 Ctrl+C로 끝낸 뒤, 학습 cluster를 계속 쓸 거면 topic만 삭제한다. 전체 종료는 named volume을 지우지 않는 make down을 쓴다.

docker compose exec broker \
  /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --delete --topic day12.protocol
make down

8. 놓치기 쉬운 함정

  • Bootstrap server가 leader를 대신하지 않는다. Metadata를 받은 뒤 Produce/Fetch는 담당 broker로 직접 간다.
  • Metadata 성공과 data request 성공 사이에는 시간차가 있다. 그 사이 election이 일어나면 cache는 즉시 stale해질 수 있다.
  • Correlation ID는 global message ID가 아니다. Connection의 미완료 request와 response를 맞추는 client-local 값이다.
  • TCP ordered delivery가 application exactly-once를 만들지 않는다. Timeout 뒤 broker 처리 여부를 모르는 ambiguous window와 retry 중복은 별도 문제다.
  • KRaft controller는 일반 client bootstrap endpoint가 아니다. Controller quorum과 broker listener를 섞으면 control/data plane 경계가 깨진다.
  • Socket buffer가 넉넉하면 장애가 늦게 보일 수 있다. Local write 성공 뒤 remote가 처리하지 못해 request age가 증가할 수 있다.

9. 대기업 기술 면접 질문 3개

Q1. Producer에 bootstrap broker 두 개만 줬는데 100개 broker로 어떻게 정확히 routing합니까?
좋은 답변 구조: 요구사항(동적 leader) → bootstrap은 seed → DNS/TCP/ApiVersions/Metadata sequence → partition→leader cache → broker별 connection → stale metadata error와 refresh → seed failure·advertised listener trade-off까지 설명한다.
Q2. “Port 9092 TCP connect는 되는데 produce timeout”을 어떻게 진단합니까?
좋은 답변 구조: TCP 성공의 범위를 제한 → TLS/SASL·ApiVersions·Metadata·authorization·leader·broker queue 계층화 → client error/correlation age와 broker request queue·throttle·controller event 증거 → 안전한 traffic 제한 → listener/timeout 무작정 변경을 피한다.
Q3. 5,000개 producer가 broker rolling restart 때 동시에 재접속합니다. 무엇을 설계합니까?
좋은 답변 구조: Connection rate·FD·accept backlog·TLS CPU 수치 가정 → persistent connection과 exponential backoff+jitter → bootstrap failure domain·DNS cache → retry/delivery deadline → rolling batch size·readiness → dashboard와 rollback 기준을 방어한다.

    정답: 여러 record의 반복 패턴과 header 고정비를 함께 줄여 압축률과 request/syscall amortization이 좋아진다.
  2. Broker가 compressed batch를 저장해도 CPU가 0이 아닌 이유는?
    정답: Record count·CRC·offset/sequence 같은 불변식 검증을 위해 payload를 해제할 수 있고 codec 강제 변환 시 재압축한다.
  3. Zero-copy가 깨지는 대표 경계 두 가지는?
    정답: User-space TLS 암호화와 message/codec 변환. Consumer의 decompression·deserialization도 별도 CPU 작업이다.

오늘 내용 확인 3문제

  1. Bootstrap server와 advertised listener의 역할 차이는?
    정답: Bootstrap은 최초 metadata 획득용 seed이고, advertised listener는 metadata가 알려주는 각 broker의 후속 접속 주소다.
  2. Correlation ID가 보장하는 것과 보장하지 않는 것은?
    정답: Request-response 대응은 보장하지만 record의 전역 identity·중복 제거·exactly-once는 보장하지 않는다.
  3. Leader가 바뀐 직후 client의 state transition을 설명하라.
    정답: 이전 leader로 request → leader/socket error → metadata update 요청 → 새 leader endpoint cache → 새/기존 connection으로 deadline 안에서 retry한다.

채점: 각 답에 “상태 소유자 + wire 단계 + 성공 시점 + 실패 창 + 안전한 대응” 중 4개 이상이 들어가면 면접 방어 수준이다. Component 이름만 나열하면 절반 점수다.
