APACHE KAFKA 4.3 · WEEK 4 / DAY 25 · REPLICATION

leader election과 unclean election 위험

안전 후보·epoch·ELR·유실 구간으로 failover를 설명하기 · 이론 75분 + 실습 30분

한 줄 요약
Leader election은 단순히 살아 있는 replica 하나를 고르는 일이 아니다. 확정된 log prefix를 가진 후보를 새 leader로 선택하고 epoch를 올려 과거 leader를 fencing하는 상태 전이다. 안전 후보가 없을 때 non-ISR replica를 고르는 unclean election은 RTO를 줄이는 대신 그 replica가 가지지 못한 record를 영구 포기하는 명시적 RPO 결정이다.

1. 선수 용어 사전

Leader한 partition의 현재 쓰기·읽기 기준 replica. Producer와 consumer는 controller가 아니라 partition leader의 broker와 data path를 만든다.
Election후보 중 하나를 새 권한자로 확정하는 선출. Kafka에서는 KRaft active controller가 partition metadata 상태 전이를 결정한다.
ISRIn-Sync Replicas. 현재 leader의 committed history를 충분히 따라온 동적 집합. 일반적인 clean election의 첫 후보군이다.
ELREligible Leader Replicas. Kafka 4.x의 strict min ISR 규칙 덕분에 일부 non-ISR replica도 안전 후보가 될 수 있어 controller가 별도로 추적하는 집합이다. 임의의 stale replica와 같지 않다.
Leader epochPartition leader 세대를 나타내는 단조 증가 번호. 새 선출 때 증가하며 과거 세대의 요청·log tail을 식별하고 fencing하는 논리 시계다.
Fencing오래된 권한자가 계속 쓰는 것을 막는 조치. Network partition으로 old leader가 살아 있어도 낮은 epoch의 권한을 거부해 split-brain write를 막는다.
LEO / HWLog End Offset은 replica별 다음 append 위치, High Watermark는 안전하게 공개할 수 있는 next-offset 경계다. LEO가 크다는 사실만으로 안전 후보는 아니다.
Clean electionCommitted prefix를 보존하는 후보를 선택하는 선출. Kafka 4.x에서는 ISR 우선, feature 조건을 만족하면 ELR도 안전 후보가 될 수 있다.
Unclean election안전 후보가 없을 때 ISR 밖의 뒤처진 replica를 last resort leader로 선택하는 선출. 빠른 복구와 data loss를 맞바꾼다.
RPO / RTORecovery Point Objective는 허용 가능한 유실 시점, Recovery Time Objective는 허용 가능한 복구 시간. Unclean election은 RTO를 줄이기 위해 RPO를 악화시키는 결정이다.

2. 왜 중요한가

Leader 장애 자체는 흔하다. 문제는 새 leader가 무엇을 알고 있느냐다. RF=3 partition에서 B1·B2가 offset 119까지 가졌지만 B3가 111까지만 가졌다고 하자. B1·B2가 동시에 사라진 뒤 B3를 leader로 세우면 service는 빨리 살아나지만 B3에 없는 offsets 112~119는 새 history에 존재하지 않는다. 나중에 B1이 돌아와도 더 긴 tail을 합치는 것이 아니라 현재 leader history에 맞춰 divergent tail을 버려야 한다.

그래서 “replica가 하나 살아 있으니 복구 가능”과 “성공 응답을 받은 record가 보존된다”는 다른 주장이다. 전자는 availability, 후자는 durability다. 면접과 장애 대응에서는 후보의 LEO만 보지 말고 ISR·ELR·HW·leader epoch·failure domain을 함께 설명해야 한다.

Kafka 4.3에서 unclean.leader.election.enable의 기본값은 false다. 이것은 안전 후보가 없으면 partition을 offline 상태로 남겨 data loss보다 가용성 중단을 선택한다는 뜻이다. 이를 켜는 행위는 단순한 설정 변경이 아니라 “얼마나 잃을 수 있는지, 어디서 재생할지, 누가 승인했는지”가 필요한 사고 대응 결정이다.

3. Architecture: leader 실패에서 새 epoch까지

1 · DetectB1 heartbeat/session 실패 → controller가 broker를 fenced로 판단
↓ CONTROL PATH · broker registration / partition state
2 · InspectP0: leader=B1, epoch=7, ISR=[B1,B2], ELR·fence 상태 확인
↓ SAFE CANDIDATE · ISR → unfenced ELR → unfenced last-known leader
3 · ElectB2를 leader로 선택, leader epoch 7→8
↓ COMMIT · PartitionRecord를 KRaft metadata log에 확정
4 · ApplyBroker가 metadata 적용, B2가 epoch 8 leader 역할 수락
↓ DATA PATH RESUME · client metadata refresh
5 · ServeProducer·consumer → B2, 복귀한 B1은 epoch 8 history로 수렴
  1. Failure detection: Controller는 broker heartbeat와 registration epoch를 바탕으로 B1이 더는 현재 권한을 행사할 수 없다고 판단한다. Packet 하나가 늦었다고 즉시 죽은 것으로 단정하지 않으므로 detection timeout 동안 client latency와 retry가 발생한다.
  2. State lookup: Controller는 data record를 읽어 후보를 고르는 것이 아니라 KRaft metadata의 leader·ISR·ELR·fence 상태를 사용한다. Record bytes는 broker log에 남고 control path와 data path는 분리된다.
  3. Candidate order: Kafka 4.3 공식 ELR 문서의 순서는 ISR이 비어 있지 않으면 ISR, 다음은 unfenced ELR, 다음은 unfenced last-known leader다. ELR은 strict min ISR 때문에 committed prefix가 안전하다고 추론 가능한 후보이지 아무 non-ISR replica가 아니다.
  4. Authority commit: 새 leader와 증가한 epoch가 metadata log에 확정된다. 이 시점이 cluster의 새 권한 근거이며 broker들은 이를 적용해 stale leader를 fencing한다.
  5. Client recovery: Client가 stale metadata로 B1에 보내면 leader 관련 오류를 받고 metadata를 갱신해 B2로 재시도한다. 새 leader 선출 완료와 모든 client 정상화는 같은 시점이 아니다.

왜 더 긴 old leader log를 합치지 않는가

두 replica의 log tail이 갈라진 뒤 record를 합치면 동일 offset에 서로 다른 record가 생기고 partition ordering이 깨진다. Kafka는 새 epoch의 leader history를 단일 진실로 정한다. 복귀 replica는 leader epoch cache와 end offset을 비교해 공통 prefix 뒤의 divergent tail을 truncate하고 follower fetch로 다시 채운다. 이 규칙이 deterministic convergence를 주지만, unclean election에서 버린 tail을 자동 복구해 주지는 않는다.

ELR은 unclean election의 다른 이름이 아니다

Kafka 4.0부터 ELR이 제공되고 새 Kafka 4.1+ cluster에서는 기본 활성화된다. Strict min ISR에서는 ISR 크기가 min ISR보다 작으면 HW가 전진하지 않는다. 따라서 ISR에서 빠졌더라도 특정 시점의 committed prefix를 잃지 않은 replica를 controller가 ELR로 추적할 수 있다. 공식 4.3 선출 순서는 ISR → unfenced ELR → unfenced last-known leader다. ELR 후보는 안전성 근거가 있지만, 임의의 stale non-ISR 후보를 허용하는 unclean election은 data loss를 감수한다.

Feature level, upgrade 이력, cluster/topic min ISR 변경으로 ELR 상태가 달라질 수 있다. 특히 min ISR 변경은 ELR state 정리에 영향을 주므로 사고 중 “설정 하나만 낮추기”가 후보 상태까지 바꿀 수 있음을 고려한다.

성공 시점·failure window·비용

Election 성공은 controller가 새 leader·epoch metadata를 합의하고 broker가 이를 적용해 새 leader 역할을 수락할 수 있을 때다. Service 복구는 client metadata refresh와 retry까지 끝난 뒤다. 이 둘 사이에는 stale leader error, request timeout, producer unknown outcome, consumer fetch 재연결이 존재한다.

Failure detector timeout을 짧게 하면 RTO는 줄지만 일시 network jitter를 broker 장애로 오판해 election churn을 늘릴 수 있다. 길게 하면 false positive는 줄지만 offline partition 시간이 늘어난다. Election 자체보다 disk stall, controller event queue, metadata propagation, client DNS·connection 재수립이 tail latency를 좌우할 수 있다.

선행 증거: Topic describe의 leader·replicas·ISR·ELR, replica별 LEO/HW와 leader epoch, 마지막 성공 produce offset·timestamp, controller/broker log, broker fence 상태, rack/AZ, upstream source offset을 보존한다. 설정 변경 전에 loss lower/upper bound를 문서화한다.

Anti-pattern: Offline partition 수를 빨리 0으로 만들려고 cluster-wide unclean을 켜기, min ISR 하향과 unclean enable을 동시에 수행하기, 모든 broker를 함께 재시작하기, stale replica log를 삭제하기, RF=3이면 세 copy가 모두 최신이라고 가정하기, KRaft controller leader와 data partition leader를 혼동하기.

Edge case: Controller quorum은 건강하지만 특정 partition만 leader가 없을 수 있다. 반대로 controller quorum 장애는 새 election을 막아도 이미 알려진 data leader가 잠시 요청을 처리할 수 있다. Rack label 누락, 같은 AZ의 replica 집중, remote tier에 segment가 있다는 사실, compacted topic의 key history, transaction marker는 leader eligibility를 대신하지 않는다.

Version/engine: 이 자료는 Kafka 4.3 KRaft 기준이다. 새 Kafka 4.1+ cluster의 ELR 기본 활성화와 upgrade cluster의 feature level은 다를 수 있다. KRaft에서 unclean 설정을 동적으로 켜면 periodic unclean election thread까지 기본 5분을 기다릴 수 있어, 즉시 필요하면 공식 CLI의 unclean election을 별도로 실행한다. ZooKeeper 방식은 legacy 비교에만 둔다.

7. 30분 실습: leader가 없을 때 후보의 의미

실행 전 예측
RF=1 partition의 유일한 broker를 멈추면 다른 leader가 선출될까? Preferred election은 data loss를 만들까? unclean=false override는 단일 broker 복구 동작을 어떻게 바꿀까?

사전 조건: 저장소 루트, Docker, 공식 Kafka 4.3.1 단일 broker KRaft. 단일 broker에서는 clean/unclean 다중 replica 비교를 재현할 수 없다. 오늘은 “후보가 없으면 election도 없다”와 config·leader 상태를 관찰하고, Week 4 통합 랩에서 3-broker failure injection으로 확장한다.

Step 1 · Topic과 안전 정책 고정

make up docker compose exec broker /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server localhost:9092 --create --if-not-exists \ --topic day25.election --partitions 1 --replication-factor 1 \ --config unclean.leader.election.enable=false docker compose exec broker /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server localhost:9092 --describe --topic day25.election docker compose exec broker /opt/kafka/bin/kafka-configs.sh \ --bootstrap-server localhost:9092 --entity-type topics \ --entity-name day25.election --describe

예상: Leader·Replicas·Isr가 모두 broker 1을 가리키고 topic override가 false다. RF=1이므로 안전한 대체 후보는 0개다.

Step 2 · Preferred election은 안전한 재배치 요청

docker compose exec broker /opt/kafka/bin/kafka-leader-election.sh \ --bootstrap-server localhost:9092 --election-type preferred \ --topic day25.election --partition 0

예상: 이미 preferred replica가 leader이므로 실질 변경이 없거나 election이 성공했다는 결과가 나온다. 이 명령은 stale non-ISR를 강제로 고르는 unclean 명령이 아니다.

Step 3 · 실패 주입: 유일한 후보 중단

docker compose stop broker docker compose ps

예상: 대체 replica도, controller·broker process도 없으므로 partition은 서비스를 제공하지 못한다. Unclean election은 없는 replica를 만들어 내지 않는다. RF와 failure domain이 먼저다.

Step 4 · 같은 log를 가진 broker 복구

docker compose start broker make status docker compose exec broker /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server localhost:9092 --describe --topic day25.election

예상: 기존 local log와 metadata를 가진 broker가 healthy가 되면 leader·ISR가 다시 보인다. 이것은 stale non-ISR 승격이 아니라 같은 replica 복구다.

Step 5 · 종이 failure injection으로 손실 계산

B1/B2 LEO=120, B3 LEO=112, 이전 leader epoch=7을 적는다. B1만 죽으면 B2 clean leader epoch=8, B1·B2가 모두 죽고 B3가 unclean leader가 되면 epoch=9다. 실행 전에 “보존 마지막 offset=111, 잠재 손실=112~119, 8 records”를 계산한다. 이 계산을 실제 incident의 replica LEO/HW와 대조하는 것이 실습 목표다.

자주 나는 오류와 해결: Startup 직후 connection refused는 make status가 healthy일 때까지 기다린다. Preferred election 결과가 “no election needed”여도 정상이다. Topic이 남아 있으면 config describe로 override를 확인한다. 단일 broker 결과를 RF=3의 clean/unclean 실험으로 과장하지 않는다.

Cleanup:

docker compose exec broker /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server localhost:9092 --delete --topic day25.election make down

8. 놓치기 쉬운 함정

  • LEO가 가장 큼 ≠ 안전 후보: Divergent uncommitted tail일 수 있다. ISR·ELR·HW·epoch가 근거다.
  • ELR ≠ arbitrary non-ISR: Strict min ISR가 준 안전성으로 controller가 추적한 후보다.
  • Election 완료 ≠ client 정상화: Metadata refresh·TCP 재연결·retry가 남는다.
  • Unclean election ≠ 복구: 가용성을 위해 history 일부를 포기하는 새 기준점 생성이다.
  • Old leader의 긴 tail ≠ 복원 원본: 새 epoch와 충돌하면 truncate 대상이다. 별도 source-of-truth로 대사한다.
  • RF3 ≠ AZ3: Rack-aware 배치와 실제 장애 domain을 확인한다.
  • Controller leader ≠ partition leader: 전자는 metadata control path, 후자는 record data path를 담당한다.
  • Dynamic enable ≠ 즉시 election: KRaft periodic thread 지연이 있어 즉시 실행은 별도 CLI와 승인 절차가 필요하다.

좋은 답변 구조: failure domain·heartbeat 가정 → controller의 leader/ISR/ELR/fence 조회 → ISR 우선 후보 선택 → PartitionRecord·epoch 증가 합의 → broker 적용·old leader fencing → client metadata refresh → RTO와 controller/network/disk 지표 → 후보가 없을 때 안전 중단.

Q2. Unclean election을 켜 달라는 장애 요청을 받으면 어떻게 판단합니까?
좋은 답변 구조: Business RPO/RTO·topic 중요도 확인 → ISR/ELR·replica별 LEO/HW/epoch와 source-of-truth 수집 → 잠재 손실 offset·시간 계산 → 안전 replica 복구 대안 → topic 단위 승인·blast radius → unclean 후 write 제한 → 대사·idempotent replay·rollback 계획.

Q3. Kafka 4.x ELR은 왜 non-ISR인데도 clean 후보가 될 수 있나요?
좋은 답변 구조: ISR·min ISR·HW 정의 → strict min ISR에서 ISR 미달 시 HW가 전진하지 않는 불변식 → controller의 ELR 추적 → ISR→ELR→last-known leader 순서 → arbitrary stale replica와 구분 → feature level·min ISR 변경 edge case → ELR metric과 운영 검증.

10. 복습과 정답

어제 내용 회상 3문제

  1. ISR=3, min ISR=2에서 acks=all은 몇 replica를 기다리는가?
  2. NotEnoughReplicas와 NotEnoughReplicasAfterAppend의 failure window 차이는?
  3. RF=3·min ISR=2가 서로 다른 AZ의 두 copy를 보장하지 않는 이유는?

짧은 정답: ① 현재 ISR 전체 3개이며 min ISR은 admission floor다. ② 전자는 append 전 거부, 후자는 local append 뒤 안전 조건 미달이라 결과가 불명확할 수 있다. ③ Min ISR은 개수만 세고 rack/AZ placement는 별도 rack-aware assignment가 담당한다.

오늘 확인 3문제

  1. Clean election에서 leader epoch는 왜 증가해야 하는가?
  2. B1/B2 LEO=120, B3 LEO=112에서 B3 unclean 선출 시 잠재 손실 offset은?
  3. ELR과 unclean non-ISR replica의 가장 중요한 차이는?

채점 기준: ① 새 authority 순서를 확정하고 stale leader/request를 fencing하며 divergent log를 수렴시킨다고 설명(3점). ② B3는 0~111을 보유하므로 112~119, 최대 8 records라고 next-offset까지 계산(3점). ③ ELR은 strict min ISR 근거로 controller가 추적한 안전 후보이고 unclean 후보는 committed prefix 보장이 없어 data loss가 가능하다고 구분(4점). 총 8점 이상 통과.
