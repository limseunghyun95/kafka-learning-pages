RF=3·min ISR=2를 실제 장애 상태 전이로 검증 · 이론 45분 + 실습 40분

한 줄 요약
Replication factor는 배치 계획이고 ISR은 지금 안전하게 따라온 replica 집합이다. RF=3·min.insync.replicas=2·acks=all에서는 ISR 3→2까지 쓰기가 가능하지만 ISR 2→1에서는 내구성을 지키기 위해 쓰기를 거부하며, clean leader failover는 살아 있는 안전 후보가 committed prefix를 보존할 때만 가능하다.

1. 선수 용어 사전

Replica같은 partition log를 보관하는 복제본. Leader 하나와 follower 여러 개가 같은 offset 순서를 유지한다.
RFReplication factor. Partition에 배치할 replica 총수다. RF=3은 replica가 세 개라는 설정이며 현재 건강한 수를 뜻하지 않는다.
ISRIn-Sync Replicas. Leader를 포함해 충분히 따라와 안전 후보로 인정된 동적 집합이다. Broker 중단·지연으로 줄고 catch-up 뒤 늘어난다.
Leader / followerClient read/write를 받는 replica가 leader, leader에게 Fetch 요청을 보내 log를 복제하는 replica가 follower다.
LEOLog End Offset. 각 replica가 다음에 append할 위치다. Replica별로 달라질 수 있다.
HWHigh Watermark. Consumer에 안전하게 공개할 committed 경계다. Local append로 LEO가 먼저 늘어도 HW 전진 전에는 성공·가시성이 확정되지 않을 수 있다.
Leader epochLeader 세대를 나타내는 번호. 새 leader가 선출되면 증가하며 stale leader를 차단하고 log divergence를 복구하는 기준이 된다.
acks=allProducer 성공 조건. Leader가 현재 ISR 전체의 복제를 기다린다. 고정된 “2개 ack”가 아니라 그 시점의 ISR을 기준으로 한다.
min ISRacks=all 쓰기를 허용할 최소 ISR 크기. ISR이 작으면 NotEnoughReplicas 계열 오류로 admission을 막는다.
Clean electionISR 또는 안전성이 입증된 후보에서 새 leader를 고르는 선출. Committed prefix 보존을 우선한다.
Failure domain같이 실패할 수 있는 범위. Process·host·rack·AZ·network segment를 구분해야 replica 세 개가 실제 독립 장애를 견딘다.
Unknown outcomeClient timeout만으로 server commit 여부를 알 수 없는 상태. “실패”가 아니라 “결과를 모름”이며 idempotence·결과 조회가 필요하다.

2. 왜 중요한가

운영 장애에서 “broker 하나가 죽었다”는 설명만으로는 쓰기 결과를 예측할 수 없다. 죽은 broker가 어느 partition의 leader인지, ISR에 몇 개가 남았는지, producer의 acks와 min ISR, controller quorum이 metadata 변경을 commit할 수 있는지를 함께 봐야 한다.

대표적 출발점인 RF=3·min ISR=2·acks=all은 한 replica 장애 동안 쓰기를 계속하고, 두 번째 장애에서는 availability를 포기해 acknowledged data를 한 replica에만 의존하지 않게 한다. 이것은 CAP 구호가 아니라 어느 실패 창에서 write admission을 닫을지 정한 운영 계약이다.

면접에서 좋은 답변은 “복제 3개라 안전합니다”가 아니다. 상태 전이마다 leader·replicas·ISR·HW·controller quorum·producer 결과를 표로 적고, client timeout의 unknown outcome과 복구 후 catch-up 조건까지 방어한다.

3. Architecture: 한 장애가 쓰기 결과가 되기까지

1 · Producerbatch + acks=all → partition leader B1
↓ DATA PATH · B1 local append, LEO advances
2 · ReplicasB2·B3 follower Fetch → append → fetch progress
↓ B3 STOPS · lag timer expires
3 · Leader B1ISR change proposal: {1,2,3} → {1,2}
↓ CONTROL PATH · controller commits partition metadata
4 · DecisionISR=2 ≥ min ISR=2 → append 허용, B1·B2 ack 후 성공
↓ B2 ALSO STOPS · ISR {1}
5 · Fail closedISR=1 < min ISR=2 → NotEnoughReplicas*, write unavailable
↓ RESTART · fetch missing offsets → catch-up → ISR expand
6 · RecoverISR ≥ 2 확인 뒤 write 재개; leader 장애면 clean election
  1. Local append: Leader는 request를 검증하고 partition log/page cache에 batch를 append한다. Leader LEO는 늘지만 producer 성공과 consumer visibility는 아직 별도 사건이다.
  2. Follower pull: B2·B3의 replica fetcher가 leader에 Fetch를 보내 bytes를 가져간다. Leader는 follower fetch offset·마지막 성공 시간을 추적한다.
  3. ISR shrink: B3가 lag 시간보다 오래 따라오지 못하면 leader가 ISR 축소를 요청하고 active controller가 partition metadata를 commit한다. RF는 3 그대로다.
  4. Write admission: ISR이 min ISR 이상이면 append를 허용하고, 현재 ISR 전체가 batch를 복제해야 acks=all request가 성공한다.
  5. Fail closed: 두 번째 follower까지 잃어 ISR이 1이면 leader가 살아 있어도 새 쓰기를 거부한다. Read availability와 write availability는 다를 수 있다.
  6. Catch-up: 복귀한 follower는 자신의 LEO부터 missing batches를 fetch한다. 충분히 동기화된 뒤에야 ISR에 재가입하므로 process 기동만으로는 복구가 아니다.
  7. Leader failover: Leader가 죽으면 controller가 안전 후보를 새 leader로 정하고 epoch를 올린다. Client는 metadata refresh 후 새 leader에 재연결한다.

OS·network·분산 시스템 연결

  • OS: Ack는 개별 record마다 platter fsync했다는 뜻이 아니다. Kafka는 append-only log와 page cache, replica redundancy로 throughput과 durability를 조합한다. Host power loss까지 견디려면 서로 다른 failure domain의 replica가 필요하다.
  • Network: Follower는 push를 받는 수동 mirror가 아니라 Fetch를 반복하는 client다. Packet loss·RTT·NIC saturation은 process가 살아 있어도 fetch progress를 멈춰 ISR shrink를 만든다.
  • Failure detector: Kafka는 완벽하게 죽음을 아는 것이 아니라 timeout으로 “충분히 오래 진전이 없다”고 의심한다. 너무 짧으면 GC pause를 장애로 오인하고 너무 길면 위험 replica를 ISR에 오래 남긴다.
  • Consensus와 replication: Data ISR은 user record 복제 상태이고 KRaft quorum은 metadata 합의 상태다. Data replica가 충분해도 controller 과반이 없으면 새 leader·ISR 변경을 commit하지 못할 수 있다.
  • At-least-once 경계: Broker가 commit하고 response가 유실되면 retry가 같은 logical event를 다시 보낼 수 있다. Idempotent producer는 Kafka partition 내부 duplicate를 줄이지만 외부 DB side effect까지 보호하지 않는다.

Best practice: 장애 타임라인에 broker process·controller quorum·partition leader/epoch·replicas/ISR·UnderReplicatedPartitions·UnderMinIsrPartitionCount·ISR shrink/expand rate·producer error/latency를 같은 시각 축으로 놓는다. “무엇이 먼저 변했나”가 원인과 결과를 가른다.

Runbook: ① 영향 topic·partition과 client error 특정 ② topic describe와 controller quorum 수집 ③ healthy majority 보호, 한 번에 한 node 복구 ④ follower lag 0·ISR 회복 확인 ⑤ canary acks=all write/read 순서로 진행한다.

Anti-pattern: 장애 중 min ISR을 1로 즉시 낮추기, under-replicated 상태에서 rolling restart 계속하기, lagging replica를 강제 leader로 선출하기, 모든 broker를 동시 재시작하기, process green만 보고 종료하기.

Version/engine: Apache Kafka 4.3.1 KRaft 기준이다. 새 4.1+ cluster에서는 ELR이 기본 활성화될 수 있어 ISR 밖이라도 strict min ISR 때문에 안전성이 입증된 eligible replica가 후보가 될 수 있다. Arbitrary unclean election과 혼동하지 말고 feature level·ELR·min ISR을 함께 확인한다. Managed service는 provider의 fault injection·동등 지표를 사용한다.

7. 40분 실습: 5-node combined lab에서 RF=3 장애표 검증

실행 전 예측부터 작성
아래 단계의 B3 stop, B2 stop, B2 restart, B1 leader stop마다 예상 Leader·ISR·acks=all 결과를 먼저 적는다. 실행 출력은 예측을 채점하는 증거이지 정답을 대신하지 않는다.

사전 조건: Docker 20.10.4+, 약 2GB 여유 메모리, 공식 apache/kafka:4.3.1 image. 저장소 기본 single broker와 충돌하지 않도록 host port를 열지 않고 k27-* 전용 network/container/volume만 사용한다.

왜 5개 combined node인가: Topic replica는 B1·B2·B3 세 개지만 controller voter는 B1~B5 다섯 개다. B2·B3을 멈춰 data ISR을 1로 만들어도 B1·B4·B5가 controller 과반 3/5를 유지해 ISR 축소 metadata를 commit한다. Combined mode는 교육용이며 production 권장은 dedicated controllers다.

Step 1 · 격리된 5-node cluster 기동

docker network create k27-net VOTERS='1@k27-b1:9093,2@k27-b2:9093,3@k27-b3:9093,4@k27-b4:9093,5@k27-b5:9093' for n in 1 2 3 4 5; do docker volume create "k27-b${n}-data" docker run -d --name "k27-b${n}" --hostname "k27-b${n}" \ --network k27-net \ -e CLUSTER_ID='4L6g3nShT-eMCtK--X86sw' \ -e KAFKA_NODE_ID="${n}" \ -e KAFKA_PROCESS_ROLES='broker,controller' \ -e KAFKA_LISTENER_SECURITY_PROTOCOL_MAP='CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT' \ -e KAFKA_CONTROLLER_QUORUM_VOTERS="${VOTERS}" \ -e KAFKA_LISTENERS='PLAINTEXT://:19092,CONTROLLER://:9093' \ -e KAFKA_ADVERTISED_LISTENERS="PLAINTEXT://k27-b${n}:19092" \ -e KAFKA_INTER_BROKER_LISTENER_NAME='PLAINTEXT' \ -e KAFKA_CONTROLLER_LISTENER_NAMES='CONTROLLER' \ -e KAFKA_REPLICA_LAG_TIME_MAX_MS='5000' \ -e KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR='3' \ -e KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR='3' \ -e KAFKA_TRANSACTION_STATE_LOG_MIN_ISR='2' \ -e KAFKA_HEAP_OPTS='-Xms384m -Xmx384m' \ -v "k27-b${n}-data:/tmp/kraft-combined-logs" \ apache/kafka:4.3.1 done for n in 1 2 3 4 5; do until docker exec "k27-b${n}" /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server k27-b1:19092 --list >/dev/null 2>&1; do sleep 2; done done

예상: 다섯 container가 실행되고 cluster가 요청을 받는다. replica.lag.time.max.ms=5s는 관찰 시간을 줄이는 lab-only 값이므로 production에 복사하지 않는다.

Step 2 · RF=3·min ISR=2 baseline

docker exec k27-b1 /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server k27-b1:19092 --create --topic day27.isr \ --replica-assignment 1:2:3 --config min.insync.replicas=2 docker exec k27-b1 /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server k27-b1:19092 --describe --topic day27.isr printf 'baseline\n' | docker exec -i k27-b1 \ /opt/kafka/bin/kafka-console-producer.sh \ --bootstrap-server k27-b1:19092 --topic day27.isr \ --producer-property acks=all \ --producer-property request.timeout.ms=5000 \ --producer-property delivery.timeout.ms=7000

예상: Partition 0의 Leader=1, Replicas=1,2,3, Isr=1,2,3이 보이고 baseline write가 성공한다. RF·ISR·leader·min ISR을 표 첫 행에 기록한다.

Step 3 · Follower 하나 중단: ISR 3→2

docker stop k27-b3 sleep 8 docker exec k27-b1 /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server k27-b1:19092 --describe --topic day27.isr printf 'one-follower-down\n' | docker exec -i k27-b1 \ /opt/kafka/bin/kafka-console-producer.sh \ --bootstrap-server k27-b1:19092 --topic day27.isr \ --producer-property acks=all \ --producer-property request.timeout.ms=5000 \ --producer-property delivery.timeout.ms=7000

예상: Replicas는 1,2,3 그대로지만 ISR은 1,2로 줄고 write는 성공한다. “RF가 줄었다”가 아니라 failure margin 하나를 사용했다.

Step 4 · 두 번째 follower 중단: ISR 2→1, fail closed

docker stop k27-b2 sleep 8 docker exec k27-b1 /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server k27-b1:19092 --describe --topic day27.isr printf 'must-fail\n' | docker exec -i k27-b1 \ /opt/kafka/bin/kafka-console-producer.sh \ --bootstrap-server k27-b1:19092 --topic day27.isr \ --producer-property acks=all \ --producer-property request.timeout.ms=5000 \ --producer-property delivery.timeout.ms=7000

예상: ISR=1이고 write는 NotEnoughReplicas, NotEnoughReplicasAfterAppend 또는 deadline 계열 오류로 끝난다. B1은 살아 있지만 min ISR=2 계약 때문에 write availability가 닫힌다. 이 실패는 정상 안전 동작이다.

Step 5 · B2 복구: process up보다 ISR 재가입을 기다린다

docker start k27-b2 for i in 1 2 3 4 5 6; do docker exec k27-b1 /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server k27-b1:19092 --describe --topic day27.isr sleep 3 done printf 'recovered-two-isr\n' | docker exec -i k27-b1 \ /opt/kafka/bin/kafka-console-producer.sh \ --bootstrap-server k27-b1:19092 --topic day27.isr \ --producer-property acks=all

예상: B2 기동 직후에는 ISR=1일 수 있다. Missing offsets를 fetch해 leader와 catch-up하면 ISR=1,2로 확장되고 write가 다시 성공한다. Recovery time은 process startup이 아니라 catch-up 완료까지다.

Step 6 · Clean leader failover

docker start k27-b3 sleep 10 docker stop k27-b1 sleep 8 docker exec k27-b2 /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server k27-b2:19092 --describe --topic day27.isr printf 'after-clean-failover\n' | docker exec -i k27-b2 \ /opt/kafka/bin/kafka-console-producer.sh \ --bootstrap-server k27-b2:19092 --topic day27.isr \ --producer-property acks=all

예상: B2 또는 B3가 새 leader가 되고 write가 선출·metadata refresh의 짧은 공백 뒤 성공한다. Replicas는 그대로이며 leader와 epoch가 바뀐다. B4·B5를 포함한 controller 과반은 살아 있다.

실패 시 해석·cleanup

자주 나는 오류: OOM이면 다른 Docker workload를 줄이거나 heap을 512MB로 높인다. Topic 생성이 실패하면 다섯 node log와 quorum 준비를 확인한다. 8초 뒤 ISR이 아직 줄지 않으면 실제 lag 설정과 controller quorum을 확인하고 조금 더 기다린다. Producer timeout은 record가 반드시 없다는 뜻이 아니므로 cleanup 전 consume로 결과를 확인한다.

docker start k27-b1 k27-b2 k27-b3 2>/dev/null || true docker rm -f k27-b1 k27-b2 k27-b3 k27-b4 k27-b5 docker volume rm k27-b1-data k27-b2-data k27-b3-data k27-b4-data k27-b5-data docker network rm k27-net

Cleanup은 이름이 k27-로 시작하는 이 실습 자원만 제거한다. 저장소 기본 kafka-learning-broker와 volume은 건드리지 않는다.

8. 놓치기 쉬운 함정

  • RF와 ISR 혼동: Broker가 죽어도 RF=3은 바뀌지 않고 ISR만 줄어든다.
  • acks=all을 과반 ack로 오해: 현재 ISR 전체 ack를 기다리며 min ISR은 admission floor다.
  • Process up=복구 완료: Follower가 gap을 따라잡아 ISR에 돌아와야 failure budget이 복원된다.
  • Data ISR=controller quorum: 두 집합은 다른 log·다른 안전 규칙을 가진다.
  • Timeout=확정 실패: Commit 후 response 유실이면 retry가 duplicate를 만들 수 있다.
  • Unclean election을 availability 스위치로 사용: 즉시 쓰기를 살리는 대신 acknowledged data loss 가능성을 연다.
  • 한 host의 다섯 container를 HA로 오해: 오늘 lab은 protocol 관찰용이며 host failure에는 전부 사라진다.
  • 낮춘 lag timeout을 production 복사: 짧은 GC·network jitter를 ISR flapping으로 오인할 수 있다.

9. 대기업 기술 면접 질문 3개

Q1. RF=3·min ISR=2·acks=all에서 broker가 차례로 두 대 죽으면 어떻게 됩니까?
좋은 답변 구조: Leader/follower와 initial ISR 가정 → 첫 follower failure 후 ISR=2·쓰기 가능 → 둘째 failure 후 ISR=1·NotEnoughReplicas 계열·fail closed → RF는 3 유지 → controller quorum 전제 → replica 복구·catch-up·ISR expand 뒤 재개 → availability/durability trade-off.

Q2. Leader가 append한 직후 죽고 producer는 timeout을 받았습니다. Record는 유실됐습니까?
좋은 답변 구조: Local LEO와 HW/ack 분리 → follower replication·min ISR·response 전송 시점의 failure window → 새 leader의 committed prefix → timeout은 unknown outcome → idempotent producer와 business key reconciliation → 외부 side effect 경계.

Q3. ISR이 반복해서 3↔2로 흔들릴 때 무엇을 보겠습니까?
좋은 답변 구조: 영향 partition·broker 특정 → shrink/expand timeline → replica fetch lag, network RTT/loss, disk latency, GC, CPU, hot key 확인 → threshold를 먼저 늘리지 않음 → 문제 domain 격리·traffic 제한 → 안정 시간·canary로 복구 판정.

10. 복습과 정답

어제 내용 회상 3문제

  1. Metadata leader local append와 quorum commit은 무엇이 다른가?
  2. 3-controller와 5-controller quorum은 각각 몇 개 동시 실패를 견디는가?
  3. Controller quorum을 잃으면 기존 data path가 반드시 즉시 모두 멈추는가?

짧은 정답: ① Local LEO 전진은 미확정이고 voter 과반 복제로 metadata HW가 지나야 committed다. ② 각각 1개와 2개다. ③ 기존 leader와 적용된 metadata로 일부 produce/fetch가 잠시 가능하지만 새 metadata mutation·leader election은 막힐 수 있다.

오늘 확인 3문제

  1. RF=3인데 ISR=1일 수 있는 이유와 두 값의 상태 소유자를 설명하라.
  2. ISR=2·min ISR=2에서 acks=all은 몇 replica의 ack를 기다리며, follower 하나를 더 잃으면 왜 실패하는가?
  3. Restarted follower를 복구 완료로 선언할 증거 네 가지는?

채점 기준: ① RF는 metadata의 고정 assignment, ISR은 leader가 관찰해 controller에 반영하는 동적 집합(3점). ② 현재 ISR 둘 모두 ack, ISR=1이면 admission floor 미달로 거부(3점). ③ Process health 외 LEO gap/lag 0 수렴, ISR 재가입, URP·UnderMinISR 정상화, canary write/read 중 네 가지(4점). 총 8점 이상 통과.
