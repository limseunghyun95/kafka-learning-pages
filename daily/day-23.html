APACHE KAFKA 4.3 · WEEK 4 / DAY 23 · CONSISTENCY

LEO, HW, leader epoch

log의 끝·안전 공개 경계·leader 세대를 하나의 장애 복구 모델로 연결하기 · 이론 70분 + 실습 30분

한 줄 요약
LEO는 replica마다 다른 “다음 append 위치”, HW는 복제 조건을 만족해 일반 consumer가 읽을 수 있는 안전 경계, leader epoch는 leader가 바뀔 때 증가하는 세대 번호다. 세 값을 함께 봐야 “어디까지 존재하고, 어디까지 확정됐으며, 어느 leader의 기록인가”를 답할 수 있다.

1. 선수 용어 사전

Offsetpartition 안 record의 위치를 가리키는 증가하는 정수. 이 자료에서 경계값 105는 “offset 105가 존재한다”가 아니라 “다음 위치가 105이므로 0~104가 존재한다”는 뜻이다.
Replica하나의 partition log 사본. leader와 follower 각각이 local log와 local end를 가진다.
LEOLog End Offset. 해당 replica에서 다음 record가 append될 위치. partition 공통값이 아니라 replica-local 값이다.
HWHigh Watermark. 복제 안전 조건을 만족한 log의 상한 경계. 일반 consumer는 offset이 HW보다 작은 record만 읽는다.
Leader epochpartition leader 세대 번호. leader가 새로 선출되면 증가하며, 오래된 metadata를 가진 client·replica를 fencing하고 서로 다른 tail을 비교하는 기준이 된다.
Fencing낡은 세대의 주체가 계속 명령하지 못하게 거부하는 안전 장치. 울타리 밖으로 밀어낸다는 뜻이다.
ISRIn-Sync Replicas. leader를 충분히 따라온 replica의 동적 집합. HW 전진과 안전한 leader 후보 판단에 관여한다.
Truncation새 leader의 역사와 충돌하는 follower tail을 공통 지점까지 잘라내는 복구. 임의 데이터 삭제가 아니라 하나의 순서를 회복하기 위한 상태 전이다.
LSOLast Stable Offset. 진행 중 transaction 때문에 read_committed consumer가 넘지 못하는 경계. HW와 다른 축이며 보통 LSO ≤ HW ≤ LEO로 생각한다.
Control pathKRaft controller가 leader·epoch·ISR metadata를 확정해 전파하는 길. record bytes가 흐르는 data path와 구분한다.

2. 왜 중요한가

“leader에 record가 append됐다”는 사실만으로 consumer가 읽을 수 있거나 장애 뒤 살아남는다고 단정할 수 없다. leader LEO가 105여도 HW가 101이면 offset 101~104는 아직 leader에만 있거나 일부 replica에만 있어 일반 consumer에게 공개되지 않는다. 이 구간에서 leader가 죽으면 새 leader의 안전한 역사에 맞춰 tail이 잘릴 수 있다.

반대로 HW만 보면 누가 현재 ordering authority인지 알 수 없다. network partition으로 오래된 leader가 살아 있다고 착각할 때 leader epoch가 낡은 요청을 거부하지 않으면 두 leader가 동시에 쓰는 split-brain 위험이 생긴다. Kafka는 offset 경계와 epoch 세대를 조합해 하나의 partition history를 유지한다.

면접에서 강한 답은 숫자를 정확히 쓴다. “LEO는 마지막 offset”이라고 뭉개지 않고 next-offset convention을 선언하고, 상태 소유자 → 불변식 → 성공 확정 시점 → failure window → 복구 truncation → 비용 순으로 설명한다.

3. Architecture: append에서 epoch 기반 복구까지

1 · Producerepoch 7의 leader B1에 ProduceRequest → batch append
↓ DATA PATH · B1 LEO 101 → 105
2 · FollowersB2 LEO=103, B3 LEO=101에서 각자 FetchRequest
↓ 공통 복제 경계 · HW=101, offsets < 101 공개
3 · ConsumerHW까지만 fetch. leader에만 있는 101~104는 아직 숨김
↓ B1 장애 · CONTROL PATH에서 B2 선출, epoch 8
4 · KRaftleader=B2, leaderEpoch=8 metadata 확정·전파
↓ OffsetForLeaderEpoch · 공통 역사 끝을 질의
5 · Recovery낡거나 divergent한 tail을 안전 지점까지 truncate → epoch 8 leader에서 다시 fetch
  1. Append: epoch 7 leader B1이 새 batch의 partition 순서를 정한다. leader local LEO는 가장 먼저 전진할 수 있다.
  2. Replication: followers는 자신의 LEO를 next fetch offset으로 보내 연속 bytes를 복제한다. 따라서 한 순간에 LEO가 서로 다를 수 있다.
  3. Visibility: leader는 ISR replica들의 진척을 관찰해 HW를 전진시킨다. 예시는 next-offset convention이므로 HW=101이면 offset 100까지 공개된다.
  4. Election: B1 장애를 KRaft controller가 처리해 B2를 새 leader로 정하고 leader epoch를 8로 올린다. clients는 새 metadata를 받아야 한다.
  5. Reconciliation: 복귀 replica는 epoch별 end offset을 비교한다. 자기 tail이 새 leader history와 충돌하면 공통 지점까지 truncate하고 다시 fetch한다.

LEO: 마지막 record가 아니라 다음 칸

offset 0~104가 local log에 있으면 LEO는 105다. 이 정의를 쓰면 log 길이와 range 계산이 자연스럽다. follower는 fetchOffset=105로 “105부터 달라”고 요청한다. 운영 도구가 logEndOffset=105를 보여줄 때 record 105가 이미 있다는 뜻으로 해석하면 lag를 1씩 틀리게 계산한다.

LEO는 replica-local이다. B1=105, B2=103, B3=101이면 B2는 두 record, B3는 네 record 뒤처져 있다. 단, offset 차이만으로 시간·bytes 비용은 알 수 없다. 큰 batch 하나와 작은 records 수천 개가 다른 비용을 만들므로 bytes lag, fetch latency, disk queue를 함께 본다.

HW: “존재”와 “안전하게 보임”을 분리

Leader append는 local 존재를 만들고 follower replication은 failure domain을 넘는 안전성을 만든다. Kafka는 이 둘 사이를 HW로 구분한다. 일반 read-uncommitted consumer도 HW를 넘는 leader-only tail을 읽지 않으므로, 읽은 record가 곧 leader failover로 사라지는 현상을 막는다.

Follower fetch response는 data뿐 아니라 leader HW도 전달한다. follower가 local LEO까지 append했다고 즉시 동일 HW를 아는 것은 아니며 fetch round-trip을 거쳐 state가 전파된다. 이 때문에 아주 짧은 시점에는 leader와 follower가 관찰한 HW가 다를 수 있다. 분산 시스템에서는 값뿐 아니라 누가 언제 관찰했는지가 중요하다.

Kafka 4.x ELR이 활성화되면 strict min ISR 규칙 때문에 ISR 크기가 min.insync.replicas보다 작을 때 data partition HW가 전진하지 않는 동작이 중요해진다. 이 안전성으로 일부 non-ISR replica도 eligible leader로 추적할 수 있다. 그러므로 “HW는 무조건 현재 ISR LEO의 단순 최솟값”이라는 한 줄 공식은 version·feature 조건을 놓친다.

Leader epoch: term과 log history

Leader epoch는 Raft의 term과 비슷한 세대 개념이지만 data partition replication은 KRaft metadata quorum 자체와 동일한 log가 아니다. KRaft controller가 partition leader·epoch metadata를 관리하고, 각 broker는 실제 record log와 epoch별 offset history를 관리한다. control plane의 epoch가 data plane의 낡은 주체를 fencing한다.

OffsetForLeaderEpoch request에는 현재 알고 있는 leader epoch와 조회할 epoch가 들어간다. broker는 current epoch가 작으면 FENCED_LEADER_EPOCH, 더 크면 UNKNOWN_LEADER_EPOCH로 잘못된 세대를 드러낼 수 있고, 조회 epoch의 end offset을 응답한다. Follower는 이를 자기 log와 비교해 divergence가 시작된 위치를 찾고 truncate한다.

Producer 성공 시점: 정확한 ack 확정은 acks, ISR, min.insync.replicas, ELR 활성화 조건에 의존하며 Day 24에서 깊게 다룬다. 오늘의 핵심은 local append(LEO 전진), consumer visibility(HW 전진), leader authority(epoch 전진)가 서로 다른 사건이라는 점이다.

OS·network 비용

LEO 전진은 batch append가 page cache와 log segment에 반영되는 hot path다. HW 전진은 follower fetch round-trip, inter-broker TCP, follower disk/page cache append, leader의 replica progress 추적을 기다린다. 따라서 producer latency가 늘고 HW-LEO gap이 벌어질 때 CPU만 보지 말고 network retransmission, socket buffer, fetch latency, disk await, I/O queue, GC pause를 같은 timeline에 둔다.

Epoch change 자체는 metadata record로 작지만 뒤따르는 비용은 클 수 있다. clients metadata refresh, leader cache miss, follower truncation, replica catch-up, page cache 냉각이 동시에 발생한다. 잦은 leader flap은 작은 control event가 큰 data-path tail latency를 만드는 전형적인 연쇄 장애다.

복구truncate 전 partition·epoch·end offset 증거 보존자동 복구를 방해하지 않으면서 유실 여부와 원인을 사후 설명할 수 있다.

Best practice: dashboard에 leader LEO, follower LEO 또는 replica lag, HW 관련 fetch/lag, ISR 크기, UnderReplicatedPartitions, UnderMinIsrPartitionCount, leader election, offline partitions를 동일 partition·broker·시간 축으로 연결한다. runbook에는 모든 offset이 next-position인지 last-record인지 명시한다. 장애 전후 topic describe와 broker/controller log를 보존한다.

Anti-pattern: LEO를 committed offset이라고 부르기, consumer lag을 replication lag으로 해석, HW=leader LEO라고 가정, epoch 증가를 데이터 유실 자체로 단정, follower tail 파일을 수동 삭제해 “복구”, 모든 lag에 timeout 확대부터 적용.

Edge case: transaction topic에서는 read_committed visibility가 HW가 아니라 LSO에도 제한된다. log retention으로 log start offset이 올라간 경우 epoch end와 비교할 수 있는 범위가 달라질 수 있다. remote/tiered storage는 local log size만으로 전체 history를 판단하지 못한다. preferred leader 이동은 정상적인 epoch 증가를 만들 수 있다.

Version/engine 차이: 이 자료는 Kafka 4.3 KRaft와 ELR-aware 운영을 기준으로 한다. ELR은 Kafka 4.0부터 제공되고 새 4.1+ cluster에서 기본 활성화될 수 있으므로 feature level과 cluster/topic min.insync.replicas를 확인한다. ZooKeeper legacy는 controller metadata 경로가 다르며, managed service는 epoch cache·HW를 직접 노출하지 않을 수 있어 provider의 equivalent metrics와 broker logs를 매핑한다.

7. 30분 실습: next-offset 경계를 직접 검증

실행 전 예측
빈 partition의 earliest와 latest는 둘 다 0이다. record 5개를 쓰면 latest는 5이고 실제 마지막 record offset은 4다. offset 2부터 2개를 읽으면 어떤 offset이 출력될까? broker 재시작 뒤 latest는 유지될까?

사전 조건: 저장소 루트, Docker, 공식 Kafka 4.3.1 단일 broker KRaft. RF=1이라 follower divergence와 HW-LEO gap은 만들 수 없다. 대신 CLI가 보여주는 LEO의 경계 정의를 재현하고, 다중 replica 사고 실험으로 HW를 계산한다.

Step 1 · 빈 log의 두 경계

make up docker compose exec broker /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server localhost:9092 --create --if-not-exists \ --topic day23.offsets --partitions 1 --replication-factor 1 docker compose exec broker /opt/kafka/bin/kafka-get-offsets.sh \ --bootstrap-server localhost:9092 --topic day23.offsets --time -2 docker compose exec broker /opt/kafka/bin/kafka-get-offsets.sh \ --bootstrap-server localhost:9092 --topic day23.offsets --time -1

예상: earliest(-2)와 latest(-1) 모두 day23.offsets:0:0. 아직 record가 없어 next append 위치가 0이다.

Step 2 · 5개 append 후 LEO 확인

printf 'e0\ne1\ne2\ne3\ne4\n' | docker compose exec -T broker \ /opt/kafka/bin/kafka-console-producer.sh \ --bootstrap-server localhost:9092 --topic day23.offsets docker compose exec broker /opt/kafka/bin/kafka-get-offsets.sh \ --bootstrap-server localhost:9092 --topic day23.offsets --time -1

예상: latest가 5다. 존재하는 offsets는 0~4이며 LEO는 다음 위치 5다. 출력값을 “마지막 offset 5”라고 기록하면 off-by-one 버그다.

Step 3 · 특정 offset부터 읽기

docker compose exec broker /opt/kafka/bin/kafka-console-consumer.sh \ --bootstrap-server localhost:9092 --topic day23.offsets \ --partition 0 --offset 2 --max-messages 2 \ --property print.offset=true --property print.value=true

예상: offset 2의 e2, offset 3의 e3가 출력된다. consumer position은 다음에 읽을 4가 된다. 이 position, committed offset, broker LEO는 값이 우연히 같아도 소유자와 의미가 다르다.

Step 4 · 실패 주입과 복구

docker compose stop broker docker compose start broker make status docker compose exec broker /opt/kafka/bin/kafka-get-offsets.sh \ --bootstrap-server localhost:9092 --topic day23.offsets --time -1

예상: health가 돌아온 뒤 latest는 5다. RF=1이므로 leader 교체나 follower truncation을 증명한 것은 아니다. persistent local log의 end가 재시작 뒤 복구된 것만 증명한다.

Step 5 · 종이 위 다중 replica 실험

B1/B2/B3가 모두 ISR이고 next-offset LEO가 105/103/101이라면 현재 공통 복제 범위는 offsets <101이다. 기본 정신 모델에서 HW는 101을 넘을 수 없다. B3가 105까지 따라오고 복제 조건이 충족되면 HW는 105로 전진한다. 이후 B1이 죽고 B2가 epoch 8 leader가 되면 B1이 복귀할 때 current epoch 7 요청은 fenced되고 epoch history에 따라 tail을 검증한다.

자주 나는 오류와 해결: startup 직후 connection 오류는 make status가 healthy가 될 때까지 기다린다. 출력의 broker ID는 환경에 따라 다르다. kafka-get-offsets.sh가 없으면 image version이 프로젝트 기준 4.3.1인지 확인한다. 단일 broker 결과로 “HW=LEO는 항상 성립”이라 일반화하지 않는다.

Cleanup:

docker compose exec broker /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server localhost:9092 --delete --topic day23.offsets make down

8. 놓치기 쉬운 함정

  • LEO는 마지막 record offset이 아니다: 다음 append 위치이므로 last offset은 보통 LEO-1이다.
  • LEO는 partition 공통값이 아니다: 복제 중 replica마다 다르다.
  • HW는 consumer committed offset이 아니다: 전자는 broker 복제 경계, 후자는 group 재시작 위치다.
  • HW만으로 transaction visibility가 끝나지 않는다: read_committed에는 LSO가 추가된다.
  • Epoch 증가 ≠ 유실: leader 이동의 세대 변화다. 유실 여부는 HW·ack·선출 후보·truncation 증거로 판단한다.
  • Truncation ≠ 항상 장애: divergent uncommitted tail을 제거해 단일 history를 복구하는 정상 절차일 수 있다.
  • HW 단순 최솟값 공식 주의: ISR 변화, min ISR, Kafka 4.x ELR 조건을 포함해 설명한다.

9. 대기업 기술 면접 질문 3개

Q1. LEO와 HW가 왜 둘 다 필요한가요?
좋은 답변 구조: next-offset convention 선언 → replica-local append progress와 cluster-safe visibility 분리 → B1/B2/B3 수치 예시 → consumer가 HW 미만만 읽는 이유 → leader failure window → latency·durability trade-off → transaction이면 LSO 추가.

Q2. Leader epoch가 데이터 유실을 어떻게 막나요?
좋은 답변 구조: leader authority 세대 → KRaft controller가 새 leader·epoch 확정 → stale current epoch fencing → OffsetForLeaderEpoch로 epoch end 조회 → divergent follower tail truncate → 단일 partition history 회복 → unsafe election은 별도 위험이라고 경계.

Q3. Producer latency가 늘고 consumer는 새 record를 못 봅니다. 진단하세요.
좋은 답변 구조: SLO와 영향 partition 수 확인 → leader/follower LEO와 HW gap → ISR·UnderMinISR·acks 조건 → fetch/network/disk/GC 증거 → 안전한 workload 제한 → follower catch-up과 HW 전진 확인 → replay·rollback → timeout만 늘리지 않기.

10. 복습과 정답

어제 내용 회상 3문제

  1. RF=3과 ISR=2는 각각 무엇을 뜻하는가?
  2. Follower가 leader에게 pull fetch하는 장점은?
  3. ISR shrink 때 controller와 partition leader의 역할은 어떻게 다른가?

짧은 정답: ① RF는 assignment 크기, ISR은 현재 충분히 동기화된 동적 집합. ② follower 속도 기반 backpressure와 offset 기반 연속 batch 복제. ③ leader가 replica 진척을 관찰하고 KRaft controller가 ISR/leader metadata 전이를 확정·전파한다.

오늘 확인 3문제

  1. Offsets 0~9가 있으면 LEO는 얼마이며 왜 그런가?
  2. B1/B2/B3 LEO가 105/103/101이고 모두 ISR일 때 HW 상한 경계를 설명하라.
  3. Old leader가 돌아왔을 때 leader epoch와 OffsetForLeaderEpoch가 하는 일을 설명하라.

채점 기준: ① 다음 append 위치 10과 off-by-one 설명(2점). ② next-offset convention으로 offsets <101 공통, HW는 101을 넘지 못한다고 설명하되 feature 조건을 명시(4점). ③ stale epoch fencing, epoch end 비교, divergent tail truncation, 새 leader fetch까지 연결(4점). 총 8점 이상 통과.
