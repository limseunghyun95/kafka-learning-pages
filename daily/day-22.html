APACHE KAFKA 4.3 · WEEK 4 / DAY 22 · REPLICATION

leader/follower fetch와 ISR

복제본의 역할 이름이 아니라 pull loop·상태 전이·선출 자격으로 이해하기 · 이론 65분 + 실습 30분

한 줄 요약
Producer write는 partition leader가 순서를 정하고, follower는 leader에게 반복적으로 fetch해 같은 log를 복제한다. ISR은 고정된 replica 목록이 아니라 현재 충분히 따라온 replica의 동적 집합이며, 안전한 write·leader election·consumer visibility의 기준에 관여한다.

1. 선수 용어 사전

Replica하나의 topic partition log를 가진 복제본. replication factor가 3이면 그 partition의 replica가 세 broker에 배치된다.
Leader replica현재 partition의 쓰기 순서를 결정하는 replica. 일반 producer와 consumer 요청은 이 leader를 향한다.
Follower replicaleader log를 복제하는 replica. leader가 데이터를 push하는 것이 아니라 follower가 자신의 다음 offset을 담아 fetch한다.
Replication factorpartition에 할당된 전체 replica 수. 설정·assignment의 크기이며 현재 건강 상태가 아니다.
ISRIn-Sync Replicas. leader를 포함해 현재 leader log를 충분히 따라오는 replica 집합. 장애·지연에 따라 줄고 회복하면 늘어난다.
LEOLog End Offset. 각 replica log에서 다음에 append할 위치. 같은 partition이어도 복제 중에는 replica별 LEO가 다를 수 있다.
HWHigh Watermark. 복제 안전성 때문에 일반 consumer에게 공개할 수 있는 경계. 단순 leader LEO와 다르다.
Replica lagfollower가 leader보다 뒤처진 정도. bytes·offset·시간으로 볼 수 있으며 느린 disk/network/fetch thread가 원인이 될 수 있다.
KRaft controllerbroker 등록, partition leader·ISR 같은 cluster metadata의 변경을 관리하는 controller quorum의 역할. record data path를 직접 운반하지 않는다.
ELREligible Leader Replicas. Kafka 4.x의 KIP-966 계열 기능으로, 엄격한 min ISR 조건 아래 안전성을 보존하며 선출 후보를 확장하는 별도 metadata 집합이다.

2. 왜 중요한가

replication.factor=3이라고 화면에 보인다는 이유만으로 지금 세 copy가 모두 안전하다고 말할 수 없다. 한 follower의 disk가 느리거나 network가 단절되면 assignment는 3인 채 ISR은 2 또는 1로 줄 수 있다. 이 차이를 모르면 under-replicated partition 경보를 무시하거나, 반대로 정상적인 leader 이동을 데이터 유실로 오판한다.

면접에서 “leader는 쓰고 follower는 복제한다”로 끝내면 얕다. 강한 답은 follower pull 경로, replica별 LEO, ISR 상태 전이의 증거, write 성공이 확정되는 지점, controller가 바꾸는 metadata, leader 장애 시 선출 후보를 연결하고 durability와 availability의 비용을 설명한다.

3. Architecture: produce와 follower fetch의 두 경로

1 · Producermetadata로 P0 leader=B1 확인 → ProduceRequest(batch)
↓ DATA PATH: client → B1 leader
2 · Leader B1batch 검증 → P0 log에 순서대로 append → LEO 전진
↑ REPLICA FETCH: B2/B3가 자신의 offset부터 요청
3 · FollowersB2·B3가 bytes를 받아 local log append → 각 LEO 보고
↓ ISR의 replica들이 적용한 범위까지 commit/HW 전진
4 · Ack/Fetchacks 조건 충족 시 producer 응답, consumer는 안전한 공개 범위 fetch
↕ CONTROL PATH: ISR shrink/expand·leader change metadata
5 · ControllerKRaft metadata log에 partition state 변경 기록 → brokers에 전파
  1. Metadata: producer는 모든 replica에 쓰지 않고 현재 leader endpoint를 찾는다.
  2. Append: leader가 partition 내 순서의 단일 기준이다. page cache·segment에 batch가 append된다.
  3. Pull: follower fetcher가 “내 LEO부터” 요청하므로 backpressure가 자연스럽고 leader는 여러 follower 속도를 각각 관찰한다.
  4. Progress: follower가 fetch를 반복하며 따라오면 leader는 replica 상태를 갱신한다. 충분히 뒤처지면 ISR에서 제외하고 회복하면 다시 포함한다.
  5. Metadata transition: ISR/leader 변경은 KRaft controller가 cluster metadata로 확정·전파한다. data batch가 controller를 통과하는 것은 아니다.

왜 follower가 pull하는가

Follower는 자신의 처리 속도에 맞춰 fetch하므로 leader가 follower별 push queue와 재전송 상태를 과도하게 관리하지 않아도 된다. fetch request에는 다음 필요한 offset이 포함되고 response는 연속 log bytes다. 이는 Kafka consumer fetch와 유사한 sequential I/O·batching 이점을 갖는다. 느린 follower는 request 주기와 LEO 진척으로 드러난다.

ISR state transition

Replica가 assignment에 남아 있어도 fetch가 끊기거나 leader LEO를 충분히 따라오지 못한 상태가 replica.lag.time.max.ms 이상 지속되면 ISR에서 빠질 수 있다. 반대로 lagging replica가 leader의 최신 범위까지 따라잡고 조건을 만족하면 ISR에 다시 들어온다. ISR shrink는 데이터 삭제가 아니라 현재 동기화·선출 자격의 변화다.

상태 전이는 보통 ISR 3 → 2 → 1처럼 보이며, replication factor는 계속 3이다. ISR이 줄면 남은 replica가 더 적어 durability margin이 감소하고, acks=all과 min.insync.replicas에 따라 write availability가 달라진다. 세부 상호작용은 Day 24에서 수치로 다룬다.

Network·OS 비용

복제는 broker 간 TCP, follower fetcher thread, leader network/request thread, page cache, disk append를 함께 소비한다. follower disk latency가 증가하면 fetch response를 받아도 local append 진척이 느려지고 replica lag가 커진다. 네트워크 포화·packet loss·broker GC pause도 같은 증상으로 보일 수 있으므로 ISR 결과만 보고 disk 장애로 단정하면 안 된다.

Replication factor를 늘리면 storage와 inter-broker network bytes가 비례해 늘고 leader가 관리할 fetch traffic도 증가한다. 대신 leader 장애 후 committed data를 가진 후보가 늘어난다. 이것이 분산 시스템의 durability·availability·cost trade-off다.

Kafka 4.x ELR 주의

Kafka 4.0부터 ELR 기능이 제공되고 새 Kafka 4.1+ cluster에서는 기본 활성화되는 구성이 있다. ELR은 ISR과 같은 말이 아니다. 엄격한 min ISR 규칙으로 안전성이 확보된 특정 replica를 KRaft metadata에 별도 후보로 기록한다. 면접에서는 기본 ISR 모델을 설명한 뒤 “4.x에서는 ELR이 선출 후보를 보완하므로 cluster 설정과 공식 문서를 확인한다”고 범위를 명시하는 편이 정확하다.

5. 실무 설계 판단

ISR shrink 경보leader/follower별 disk·network·fetch lag와 controller event 동시 수집증상만으로 원인을 단정하지 않고 병목 계층을 분리한다.

용량 계획steady state가 아니라 broker 1대 장애 시 network/disk headroom 계산복구 fetch와 leader 이동이 동시에 발생하는 최악 구간을 버틴다.

Best practice: topic describe의 Replicas와 Isr를 별도 필드로 수집한다. under-replicated partitions, ISR shrink/expand rate, follower lag, replica fetcher throughput, disk latency, network saturation, broker registration/fencing event를 같은 timeline에 놓는다. 배포 전 broker 한 대 상실 시에도 min ISR과 SLO를 만족하는지 계산한다.

Anti-pattern: RF=3을 현재 copy 3개 건강으로 해석, ISR shrink마다 모든 broker 동시 restart, follower lag 원인 확인 없이 throttling 해제, 복구 중 대규모 reassignment 병행, controller와 partition leader를 같은 역할로 설명.

Edge case: low-throughput topic에서 fetch wait와 lag timeout의 관계, tiered storage follower bootstrap, disk 교체 후 대량 catch-up, preferred leader rebalance, ELR enablement·migration 상태, rack 정보 누락을 확인한다.

Version/engine 차이: Kafka 4.3 KRaft와 ELR-aware 문서를 기준으로 한다. ZooKeeper 기반 legacy cluster의 controller metadata 저장·전파 경로는 다르지만 partition leader/follower data replication의 핵심 정신 모델은 유사하다. Managed Kafka는 일부 broker metrics/config를 감추므로 provider의 등가 지표를 매핑한다.

7. 30분 실습: Replicas와 ISR을 다른 상태로 읽기

실행 전 예측
현재 local cluster가 broker 1대라면 RF=1 topic의 Leader·Replicas·Isr은 무엇일까? RF=2 생성은 왜 실패할까? broker를 중지하면 “ISR이 0”이라는 결과를 받을까, 아니면 metadata를 물어볼 broker 자체가 없어질까?

사전 조건: 저장소 루트, Docker 실행 가능, 공식 Kafka 4.3.1 단일 broker KRaft. 이 실습은 구조 읽기에 집중하며 실제 follower lag/ISR shrink는 Week 4 통합 랩에서 다중 broker로 관찰한다.

Step 1 · 단일 replica의 세 필드 확인

make up docker compose exec broker /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server localhost:9092 --create --if-not-exists \ --topic day22.replication --partitions 1 --replication-factor 1 docker compose exec broker /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server localhost:9092 --describe --topic day22.replication

예상: Leader: 1, Replicas: 1, Isr: 1처럼 같은 broker가 세 필드에 나타난다. 의미는 각각 현재 ordering authority, assignment, 현재 in-sync 집합으로 다르다.

Step 2 · RF는 물리 broker 수를 넘을 수 없음

docker compose exec broker /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server localhost:9092 --create \ --topic day22.rf2-fail --partitions 1 --replication-factor 2

실패 주입·예상: broker가 하나뿐이므로 replication factor 2를 만족할 수 없다는 오류가 난다. 같은 broker에 두 copy를 두는 방식은 broker failure domain을 분리하지 못하므로 Kafka replica assignment가 허용하지 않는다.

Step 3 · log directory 관점 확인

printf 'r0\nr1\nr2\n' | docker compose exec -T broker \ /opt/kafka/bin/kafka-console-producer.sh \ --bootstrap-server localhost:9092 --topic day22.replication docker compose exec broker /opt/kafka/bin/kafka-log-dirs.sh \ --bootstrap-server localhost:9092 --describe \ --topic-list day22.replication

예상 관찰: broker 1의 local replica path·size와 replica lag 정보가 보인다. RF=1 leader replica라 lag는 follower 비교 증거가 아니다. 다중 broker에서는 broker별 replica 상태를 비교해야 한다.

Step 4 · broker 중단과 관측 경계

docker compose stop broker docker compose ps docker compose start broker make status docker compose exec broker /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server localhost:9092 --describe --topic day22.replication

예상: broker가 멈춘 동안에는 질의 endpoint가 없어 describe 자체가 실패한다. 다시 시작하면 RF=1 replica가 leader이자 ISR로 복구된다. 이것은 고가용성 실험이 아니라 단일 broker 구성의 한계를 증명한다.

자주 나는 오류와 해결: startup 직후 connection 오류는 make status가 healthy가 될 때까지 기다린다. RF2 생성 실패 topic은 생성되지 않았으므로 cleanup에서 없어도 정상이다. broker ID 출력은 compose 설정을 기준으로 달라질 수 있으니 숫자 자체보다 세 필드 관계를 본다.

Cleanup:

docker compose exec broker /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server localhost:9092 --delete --topic day22.replication make down

8. 놓치기 쉬운 함정

  • RF ≠ ISR 크기: RF는 assignment, ISR은 현재 건강한 동적 집합이다.
  • Follower는 standby read replica가 아님: 일반 consumer read를 분산하는 역할로 단순 해석하지 않는다.
  • ISR 제외 ≠ replica 삭제: follower log와 assignment는 남고 catch-up 후 재진입할 수 있다.
  • Controller ≠ data leader: controller는 metadata control path, partition leader는 record data path를 담당한다.
  • Leader LEO ≠ consumer visibility: 복제 안전 경계 HW를 구분해야 한다.
  • ISR 모델만으로 4.x 선출을 단정 금지: ELR 활성화 여부와 metadata를 확인한다.

9. 대기업 기술 면접 질문 3개

Q1. Kafka replication data path를 설명하세요.
좋은 답변 구조: partition leader가 ordering 소유 → producer는 leader에 batch write → follower가 next offset으로 pull → local append·LEO 보고 → ISR commit/HW → ack·consumer visibility → network/disk 병목과 batching 비용.

Q2. RF=3인데 ISR=2입니다. 데이터가 유실된 건가요?
좋은 답변 구조: assignment와 runtime state 구분 → 즉시 유실 단정 금지 → leader/ISR/LEO·HW·lag·controller event 수집 → broker/disk/network/GC 가설 → min ISR·acks에 따른 write 결과 → follower 안전 복구 → unclean election 금지.

Q3. 3 replicas로 broker 한 대 장애를 견디는 설계를 하세요.
좋은 답변 구조: failure domain/AZ 가정 → RF3 rack-aware 배치 → acks=all·min ISR2 → 정상/1대/2대 장애 표 → durability와 write availability trade-off → 장애 시 headroom·catch-up throttle → Kafka 4.x ELR 설정 확인.
