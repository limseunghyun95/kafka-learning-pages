한 줄 요약
느린 consumer는 단순히 lag만 늘리는 것이 아니다. 처리 지연이 max.poll.interval.ms를 넘으면 소유권을 잃고, 재할당·cache cold start·중복 처리 비용이 다시 처리를 늦추는 rebalance storm으로 증폭될 수 있다.

1. 선수 용어 사전

Slow consumer입력 도착률보다 처리율이 낮거나, 한 번의 poll() 뒤 처리가 너무 길어 다음 poll을 제때 호출하지 못하는 consumer. 원인은 DB lock, 외부 API, GC, CPU throttling, 큰 batch 등 다양하다.
LagPartition의 log end offset과 consumer가 처리·commit한 offset 사이 차이. “대기 record 수”에 가깝고 시간 지연이나 업무 성공을 직접 뜻하지 않는다.
Poll looppoll → 처리 → commit → poll의 반복. Java consumer의 업무 진척을 나타내며 consumer 객체는 thread-safe하지 않다.
max.poll.interval.msConsumer group을 쓸 때 두 poll() 호출 사이에 허용되는 최대 시간. Kafka 4.3 기본값은 5분이며, 넘으면 처리 불능 member로 판단해 재할당을 시작한다.
Heartbeat / sessionCoordinator에게 process 통신 생존을 알리는 control path와 그 유효 시간. Heartbeat가 살아 있어도 application processing은 멈출 수 있다.
RebalanceGroup membership 또는 subscription 변화에 맞춰 partition ownership을 다시 계산·전달하는 상태 전이. 정상 기능이지만 너무 자주 발생하면 처리 중단 비용이 된다.
Rebalance stormMember join·leave·timeout이 연속되어 group이 안정 상태에 머무르지 못하는 현상. 공식 고유 오류명이 아니라 운영 현상을 부르는 말이다.
BackpressureDownstream이 느릴 때 upstream 유입을 pause·제한해 bounded queue와 처리 안전성을 지키는 역압. 무한 queue는 backpressure가 아니라 장애 지연이다.
Assignment epoch누가 어떤 partition을 소유하는지 나타내는 세대 정보. 오래된 owner가 commit하거나 계속 쓰지 못하도록 fencing하는 기준이다.

2. 왜 중요한가

입력률을 λ, group의 지속 처리율을 μ라 하면 λ > μ인 동안 lag는 대략 (λ-μ)×시간만큼 증가한다. 하지만 실무 장애는 여기서 끝나지 않는다. 느린 member가 max poll을 넘으면 partition이 이동하고, 새 owner는 connection·cache·state를 다시 데우며, 처리 중이던 record는 중복될 수 있다. 이 추가 비용이 μ를 더 낮추면 양의 피드백이 생긴다.

대기업 면접에서는 “lag가 높아 consumer를 늘렸다”보다 먼저 lag의 기울기, poll 간격, 처리 latency, member churn, rebalance 시간을 분해해야 한다. Partition 수보다 consumer를 많이 늘리면 idle member만 생기고, scale-out join 자체가 rebalance를 유발해 오히려 복구가 늦어질 수 있다.

오늘 실험의 성공 기준은 오류 로그를 한 번 보는 것이 아니다. 정상 상태의 owner·lag를 기준선으로 남기고, 실패 주입 뒤 member ID·assignment·group state가 반복 변화하는 증거를 모은 다음, 안전한 완화로 group이 다시 안정되고 lag 기울기가 음수가 되는지 확인하는 것이다.

상태의 소유자: Consumer application은 처리 중 record와 완료 frontier를 소유한다. Consumer client는 마지막 poll 시각·subscription·현재 assignment를 안다. Group coordinator는 member identity·group epoch/generation·target/current assignment를 소유한다. Partition leader는 log end와 fetch data를 소유한다.

핵심 불변식: 한 partition은 같은 group의 active owner 둘에게 동시에 처리 권한이 있어서는 안 된다. Offset은 연속 완료된 record 다음 위치까지만 commit해야 한다. Group epoch가 바뀐 뒤 old owner의 늦은 commit은 성공으로 간주하면 안 된다.

처리 예산을 수치로 잡기

한 poll의 record 수가 R, record당 p99 처리 시간이 S, 직렬 처리라면 거친 batch 시간은 R×S다. 여기에 bounded retry, commit, GC·scheduler pause, rebalance callback 시간을 더한다. 예를 들어 R=200, S=120ms면 처리만 24초다. Retry 8초, commit 1초, 40% headroom을 더하면 약 46초다.

Timeout을 10분으로 늘리면 경고는 사라질 수 있지만 owner failover도 늦어진다. 먼저 max.poll.records 축소, 처리 latency 원인 제거, bounded worker queue, pause()/resume(), 완료 순서를 보장하는 commit frontier를 검토한다. Worker를 늘려도 같은 consumer 객체를 여러 thread에서 호출하면 안 된다.

Classic과 Consumer protocol의 차이

Kafka 4.3 client 기본 group.protocol은 여전히 classic이다. Classic에서는 client의 heartbeat.interval.ms와 session.timeout.ms가 적용된다. group.protocol=consumer를 켜면 heartbeat·session은 broker의 group.consumer.heartbeat.interval.ms와 group.consumer.session.timeout.ms가 통제하고, global barrier 없는 incremental reconciliation을 사용한다.

새 protocol은 storm의 blast radius와 안정화 시간을 줄일 수 있지만 느린 business logic을 치료하지 않는다. max.poll.interval.ms와 bounded processing 문제는 여전히 남고, member가 반복 재시작하면 epoch churn·partition 이동·중복 처리 비용도 남는다.

성공 확정 시점과 failure window

  • poll 반환: Record가 처리됐다는 뜻이 아니라 client memory로 전달됐다는 뜻이다.
  • 외부 처리 성공: Side effect가 끝났지만 offset commit 전 crash하면 같은 record가 다시 올 수 있다.
  • commit 성공: 해당 group의 재시작 위치가 전진했다. 외부 시스템의 transaction과 자동 원자화되지는 않는다.
  • max poll 초과: Ownership은 바뀔 수 있지만 old worker가 이미 시작한 DB write는 자동 취소되지 않는다.
  • 복구 성공: Group이 Stable에 머물고 rebalance rate가 정상화되며, 처리율이 입력률보다 커져 lag 기울기가 지속적으로 내려갈 때다.

7. 20~40분 실습: slow poll → 반복 재가입 → storm

실패 주입 원리: Console consumer의 큰 stdout record를 아주 느린 pipe reader가 받게 해 poll thread를 막는다. max.poll.interval.ms=8000을 넘겨 member를 잃게 하고, outer loop가 process를 다시 시작해 반복 join/leave를 만든다. 운영 코드를 흉내 낸 인위적 실험이며 production 설정값이 아니다.

사전 조건: 저장소 root, Docker 실행, 이 저장소의 Apache Kafka 4.3.1 단일 broker KRaft compose 환경, Terminal 4개. 예상 시간 30~35분, 생성 데이터 약 24MiB.

0) 실행 전 예측

  1. Heartbeat thread가 살아 있어도 stdout 처리 때문에 다음 poll이 12초 늦으면 8초 max poll 판정은 어떻게 될까?
  2. Slow member ID가 매번 바뀌면 assignment와 lag는 어떤 패턴을 보일까?
  3. max.poll.records=1로도 실패한다면 batch 크기 외에 무엇이 병목이라는 뜻일까?

1) Topic과 backlog 준비

docker compose up -d
docker compose exec broker bash -lc 'bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --if-not-exists --topic day34-storm --partitions 4 --replication-factor 1'
python3 -c 'import sys; [sys.stdout.write("x"*262144+"\n") for _ in range(96)]' | docker compose exec -T broker bash -lc 'bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic day34-storm'

예상: 256KiB record 96개가 4 partitions에 쌓인다. Topic 최대 record 크기 기본 범위 안이지만 환경별 제한이 다르면 아래 오류 표를 확인한다.

2) Terminal A: 의도적으로 느린 consumer를 재시작 loop로 실행

while true; do
  docker compose exec -T broker bash -lc 'bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic day34-storm --group day34-lab --from-beginning --consumer-property group.protocol=classic --consumer-property client.id=day34-slow --consumer-property max.poll.interval.ms=8000 --consumer-property session.timeout.ms=12000 --consumer-property heartbeat.interval.ms=3000 --consumer-property max.poll.records=1 --property print.value=true' |
  while IFS= read -r record; do sleep 12; done
  sleep 1
done

첫 record의 큰 value는 pipe reader가 읽고 12초 쉰다. 다음 출력이 pipe에서 막혀 consumer의 poll loop가 8초 제한을 넘는다. Terminal A 로그에서 “time between subsequent calls to poll” 또는 group membership 상실 계열 메시지를 찾는다.

3) Terminal B: 정상 consumer 추가

docker compose exec -T broker bash -lc 'bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic day34-storm --group day34-lab --from-beginning --consumer-property group.protocol=classic --consumer-property client.id=day34-fast --consumer-property max.poll.interval.ms=300000 --property print.value=false' >/dev/null

예상: Slow member의 join·timeout·재시작 때마다 fast member의 assignment가 흔들린다. Record를 모두 소비하면 현상이 약해질 수 있으므로 관찰은 바로 시작한다.

4) Terminal C: state·members·lag를 한 timeline으로 수집

for i in $(seq 1 15); do
  date '+%H:%M:%S'
  docker compose exec broker bash -lc 'bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group day34-lab --state'
  docker compose exec broker bash -lc 'bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group day34-lab --members --verbose'
  docker compose exec broker bash -lc 'bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group day34-lab'
  sleep 3
done

관찰 포인트: (1) slow consumer ID가 바뀌는가, (2) member 수와 assignment가 반복 변하는가, (3) Stable 조회 사이에 rebalance 경고가 나타나는가, (4) lag가 줄다가 ownership 이동 때 정체·반등하는가. 단일 snapshot보다 시간축 변화가 증거다.

5) 안전한 첫 조치와 복구 검증

Terminal A에서 Ctrl-C로 slow restart loop만 중단한다. Fast consumer는 유지하고 Terminal C 관찰 명령을 다시 5회 실행한다.

복구 판정: Member ID·assignment가 더 이상 흔들리지 않고 group이 Stable에 머문다. Fast consumer의 처리율이 입력률보다 크면 lag가 0 방향으로 내려간다. 이 순서는 장애 member만 격리해 blast radius를 줄이는 production runbook과 같다.

6) 자주 나는 오류와 해결

RecordTooLargeExceptionPayload를 131072자로 낮춘다. Broker/topic 최대 message 설정을 임의로 키우기 전에 현재 값을 확인한다.
Slow consumer가 안 느려짐print.value=true와 256KiB payload인지 확인한다. Pipe buffer가 충분히 크면 payload 수를 늘리거나 sleep을 20초로 올린다.
GROUP_ID_NOT_FOUNDA/B consumer가 아직 join하지 않았거나 이미 끝났다. Terminal 로그와 group 이름을 확인한다.
Lag가 너무 빨리 0실험용 새 group 이름으로 다시 시작하고 A를 먼저 실행한다. 필요한 경우 backlog를 한 번 더 produce한다.
설정 오류이 랩은 Classic protocol을 명시한다. Consumer protocol에서는 client heartbeat/session 설정이 지원되지 않는다.

8. 놓치기 쉬운 함정

  • Lag 0 ≠ 성공: Offset만 앞서가고 외부 side effect가 실패했을 수 있다.
  • Heartbeat 정상 ≠ poll 정상: Control path와 application progress는 별도 clock이다.
  • Consumer 추가 ≠ 처리량 증가: Partition 수와 downstream 용량이 상한이다.
  • Timeout 증가 ≠ 원인 해결: 장애 판정과 failover만 늦출 수 있다.
  • pause ≠ heartbeat 중단: Pause는 fetch 반환을 제어하며 poll은 계속 호출해야 한다.
  • Cooperative ≠ 무중단: 이동 partition·callback·반복 churn 비용은 남는다.
  • Commit 최고 offset 함정: 병렬 처리에서 앞 record 미완료인데 뒤 offset을 commit하면 재시작 시 유실된다.
  • 실험의 stdout 병목: 오늘은 downstream blocking을 재현하기 위한 장치다. 실제 원인은 DB·API·CPU·GC일 수 있다.

9. 대기업 기술 면접 질문

Q1. Lag가 급증하고 rebalance가 반복될 때 10분 안에 무엇을 보겠는가?

좋은 답변 구조: SLO·영향 범위 → lag 기울기와 입력/처리율 → poll/heartbeat 분리 → group state·member churn → downstream·GC·CPU 증거 → 배포/scale 중지와 문제 member 격리 → rollback·복구 판정 순서로 답한다.

Q2. max.poll.interval.ms를 5분에서 30분으로 늘리자는 제안을 평가하라.

좋은 답변 구조: Batch p99 수치와 bounded retry 예산 → 30분 동안 잘못된 ownership을 유지하는 비용 → max.poll.records·pause/resume·worker queue 대안 → static/dynamic 차이 → 부하·failure injection으로 timeout과 RTO를 함께 검증한다.

Q3. 24 partitions, 입력 12k records/s, consumer 한 대 처리율 1.5k/s에서 확장 전략은?

좋은 답변 구조: 최소 8대 계산 후 headroom 가정 → 24 partition 병렬성 상한 → shared DB pool·network 용량 확인 → scale step/cooldown과 rebalance 비용 → lag time 환산 → 실패 시 stable replica 수로 rollback까지 제시한다.

10. 복습과 정답

어제 내용 회상 3문제

  1. Transaction coordinator와 partition leader가 각각 소유하는 상태는 무엇인가?
  2. HW가 전진했는데 read_committed consumer가 뒤 record를 못 읽는 이유는?
  3. commitTransaction() timeout 때 즉시 abort하면 안 되는 이유는?
어제 정답/채점: ① Coordinator는 transactional.id별 PID/epoch·상태·참여 partition·결정, leader는 data/control batch와 marker·aborted index(3점). ② 첫 open transaction 앞 LSO에서 가시성이 막히기 때문(2점). ③ Commit이 broker에서 이미 진행됐으나 응답만 유실된 unknown outcome일 수 있어 같은 commit retry 또는 producer close가 안전함(3점).

오늘 확인 문제 3개

  1. Heartbeat가 정상인 slow consumer도 왜 group에서 제외될 수 있는가?
  2. Rebalance storm의 양의 피드백 고리를 네 단계로 설명하라.
  3. Lag 급증 때 consumer 증설 전에 확인할 세 가지 상한은?
오늘 정답/채점: ① Process session이 아니라 application의 poll progress가 max poll을 넘었기 때문(2점). ② 처리 지연→max poll 초과/ownership 이동→rebalance·warm-up·중복 비용→실효 처리율 저하와 재가입 반복(3점). ③ Partition 수, consumer당 실제 처리율, DB/API/CPU/network 같은 shared downstream 용량(3점). 총 8점 중 6점 이상이면 통과.
