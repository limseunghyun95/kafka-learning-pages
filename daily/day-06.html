한 줄 요약
같은 topic을 읽어도 group이 다르면 각자 독립된 committed offset을 갖는다. 따라서 한 group만 멈추고 offset을 과거로 옮기면 그 group만 record를 다시 읽지만, 이미 실행한 DB write·메일·결제 같은 외부 side effect는 Kafka가 되돌리지 않는다.

1. 선수 용어 사전

Replay보존된 record를 과거 위치부터 다시 읽고 처리하는 것. 삭제 데이터 복구가 아니라 consumer의 읽기 위치 변경이다.
Committed offsetgroup이 partition별로 저장한 다음 재개 위치. “업무 처리가 확정됐다”는 보편적 증명이 아니라 consumer가 남긴 checkpoint다.
Fetch position살아 있는 consumer가 메모리에서 유지하는 다음 fetch 위치. committed offset보다 앞설 수 있고 process 종료 시 사라진다.
Consumer group같은 group.id로 partition을 분담하고 offset을 공유하는 논리적 구독자. group ID가 다르면 같은 record를 독립적으로 읽는다.
Group coordinatorgroup membership·assignment·offset commit 요청을 중재하는 broker 역할. record payload를 대신 운반하지는 않는다.
Dry run / Executedry run은 변경할 offset 계획만 보여주고, --execute는 실제 group offset을 쓴다. 안전한 replay는 계획과 실행을 분리한다.
Retentionbroker가 record를 보관하는 정책. offset을 0으로 지정해도 retention으로 지워진 record는 되살아나지 않는다.
Idempotency같은 작업을 여러 번 적용해도 최종 결과가 한 번 적용한 것과 같은 성질. replay 가능한 sink의 핵심 안전장치다.
Side effectDB 변경, 결제, 알림처럼 process 밖 상태를 바꾸는 효과. Kafka offset reset은 이를 자동 rollback하지 않는다.

2. 왜 중요한가

실무에서 replay는 버그 수정 후 재계산, 누락 데이터 복구, 새 sink backfill에 사용한다. 이때 “offset만 되돌리면 된다”는 생각은 위험하다. 어느 group·topic·partition·시간 범위를 바꿀지, 대상 record가 아직 보존되는지, 두 번째 처리가 sink에서 안전한지를 먼저 답해야 한다.

오늘 실험의 핵심은 로그 상태와 소비 상태를 분리하는 것이다. topic의 record는 그대로인데 primary group의 checkpoint만 뒤로 이동한다. audit group의 checkpoint는 바뀌지 않는다. 이 분리를 설명할 수 있어야 replay를 운영 변경으로 안전하게 승인할 수 있다.

4. CS 내부 동작: 상태 소유권·불변식·실패 창

상태소유자불변식·성공 확정 시점
Partition logleader broker와 replicapartition 안 offset은 append 순서로 증가한다. reset은 log bytes를 바꾸지 않는다.
Group offset A/B각 group coordinator-backed state같은 TopicPartition이라도 group ID가 다르면 독립 key다. reset 성공 응답은 해당 checkpoint 변경 확정이다.
Fetch positionconsumer process memory활성 consumer는 이미 옛 position을 사용 중일 수 있어 reset 전에 inactive 상태가 필요하다.
Business effectDB·API·object storeoffset commit과 외부 write는 기본적으로 원자적이지 않다. sink 확인까지가 end-to-end 성공이다.

Offset은 전역 번호가 아니라 복합 key의 값

개념적으로 checkpoint는 (group.id, topic, partition) → next offset mapping이다. 그래서 Group A의 P1 offset을 7에서 0으로 바꿔도 Group B의 P1 offset과 partition log의 LEO(Log End Offset, 로그 끝 위치)는 바뀌지 않는다. 이 key space 분리가 fan-out과 독립 replay를 가능하게 한다.

Replay의 state transition

Stable(active) → Empty(inactive) → reset plan → offset write → consumer join → Stable → fetch from new offset 순서다. 활성 member가 있는 채로 관리 도구와 application이 동시에 offset을 다루면 관리자가 예상한 checkpoint와 consumer의 in-memory position·후속 commit이 경합할 수 있다. Kafka 공식 운영 문서도 reset 전에 consumer instance를 inactive로 만들라고 요구한다.

가장 위험한 failure window

sink write 성공 → offset commit 전 crash 구간에서 이미 중복 가능성이 생긴다. replay는 의도적으로 같은 record를 더 넓은 범위에서 다시 처리하므로 이 창을 확대한다. event ID를 unique key로 upsert하거나 inbox dedup table을 두지 않으면 결제·메일처럼 되돌리기 어려운 부작용이 반복될 수 있다.

5. 실무 설계 판단

어디까지 replay할까?topic·partition·start/end offset 또는 UTC 시간 범위를 승인 문서에 고정“earliest 전체”는 비용과 중복 부작용을 불필요하게 키운다.

용량은 얼마나 필요한가?replay rate ≤ min(Kafka read headroom, sink spare capacity)무제한 replay는 production consumer와 broker page cache·network·sink를 경쟁한다.

Best Practice

  • 변경 전 current offset을 --to-current --export 또는 describe 결과로 보관해 rollback 좌표를 남긴다.
  • 대상 group을 완전히 정지하고 state가 inactive인지 확인한 뒤 기본 plan 출력을 검토하고 --execute한다.
  • replay 전 event ID 기반 idempotent upsert·dedup·dry-run sink를 검증하고 알림·결제 같은 비가역 side effect를 차단한다.
  • 속도 제한, 종료 offset, 예상 건수, 담당자, 중단 조건, rollback offset을 runbook에 기록한다.
  • 다른 group의 offset snapshot도 남겨 isolation 증거로 사용하되 변경 대상에는 포함하지 않는다.

Anti-pattern·edge case·버전 경계

  • Anti-pattern: 활성 consumer가 있는데 reset을 강행한다. in-memory position과 후속 commit 때문에 결과를 예측하기 어렵다.
  • Anti-pattern: 검증 없이 --all-topics --to-earliest --execute한다. 무관한 topic과 오래된 side effect까지 재실행할 수 있다.
  • Edge case: 요청 offset이 retention 시작점보다 과거면 사라진 record는 읽지 못하며 도구가 사용 가능한 경계로 조정할 수 있다.
  • Edge case: timestamp reset은 event-time 업무 경계와 같지 않을 수 있다. producer/broker timestamp 정책과 partition별 timestamp index 결과를 확인한다.
  • Engine 차이: 이 랩은 일반 consumer group 도구다. Kafka Streams는 internal topic과 local state store까지 있으므로 전용 application reset 절차가 필요하다.

7. 35분 통합 랩: 두 group의 isolation과 replay

사전 조건: 저장소 루트, Docker, 터미널 3개. 먼저 예상한다. 12개 record를 Group A와 B가 모두 끝까지 읽은 뒤 A만 earliest로 reset하면 A와 B의 current offset·lag는 각각 어떻게 변할까? A를 재시작했을 때 어느 group만 12개를 다시 출력할까?

1단계 · 3-partition topic과 12개 record

make up

docker compose exec broker /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --create \
  --topic day06-replay --partitions 3 --replication-factor 1

seq 1 12 | sed 's/^/event-/' | \
docker compose exec -T broker /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic day06-replay

2단계 · 두 group이 같은 log를 각각 완주

터미널 1과 2에서 각각 실행한다. --from-beginning은 committed offset이 없는 첫 실행의 시작 위치를 지정한다.

# 터미널 1: Group A
docker compose exec broker /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic day06-replay \
  --group day06-primary --from-beginning \
  --property print.partition=true --property print.offset=true \
  --max-messages 12

# 터미널 2: Group B
docker compose exec broker /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic day06-replay \
  --group day06-audit --from-beginning \
  --property print.partition=true --property print.offset=true \
  --max-messages 12

예상 관찰: 두 출력 모두 총 12개다. partition 사이의 출력 순서는 다를 수 있지만 각 partition 안 offset은 증가한다. 두 process가 끝났으므로 reset 가능한 inactive 상태가 된다.

3단계 · 두 checkpoint snapshot

for g in day06-primary day06-audit; do
  docker compose exec broker /opt/kafka/bin/kafka-consumer-groups.sh \
    --bootstrap-server localhost:9092 --describe --group "$g"
done

partition별 CURRENT-OFFSET과 LOG-END-OFFSET이 같고 lag이 0인지 확인한다. partition별 record 수는 고르지 않을 수 있으므로 offset 숫자가 모두 4일 필요는 없다.

4단계 · 실패 주입: Group A만 reset 계획 후 실행

# --execute가 없으므로 변경 없는 plan 출력
docker compose exec broker /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --group day06-primary \
  --topic day06-replay --reset-offsets --to-earliest

# NEW-OFFSET이 예상과 같을 때 한 번만 실행
docker compose exec broker /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --group day06-primary \
  --topic day06-replay --reset-offsets --to-earliest --execute

예상: Group A의 세 partition NEW-OFFSET만 earliest로 이동한다. 다시 두 group을 describe하면 A는 lag이 약 12로 늘고 B는 lag 0을 유지한다. 이 차이가 group isolation의 증거다.

5단계 · A만 replay하고 종료 조건 확인

docker compose exec broker /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic day06-replay \
  --group day06-primary \
  --property print.partition=true --property print.offset=true \
  --max-messages 12

예상: A에서 12개가 다시 보이고 B는 실행하지 않았으므로 아무것도 재처리하지 않는다. A/B를 describe해 모두 lag 0이면 Kafka checkpoint 관점의 실험은 성공이다. 실무에서는 sink의 expected ID·건수·중복도까지 대조해야 완료다.

자주 나는 오류와 해결

  • Assignments can only be reset if the group is inactive: 해당 group consumer를 모두 종료하고 state/member를 확인한다.
  • 두 번째 실행이 12개 전에 멈춘다: 최초 실행의 auto commit이 늦었을 수 있다. group describe로 committed offset을 확인하고 같은 실행에서 reset을 반복하지 않는다.
  • GROUP_ID_NOT_FOUND: 먼저 해당 group으로 한 번 소비해 offset state를 만든다.
  • earliest가 0이 아니다: retention이나 log start offset 이동 가능성을 확인한다. 삭제된 record는 replay할 수 없다.
  • 다른 group lag도 변했다: command의 --group과 관찰 대상 group ID를 다시 대조한다. topic LEO 변화와 group current offset 변화를 혼동하지 않는다.

Cleanup

docker compose exec broker /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --delete \
  --group day06-primary --group day06-audit

docker compose exec broker /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --delete --topic day06-replay

8. 놓치기 쉬운 함정

  • reset = 데이터 복원: reset은 pointer 변경이다. retention으로 사라진 bytes는 복원하지 못한다.
  • replay = exactly-once: 동일 record를 다시 읽는 것이므로 오히려 sink idempotency를 더 강하게 요구한다.
  • lag = 처리 실패 수: lag은 log end와 committed checkpoint 차이다. sink 실패·선 commit은 별도 증거가 필요하다.
  • 다른 group도 영향: topic load는 공유하지만 offset state는 group별이다. 논리 상태 영향과 resource 영향은 구분한다.
  • earliest = offset 0: 현재 보존된 log start offset이며 항상 0이라는 보장은 없다.
  • 12개가 partition당 4개: key 없는 producer의 분배와 batching 때문에 정확한 균등 분포를 전제로 하면 안 된다.

9. 대기업 기술 면접 질문

  1. 같은 topic을 서비스와 감사 시스템이 읽을 때 왜 group ID를 분리하는가?
    좋은 답은 요구사항부터 분리하고 (group, topic, partition) offset key, 독립 assignment/fetch, shared broker resource를 설명한다. 한쪽 장애·replay가 다른 쪽 checkpoint에는 영향 없지만 network·disk에는 간접 영향이 있다는 trade-off까지 말한다.
  2. 운영 데이터 3일치를 안전하게 replay하는 절차를 설계하라.
    건수·bytes·retention·sink spare capacity를 수치화하고 범위 snapshot, inactive 확인, dry run, idempotency, rate limit, 종료 offset, 검증 checksum, rollback plan 순서로 답한다. 별도 group/격리 sink 대안도 비교한다.
  3. Kafka가 exactly-once를 지원하는데 replay 중복 결제가 왜 생길 수 있는가?
    Kafka transaction의 원자성 범위와 외부 결제 API의 transaction domain을 구분한다. producer/offset transaction만으로 외부 side effect가 원자화되지 않는 failure window를 그리고 idempotency key, inbox, 보상 transaction 대안을 제시한다.

10. 복습과 정답

어제 내용 회상 3문제

  1. partition 3개에 같은 group consumer 5개면 유효 owner는 최대 몇 개인가?
  2. group coordinator의 control path와 record fetch data path를 구분하라.
  3. 처리 후 commit 전 crash가 만드는 delivery semantics는 무엇인가?

채점 기준: ① 최대 3개와 2개 idle, ② membership·assignment·offset 대 consumer↔partition leader fetch, ③ 이미 처리한 record를 재개 위치부터 다시 읽는 at-least-once 중복 창을 말하면 통과.

오늘 내용 확인 3문제

  1. Group A의 offset reset이 Group B의 offset을 바꾸지 않는 이유는?
  2. reset 전에 consumer를 inactive로 만들고 dry run을 해야 하는 이유는?
  3. Kafka checkpoint replay 성공만으로 업무 복구 완료라 할 수 없는 이유는?

짧은 정답: ① offset key에 group ID가 포함된 독립 상태이기 때문이다. ② 활성 consumer의 position·후속 commit과 경합을 막고 대상 partition·new offset을 실행 전에 검증하기 위해서다. ③ 외부 sink side effect는 별도 transaction domain이며 중복·누락·reject를 ID와 checksum으로 검증해야 하기 때문이다.
