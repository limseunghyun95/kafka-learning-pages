APACHE KAFKA 4.3 · WEEK 2 / DAY 14 · RECALL & TECH REVIEW

“디스크인데 왜 빠른가”
3분 설명

성능을 마법이 아닌 비용 모델·hot/cold path·실패 창으로 방어하기 · 예상 회상 40분 + 실습 30분

한 줄 요약
Kafka가 빠른 이유는 “디스크가 메모리보다 빨라서”가 아니라 partition-local sequential append, record batch로 비용 분할, OS page cache, sparse index, 재사용 가능한 binary batch와 효율적 network path가 작은 random I/O와 byte copy를 줄이기 때문이다.

1. 선수 용어 사전

Locality가까운 주소를 연속 접근하는 성질. 디스크 seek, CPU cache miss, page fault를 줄이는 출발점이다.
Sequential append현재 active segment의 끝에 연속해서 쓰는 패턴. “Kafka의 모든 I/O가 항상 순차”라는 뜻은 아니다.
Syscallapplication이 kernel에 read·write·send 같은 작업을 요청하는 경계. 호출과 context 전환에도 고정 비용이 든다.
Page cacheOS가 file의 page를 RAM에 보관하는 통합 cache. write가 먼저 cache에 반영될 수 있으므로 page cache 도착과 물리 매체 영속화는 다르다.
Writeback / fsyncwriteback은 dirty page를 저장장치로 내리는 과정, fsync는 application이 그 완료를 명시적으로 요구하는 syscall이다.
Record batch여러 record를 header 하나와 함께 묶는 protocol·append·compression 단위. Kafka 성능 설명의 실제 단위다.
Amortization요청·header·syscall 같은 고정 비용을 여러 record가 나눠 내는 것. batch가 커질수록 record당 비용은 낮아지지만 대기시간은 늘 수 있다.
Sparse index모든 record가 아니라 일정 byte 간격마다 offset→file position 표식을 두는 작은 색인. 근처로 점프한 뒤 batch를 순차 scan한다.
mmapfile을 process 가상 주소 공간에 매핑해 OS page 단위로 접근하는 방식. index lookup이 일반 heap object tree일 필요를 줄인다.
Zero-copy / sendfilefile page를 application user buffer로 다시 복사하지 않고 socket으로 보내는 최적화 경로. copy가 문자 그대로 0회라는 뜻은 아니다.
Hot / cold pathhot은 필요한 page가 RAM cache에 있는 경로, cold는 storage read·page fault가 필요한 경로다. 평균 성능만 보면 cold tail을 놓친다.
Throughput / p99throughput은 단위시간 처리량, p99는 요청 99%가 그 이하에 끝나는 지연. 높은 처리량과 낮은 tail latency는 같은 목표가 아니다.

2. 왜 중요한가

면접에서 “Kafka는 sequential I/O와 zero-copy를 써서 빠릅니다”만 말하면 키워드 암기다. 강한 답은 어떤 비용이 사라지고, 어느 상태가 RAM·kernel·disk·replica에 있으며, 성공 응답은 무엇을 보장하고, TLS·cold cache·작은 batch에서 왜 경로가 달라지는지까지 설명한다.

실무에서도 이 모델은 튜닝 순서를 바꾼다. 처리량이 낮다고 바로 disk를 교체하지 않고 batch fill ratio·request rate·compression ratio·network·page cache hit 가능성·partition skew를 먼저 본다. p99가 튀면 평균 throughput과 분리해 cold read, page reclaim, flush storm, TLS CPU, broker queue를 증거로 좁힌다.

3. Architecture: 한 batch의 빠른 경로

1 · Producer같은 partition의 record를 accumulator에서 batch로 묶고 압축
↓ persistent TCP · ProduceRequest · partition leader로 직접 routing
2 · Leaderbatch 검증 → active .log 끝에 append → partition offset 부여
↓ write syscall → kernel page cache의 dirty page
3 · Replicationfollower fetch·append → 설정된 acks와 ISR 조건 만족
↓ ProduceResponse · ack와 개별 fsync 완료를 혼동하지 않기
4 · Lookupsparse offset index로 target 근처 file position → batch scan
↓ caught-up consumer라면 page cache hit 가능
5 · Fetch저장된 binary batch를 FetchResponse로 전송; 가능한 경로에서 sendfile 활용
TLS·변환·cold cache·tiny batch → fast path 일부 이탈 → CPU·I/O·p99 비용 증가

요청·응답을 시간순으로 읽기: ① producer는 metadata로 leader를 찾고 batch를 보낸다. ② leader는 batch를 검증하고 partition log에 append한다. ③ follower가 leader를 pull하여 복제하고 ack 정책이 충족되면 client 성공이 확정된다. ④ consumer는 offset을 넣어 fetch하며 index가 근처로 안내한다. ⑤ broker는 log와 같은 batch format을 가능한 한 재사용해 전송하고 consumer가 압축을 해제한다.

4. CS 내부 동작: 3분 답변의 여섯 문장

  1. Locality: partition leader는 active segment 끝에 append하여 random overwrite와 tree update를 피한다.
  2. Amortization: producer가 record를 batch로 묶어 request round trip, header, checksum, syscall 비용을 여러 record에 분산한다.
  3. Compression: 비슷한 record를 함께 압축하면 network·disk byte가 감소하며 compressed batch는 log와 fetch 경로에서 유지될 수 있다.
  4. OS cache: broker heap에 record object cache를 복제하기보다 filesystem과 page cache를 사용해 RAM을 cache로 활용하고 GC 부담을 피한다.
  5. Index: sparse index가 offset 근처로 점프하게 하고, 마지막 구간은 sequential batch scan으로 확정해 index 크기와 lookup 비용을 trade-off한다.
  6. Network: persistent TCP와 큰 fetch, 공통 binary batch format, 가능한 plaintext 경로의 sendfile이 connection·copy 비용을 줄인다.

Hot path와 cold path

Hot: producer batch가 충분히 차고, leader queue가 짧고, consumer가 head 근처를 읽어 page cache가 warm하며, 큰 fetch와 reusable batch가 작동한다. Cold: 오래된 replay, broker restart 뒤 cache miss, memory reclaim, tiny batch, 작은 fetch, TLS CPU, 압축 해제나 protocol 변환이 겹치면 storage read와 copy·CPU 비용이 p99에 나타난다. 따라서 “평소 디스크 read가 0”인 cluster도 replay 때는 전혀 다른 시스템처럼 보일 수 있다.

Best Practice

  • 성능 목표를 MB/s, records/s, p50/p99, durability, replay RTO로 분리하고 한 설정으로 모두 좋아진다고 가정하지 않는다.
  • 평균 cluster 지표보다 partition별 bytes in/out, request queue, disk latency, CPU, page cache pressure와 batch 지표를 같은 시간축으로 본다.
  • batch·compression 변경은 실제 message size와 key skew를 재현한 canary에서 검증하고 이전 값을 rollback 기준으로 남긴다.
  • live consume와 historical replay capacity를 따로 산정하고 replay rate limit·중단 조건·복구 순서를 runbook에 둔다.
  • application ack, replica ack, OS writeback, consumer 처리 완료를 로그와 dashboard에서 서로 다른 상태로 표시한다.

Anti-pattern·edge case·version 경계

  • Anti-pattern: “디스크가 메모리보다 빠르다.” 정확한 말은 Kafka가 큰 linear I/O와 cache를 활용해 random I/O 비용을 피한다는 것이다.
  • Anti-pattern: flush.messages=1을 durability 만능 설정으로 일괄 적용한다. replica 기반 내구성과 latency·throughput 비용을 함께 설계해야 한다.
  • Edge case: batch가 잘 안 차는 저유량 partition은 설정상 batch.size가 커도 실제 amortization 이익이 작다.
  • Edge case: highly compressed batch는 network를 절약하지만 decompression CPU와 큰 uncompressed working set을 만든다.
  • Edge case: caught-up consumer의 hot read와 오래된 offset replay의 cold read를 같은 benchmark로 일반화하면 안 된다.
  • Version: 이 자료는 Kafka 4.3 문서를 기준으로 한다. sendfile·TLS 경계와 codec·config의 실제 동작은 배포 버전 공식 문서로 재검증한다.

7. 30분 실습: batch와 per-message flush 비용 비교

사전 조건: 저장소 루트, Docker, 약 300MB 여유 공간. 이 실습은 단일 broker 개발 환경의 상대 비교이며 production benchmark가 아니다.

실행 전 예측: 같은 3,000 records라도 batch를 허용한 topic과 매 message flush topic 중 어느 쪽의 elapsed time이 더 길까? 두 topic 모두 record는 남지만 syscall·storage completion 경로에서 어떤 비용 차이가 날까?

1단계 · 두 조건 만들기

make up

docker compose exec broker /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --create \
  --topic day14-fast --partitions 1 --replication-factor 1

docker compose exec broker /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --create \
  --topic day14-flush --partitions 1 --replication-factor 1 \
  --config flush.messages=1

2단계 · 같은 입력을 보내고 시간 기록

time seq 1 3000 | docker compose exec -T broker \
  /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic day14-fast \
  --producer-property batch.size=65536 \
  --producer-property linger.ms=20 \
  --producer-property compression.type=lz4

time seq 1 3000 | docker compose exec -T broker \
  /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic day14-flush \
  --producer-property batch.size=65536 \
  --producer-property linger.ms=20 \
  --producer-property compression.type=lz4

예상 관찰: day14-flush는 message마다 log flush를 요구해 일반적으로 더 느리다. 단, Docker Desktop cache·storage·background load 때문에 한 번의 숫자는 흔들릴 수 있다. 3회 반복 중앙값과 broker disk 지표가 있어야 주장 강도가 올라간다.

3단계 · batch 증거와 실패 주입 확인

docker compose exec broker bash -lc \
  'find /tmp/kraft-combined-logs -path "*day14-fast-0*.log" -print'

docker compose exec broker bash -lc \
  'LOG=$(find /tmp/kraft-combined-logs -path "*day14-fast-0*.log" | head -1); \
  /opt/kafka/bin/kafka-dump-log.sh --files "$LOG" --print-data-log | head -35'

docker compose exec broker /opt/kafka/bin/kafka-configs.sh \
  --bootstrap-server localhost:9092 --entity-type topics \
  --entity-name day14-flush --describe

관찰 포인트: dump에서 여러 record가 같은 batch base offset 아래 묶이는지 보고, flush topic 설정이 실제로 적용됐는지 확인한다. “3,000 write syscall”처럼 command 출력이 증명하지 않은 숫자는 단정하지 않는다.

자주 나는 오류와 해결

  • TopicExistsException: 이전 실습 topic을 cleanup하거나 다른 이름을 사용한다.
  • find 결과 없음: image의 log.dirs를 kafka-configs.sh --describe --entity-type brokers로 확인한다.
  • 두 시간이 비슷함: 3,000건이 너무 작거나 host cache가 지배할 수 있다. 입력을 무한히 키우지 말고 3회 중앙값과 broker 지표를 함께 본다.
  • Broken pipe: head가 dump 출력을 먼저 닫아 생길 수 있으며 broker data 손상은 아니다.
  • flush topic이 더 빠름: 단일 noisy run으로 결론 내리지 말고 config, record count, 반복, background load를 재검증한다.

Cleanup

docker compose exec broker /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --delete \
  --topic day14-fast

docker compose exec broker /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --delete \
  --topic day14-flush

9. 대기업 기술 면접 질문

  1. “Kafka는 디스크 기반인데 왜 빠른가?”를 3분 안에 설명하라.
    좋은 답은 요구사항을 high throughput·bounded latency·durability로 나눈 뒤 sequential append, batching·compression, page cache, sparse index, persistent TCP·sendfile 경로를 data path 순서로 연결한다. 마지막에 ack≠fsync, TLS·cold cache·tiny batch 경계와 측정 지표를 말한다.
  2. 처리량은 같은데 produce p99가 두 배가 됐다. 어떻게 진단할 것인가?
    변경 시점과 partition별 latency를 고정하고 batch fill·request queue·ISR·disk await·CPU/TLS·GC를 같은 시간축으로 수집한다. tiny batch, writeback, replica 지연 가설을 구분하고 traffic shaping·config rollback처럼 안전한 첫 조치를 제시한다.
  3. 초당 20만 records, 평균 500B, p99 50ms인 pipeline의 batch·compression·replay 정책을 설계하라.
    원시 100MB/s와 replication·consumer fan-out을 계산하고 key skew·partition ceiling을 가정한다. linger를 SLO 일부로 배정하고 실제 payload codec benchmark, peak·replay 동시 capacity, TLS CPU, rollback 값을 제시한다. 숫자 없는 “크게 설정”은 불충분하다.

10. 복습과 정답

어제 내용 회상 3문제

  1. segment의 base offset과 record batch의 base offset은 각각 무엇을 찾는 기준인가?
  2. index.interval.bytes를 작게 하면 lookup과 index footprint가 어떻게 바뀌는가?
  3. active segment roll과 OS flush는 왜 같은 state transition이 아닌가?

채점 기준: ① segment 선택용 파일 범위와 batch 내부 offset 기준을 분리, ② 더 촘촘한 entry로 scan은 줄고 index·mmap footprint는 증가, ③ roll은 append target 교체이고 flush는 dirty page 영속화임을 말하면 통과.

오늘 내용 확인 3문제

  1. batching이 network, syscall, compression 세 경로의 비용을 어떻게 줄이는가?
  2. producer ack, page cache write, storage flush, follower replication을 시간순으로 구분하라.
  3. hot consumer에서는 빠르던 fetch가 오래된 replay에서 느려지는 이유와 첫 조치는?

짧은 정답: ① round trip·header·syscall 고정비를 나누고 record 간 중복을 함께 압축한다. ② ack는 설정된 broker/replica 성공 조건이며 cache 반영·물리 flush는 별도 OS 상태다. ③ cold page fault와 disk/cache/network 경쟁 때문이므로 live SLO를 확인하며 replay rate를 먼저 낮춘다.
