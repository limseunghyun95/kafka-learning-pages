APACHE KAFKA 4.3 · WEEK 5 / DAY 33 · TRANSACTION VISIBILITY

transaction coordinator와 read-committed

의사결정 로그·marker·LSO가 만드는 원자적 가시성 · 이론 85분 + 실습 35분

한 줄 요약
Transaction coordinator는 transactional.id별 상태와 commit/abort 결정을 기록하고 각 partition에 control marker를 전파한다. read_committed consumer는 HW가 아니라 LSO까지만 읽고 abort된 batch를 건너뛰어, 여러 Kafka partition의 결과를 “전부 보이거나 전부 안 보이게” 만든다.

1. 선수 용어 사전

Transaction여러 작업을 하나의 논리 단위로 묶어 모두 commit하거나 모두 abort하는 경계. Kafka에서는 여러 topic-partition의 record와 consumer offset을 묶을 수 있다.
Atomicity중간 일부만 성공한 상태를 관찰자에게 노출하지 않는 성질. “all or nothing”이라고 부르지만 실제로는 참여 시스템과 읽기 격리 수준의 범위가 중요하다.
transactional.idApplication이 안정적으로 부여하는 producer 논리 신원. 재시작을 넘어 이전 session의 미완료 transaction을 정리하고 zombie producer를 fence하는 기준이다.
PID / producer epochBroker가 부여하는 producer ID와 그 세대 번호. 같은 PID라도 오래된 epoch의 write를 거부해 이전 instance를 무효화한다.
Transaction coordinatortransactional.id를 hash해 선택되는 broker 역할. 상태 전이, timeout, 참여 partitions, commit/abort marker 전파를 조정한다.
__transaction_stateTransaction metadata를 복제·compact해 보관하는 내부 topic. Coordinator가 바뀌어도 의사결정과 epoch를 복구하는 source of truth다.
Control marker각 data partition log에 append되는 COMMIT/ABORT 제어 record. 일반 application record가 아니며 transaction의 가시성 끝을 표시한다.
HWHigh Watermark. ISR에 충분히 복제되어 일반 consumer가 안전하게 읽을 수 있는 복제 경계.
LSOLast Stable Offset. 첫 open transaction 앞까지의 안정된 읽기 경계. Kafka 문서 정의상 첫 open transaction offset의 바로 전 위치이며 보통 LSO ≤ HW다.
isolation.levelConsumer가 transactional record를 어느 수준으로 볼지 정하는 설정. 기본은 read_uncommitted, 원자적 결과를 보려면 read_committed다.
Fencing동일 logical identity의 오래된 producer가 더 이상 append나 transaction 결정을 하지 못하도록 epoch로 거부하는 안전장치.

2. 왜 중요한가

주문 하나를 validated-orders와 billing-events 두 topic에 쓴다고 하자. 첫 topic write 뒤 process가 죽으면 단순 producer는 한쪽만 남길 수 있다. Transaction은 두 partition의 record를 먼저 물리적으로 append하되, commit 결정과 marker가 끝나기 전까지 read_committed reader에게 숨긴다.

Consume-transform-produce에서는 output record뿐 아니라 “다음에 읽을 input offset”도 같은 transaction에 넣는다. Commit되면 output과 offset이 함께 전진하고, abort되면 둘 다 보이지 않아 input을 다시 처리한다. 여기서도 외부 DB·결제 API는 Kafka transaction domain 밖이다.

면접에서 좋은 답은 “transactional.id를 설정하면 exactly-once”가 아니다. Coordinator의 상태 소유권, log에 이미 존재하지만 아직 보이지 않는 record, HW와 LSO, marker 전파, timeout의 unknown outcome, downstream isolation 조건을 순서대로 방어해야 한다.

상태의 소유자: Producer는 application 경계와 local in-flight sends를 안다. Coordinator는 transactional.id→PID/epoch·timeout·참여 partitions·결정을 소유한다. Partition leader는 실제 data/control batch와 aborted transaction index를 소유한다. Consumer는 isolation 설정과 현재 LSO까지만 반환할 책임이 있다.

4. CS 내부 동작

Transaction state machine과 불변식

상태의미안전 조건
Empty초기화됐고 open transaction 없음현재 PID/epoch만 새 txn 시작 가능
Ongoing첫 partition 등록 뒤 참여 집합이 생김해당 epoch의 batch만 참여
PrepareCommit / PrepareAbort결정이 내구적으로 정해지고 marker 전파 중Commit과 abort를 뒤집지 않음
CompleteCommit / CompleteAbort참여 partitions의 marker 처리 완료다음 transaction과 recovery가 terminal decision을 재사용

핵심 불변식: 같은 transactional.id의 한 epoch만 active writer여야 한다. 한 transaction의 terminal decision은 하나뿐이며, 모든 참여 partition은 결국 같은 COMMIT 또는 ABORT marker를 받아야 한다. Coordinator crash 뒤에도 __transaction_state에서 그 결정을 복구해야 한다.

물리적 append와 논리적 visibility를 분리하라

Transactional data도 일반 record batch처럼 partition log에 먼저 append되고 replica에 복제된다. Abort는 bytes를 지우지 않는다. ABORT marker와 transaction index를 통해 read_committed가 그 범위를 걸러 낸다. 따라서 disk·network 비용은 abort해도 이미 발생했으며, 반복 abort는 저장 공간·replication·fetch metadata 비용을 만든다.

HW는 “충분히 복제됨”을 말하고 LSO는 “transaction 결과가 안정됨”을 말한다. LEO는 local replica의 log 끝이다. 같은 partition에서 일반적으로 LSO ≤ HW ≤ LEO지만 서로 다른 안전 질문에 답한다.

Kafka 4.3의 transaction protocol v2

Kafka 4.0부터 KIP-890의 server-side defense가 기본 활성화된다. transaction.version=2를 사용할 수 있는 4.0+ producer는 transaction마다 producer epoch를 올려 이전 transaction의 늦은 batch가 다음 transaction에 섞이는 것을 더 강하게 막는다. Partition 등록도 server-side path로 단순화된다.

새 transaction이 너무 빨리 시작되어 이전 marker 처리가 끝나지 않았다면 CONCURRENT_TRANSACTIONS를 볼 수 있다. 4.3 broker는 partition 추가 과정에서 일부 retry를 server-side로 수행하므로 produce latency에 대기 시간이 나타날 수 있다. 평균 throughput만 보고 transaction protocol 비용을 놓치면 안 된다.

성공 확정 시점과 unknown outcome

  • send().get() 성공: 개별 batch append/ack의 성공이지 transaction commit이 아니다. read_committed에는 아직 안 보일 수 있다.
  • sendOffsetsToTransaction() 성공: Group coordinator가 offset 요청을 받았다는 뜻이며, transaction이 나중에 commit돼야 offset도 committed가 된다.
  • commitTransaction() 정상 반환: 모든 send가 성공했고 transaction commit이 성공했다. Record callbacks도 완료됐다.
  • commitTransaction() timeout: Broker가 요청을 못 받은 것이 아니라 응답을 제때 못 받은 것일 수 있다. Commit이 진행 중일 수 있으므로 즉시 abort로 방향을 바꾸면 안 된다. 공식 API는 같은 commit을 retry하거나 producer를 닫도록 안내한다.
  • Consumer visibility: 해당 partition에 marker가 반영되어 LSO가 전진한 뒤에야 read_committed poll 결과로 관찰된다.

Kafka→Kafka EOS의 실제 범위

Consume-transform-produce에서는 enable.auto.commit=false로 두고 output records와 ConsumerRecords.nextOffsets()를 같은 producer transaction에 넣는다. Offset은 “마지막 처리 record”가 아니라 다음에 읽을 offset이다. Consumer group metadata까지 전달하면 stale member에 대한 fencing이 더 강해진다.

하지만 HTTP 결제, RDB insert, object storage write는 coordinator의 참여 partition이 아니다. Kafka commit이 DB rollback을 일으키지 못한다. Outbox/inbox, unique event key, conditional update, idempotent API 또는 별도 distributed transaction이 필요하다.

Best practice: Transaction을 business transaction 전체와 동일시하지 말고 Kafka partition/offset 범위를 문서화한다. Canary에서 commit p99·abort rate·HW-LSO gap·restart recovery를 측정하고, transaction ID cardinality가 task 수와 일치하는지 감시한다.

Anti-pattern: 모든 replicas에 같은 transactional.id 사용, 매번 랜덤 ID 사용, read_committed 없이 EOS 주장, output은 transaction인데 input offset은 auto commit, timeout 뒤 commit과 abort를 번갈아 호출, open transaction을 오래 유지해 LSO를 막기.

Engine 차이: Kafka Streams는 processing.guarantee=exactly_once_v2로 task·state store·changelog·offset 흐름을 추상화한다. Plain consumer/producer는 lifecycle과 rebalance fencing을 application이 직접 구현한다. Connect의 EOS 범위도 source/sink connector와 지원 KIP에 따라 다르므로 이름만 보고 동일하다고 가정하지 않는다.

2) Commit transaction 만들기

Kafka 4.3의 producer performance tool은 --transactional-id와 --transaction-duration-ms를 지원하며 내부에서 transaction API를 호출한다.

docker compose exec broker bash -lc 'bin/kafka-producer-perf-test.sh +  --topic day33-txn +  --num-records 6 +  --record-size 16 +  --throughput 2 +  --transactional-id day33-commit +  --transaction-duration-ms 1000 +  --bootstrap-server localhost:9092 +  --command-property acks=all'

예상: Tool이 initTransactions → begin → send → commit을 수행한다. Transaction duration 경계에 따라 내부 transaction 개수는 달라질 수 있지만 6 records는 모두 최종 commit된다.

3) Open transaction 중 process kill

다음 명령은 transaction을 60초간 열어 두도록 낮은 throughput으로 실행한 뒤 3초에 강제 종료한다. Coordinator의 transaction.timeout.ms=10000 뒤 abort 결정을 기다린다.

docker compose exec broker bash -lc '
  ( exec bin/kafka-producer-perf-test.sh +    --topic day33-txn +    --num-records 100 +    --record-size 16 +    --throughput 1 +    --transactional-id day33-crash +    --transaction-duration-ms 60000 +    --bootstrap-server localhost:9092 +    --command-property transaction.timeout.ms=10000 +    --command-property acks=all ) &
  pid=$!
  sleep 3
  kill -9 $pid
  wait $pid || true
'
sleep 12

실패 주입: SIGKILL은 graceful abort 기회를 없앤다. 처음 몇 records는 log에 append됐지만 COMMIT marker는 없다. Coordinator timeout이 ABORT marker를 기록할 때까지 LSO가 그 앞에 머물 수 있다.

docker compose exec broker bash -lc 'bin/kafka-console-consumer.sh +  --bootstrap-server localhost:9092 +  --topic day33-txn +  --from-beginning +  --timeout-ms 5000 +  --property print.offset=true +  --consumer-property isolation.level=read_uncommitted'

docker compose exec broker bash -lc 'bin/kafka-console-consumer.sh +  --bootstrap-server localhost:9092 +  --topic day33-txn +  --from-beginning +  --timeout-ms 5000 +  --property print.offset=true +  --consumer-property isolation.level=read_committed'

8. 놓치기 쉬운 함정

  • Append 성공 ≠ transaction commit: 개별 send ack 뒤에도 abort될 수 있다.
  • Abort ≠ disk 삭제: Bytes와 replication 비용은 남고 read_committed가 index/marker로 숨긴다.
  • read_committed ≠ snapshot isolation: 여러 partitions을 한 poll에서 동시에 모두 받는다는 보장이 아니다.
  • LSO ≠ HW: Open transaction이 있으면 replica는 다 따라왔어도 reader가 멈출 수 있다.
  • Random transactional.id: 이전 session recovery/fencing을 잃고 transaction metadata cardinality를 폭증시킨다.
  • Shared transactional.id: 정상 replicas끼리 서로 fence한다.
  • Timeout 후 반대 연산: Commit timeout 뒤 abort를 호출하면 unknown outcome을 더 복잡하게 만든다.
  • 외부 DB까지 EOS 확대: Kafka coordinator는 DB row나 HTTP 결제를 rollback하지 못한다.
  • Offset 값: 처리 완료한 마지막 offset이 아니라 다음에 소비할 offset을 transaction에 넣는다.

9. 대기업 기술 면접 질문

Q1. read_committed consumer가 HW까지 읽지 못하는 상황을 내부 구조로 설명하라.

좋은 답변 구조: HW=replication 안전 경계와 LSO=transaction 안정 경계를 분리 → first open transaction 수치 예시 → 뒤의 일반 record도 offset 순서 때문에 보류 → commit/abort marker와 aborted index → HW-LSO·open txn age 관측 → timeout/fencing 복구를 제시한다.

Q2. commitTransaction이 timeout됐다. abort 후 재시도하면 되는가?

좋은 답변 구조: Timeout은 실패 확정이 아니라 response 미수신 → coordinator에 commit 결정이 기록됐을 수 있음 → 같은 commit retry 또는 producer close라는 API 계약 → 새 instance initTransactions recovery → stable event ID와 read_committed로 결과 판별 → 반대 연산 금지를 말한다.

Q3. Kafka→Kafka exactly-once 파이프라인을 설계하고 범위를 방어하라.

좋은 답변 구조: Input/output topics·partitions·처리량 가정 → stable per-task transactional.id → auto commit off → output + nextOffsets + group metadata 동일 txn → read_committed downstream → RF/min ISR/timeout → rebalance fencing → 외부 DB는 outbox/inbox·idempotency로 별도 해결한다.

10. 복습과 정답

어제 내용 회상 3문제

  1. Heartbeat와 max poll이 각각 어떤 liveness를 감시하는가?
  2. Static member가 max poll을 넘긴 뒤 partition 재할당이 지연되는 이유는?
  3. Kafka 4.3에서 Classic과 Consumer protocol의 heartbeat/session 설정 주체는?
어제 정답/채점: ① Coordinator 통신/session 생존 대 application poll progress(2점). ② Stable identity를 session timeout까지 보존해 짧은 재시작을 흡수하지만 crash RTO가 늘어남(2점). ③ Classic은 client, Consumer protocol은 broker group config(2점).

오늘 확인 문제 3개

  1. Transaction coordinator와 partition leader가 각각 소유하는 상태는?
  2. Offset 109에서 open transaction, HW=120이면 read_committed가 113의 일반 record도 보류하는 이유는?
  3. Consume-transform-produce에서 output과 input offset을 원자화하려면 어떤 조건이 필요한가?
오늘 정답/채점: ① Coordinator는 transactional.id·PID/epoch·상태·참여 집합·결정, leader는 data/control batch·marker·aborted index(3점). ② Offset 순서를 지키며 LSO가 first open txn 앞에 있으므로 뒤 record도 안정화 전 반환하지 않음(2점). ③ Stable transactional.id, output send와 nextOffsets/group metadata를 같은 transaction에, auto/manual commit off, downstream read_committed(3점). 총 8점 중 6점 이상 통과.
