APACHE KAFKA 4.3 · WEEK 6 / DAY 37 · FORMAT & COMPATIBILITY

Avro/Protobuf/JSON, compatibility 정책

포맷 선택보다 중요한 writer/reader 방향과 무중단 진화 규칙 · 이론 75분 + 실습 30분

한 줄 요약
Avro·Protobuf·JSON 중 “최고의 포맷”을 고르는 문제가 아니다. 과거 bytes를 누가 언제 읽어야 하는지 정의하고, writer schema와 reader schema의 조합을 CI에서 검증하며, reader-first rollout과 replay horizon을 지키는 것이 진짜 compatibility 설계다.

1. 선수 용어 사전

Writer schemaRecord를 bytes로 만들 때 producer가 사용한 구조 명세. 과거 data를 해석하려면 당시 writer schema를 알아야 하는 포맷이 있다.
Reader schemaConsumer가 bytes를 현재 객체로 복원할 때 기대하는 구조 명세.
Backward compatible새 reader가 옛 writer의 data를 읽을 수 있음. Consumer를 새 version으로 먼저 배포할 때 중요하다.
Forward compatible옛 reader가 새 writer의 data를 읽을 수 있음. Producer가 먼저 바뀌거나 구 consumer가 오래 남을 때 중요하다.
Full compatibleBackward와 forward를 모두 만족. 의미 호환성까지 자동 보장한다는 뜻은 아니다.
Transitive후보 schema를 최신 하나가 아니라 보존된 모든 과거 version과 검사하는 정책.
Unknown fieldWriter에는 있지만 reader가 모르는 field. 무시·보존·오류 중 어떤 동작인지 format과 library 설정에 따라 다르다.
Default valueWriter data에 field가 없을 때 reader가 채우는 값. Write 시 항상 저장되는 값과 혼동하면 안 된다.
Field numberProtobuf binary wire에서 field identity가 되는 정수 tag. 이름보다 번호가 핵심이며 사용 후 재사용하면 안 된다.
Schema fingerprint정규화된 schema에서 계산한 식별값. Text whitespace가 달라도 같은 구조를 식별하는 데 쓸 수 있다.

2. 왜 중요한가

Kafka topic은 retention 동안 여러 producer version이 쓴 records를 함께 보존한다. 오늘 새 schema로 배포해도 어제 schema로 쓴 bytes는 사라지지 않는다. Consumer group을 reset하거나 신규 consumer가 earliest에서 시작하면 수개월 전 writer schema와 오늘 reader schema가 만난다.

Rolling deployment 중에는 old producer/new producer와 old consumer/new consumer가 동시에 존재한다. 따라서 “현재 producer와 현재 consumer가 통과한다”는 테스트만으로는 부족하다. 안전성은 writer version × reader version × 실제 rollout 순서 × replay 기간의 곱으로 결정된다.

또한 syntax compatibility와 semantic compatibility는 다르다. amount를 long 그대로 두고 단위를 원에서 센트로 바꾸면 schema 검사는 통과하지만 정산은 틀린다. 그래서 registry의 구조 검사와 domain contract review, data quality 관측이 모두 필요하다.

Avro: writer schema와 reader schema를 함께 푼다

Avro binary에는 field name과 type 정보가 반복되지 않는다. Reader는 writer schema를 확보하고 자기 reader schema와 resolution한다. Writer에만 있는 field는 reader가 무시할 수 있고, reader에만 있는 field는 default가 있으면 채울 수 있다. Default가 없는 새 reader field가 old writer data에 없으면 오류다.

Field 순서는 schema resolution에서 이름으로 맞출 수 있지만 binary bytes 자체는 writer schema 순서를 따른다. Enum symbol 삭제, union branch 변경, decimal precision/scale 변경은 단순 field 추가보다 위험하다. Alias는 rename migration을 도울 수 있지만 domain 의미 변화까지 해결하지 않는다.

Protobuf: 이름보다 field number가 wire identity다

Binary wire에는 field number와 wire type이 기록된다. 새 고유 번호의 optional field 추가는 old reader가 unknown field로 다룰 수 있어 일반적으로 안전한 변화다. 반면 기존 번호를 다른 의미로 재사용하면 같은 bytes가 다른 field로 해석되어 corruption이나 민감정보 노출까지 이어질 수 있다. 삭제한 번호와 이름은 reserved로 남긴다.

Proto3 binary는 unknown fields를 보존할 수 있지만 field-by-field 객체 복사나 ProtoJSON 변환을 거치면 유실될 수 있다. Binary compatibility와 ProtoJSON compatibility는 동일하지 않다. Presence가 필요한 scalar는 optional을 명시해 “미설정”과 zero value를 구분한다.

JSON: 스스로 보이는 것과 contract가 있는 것은 다르다

JSON에는 field name과 primitive token이 보여 debug가 쉽다. 하지만 required, additionalProperties, number 범위, string format을 강제하려면 JSON Schema와 validator 정책이 필요하다. Old reader가 unknown field를 거부하면 optional field 추가도 forward-incompatible할 수 있다.

JSON number는 consumer 언어의 숫자 모델에 따라 정밀도가 달라질 수 있다. 64-bit ID를 JavaScript number로 읽으면 정확성을 잃을 수 있어 string contract를 선택하기도 한다. 사람이 읽을 수 있다는 사실은 안정적인 type system을 뜻하지 않는다.

Best practice: Schema file을 application code와 함께 version control하고 PR에서 owner review·compatibility test·golden bytes test를 수행한다. Consumer를 먼저 배포해 old+new fixture를 읽히고, producer canary를 통해 deserialization error·unknown enum·business invariant 지표를 본 뒤 확대한다.

Change checklist: Field 추가/삭제/rename/type 변경, nullability/default, enum, logical type·단위, key bytes, schema identity, generated code version, unknown-field policy, retry/quarantine, rollback writer, retention/replay 기간, downstream catalog를 모두 검토한다.

Version/engine 차이: Kafka 4.3.1 core는 Java primitive/basic Serde를 제공하지만 Avro/Protobuf/JSON registry compatibility 정책은 Kafka broker의 내장 보장이 아니다. Registry product와 serializer integration에 따라 subject naming, ID envelope, cache, auto-registration, reference 동작이 다르므로 운영 중인 구현 문서를 별도로 고정해야 한다.

Anti-pattern: Production producer가 권한 없이 schema auto-register, compatibility를 NONE으로 잠시 풀고 복구하지 않음, default에 business 의미 숨김, Protobuf number 재사용, JSON unknown field strictness 미테스트, 최신 두 version만 fixture test, schema rollback 없이 application만 rollback.

7. 20~40분 실습: backward·forward·transitive를 코드로 판정

목표: Python 표준 라이브러리만으로 writer/reader 조합을 만들고, “새 reader가 old data를 읽는다”와 “old reader가 new data를 읽는다”를 직접 구분한다. 이어 latest 검사는 통과하지만 transitive 검사는 실패하는 schema chain을 재현한다.

사전 조건: 저장소 root와 Python 3. Kafka broker는 이 실험에서 bytes를 해석하지 않으므로 실행하지 않아도 된다. 약 30분.

0) 실행 전 예측

  1. 새 reader가 새 field currency에 default를 가지면 old data를 읽을 수 있는가?
  2. Old reader가 unknown field를 거부하면 new writer data를 읽을 수 있는가?
  3. Candidate가 직전 schema와 compatible이면 모든 과거 data도 안전한가?

1) Backward와 forward를 반대 방향으로 실행

python3 - <<'PY'
old_data={"order_id":"o-1","amount":12000}
new_data={"order_id":"o-2","amount":9000,"currency":"KRW"}

def new_reader(x):
    allowed={"order_id","amount","currency"}
    assert set(x)<=allowed
    return {"order_id":x["order_id"],"amount":x["amount"],"currency":x.get("currency","KRW")}

def old_reader_strict(x):
    allowed={"order_id","amount"}
    unknown=set(x)-allowed
    assert not unknown, f"unknown={unknown}"
    return {"order_id":x["order_id"],"amount":x["amount"]}

print("BACKWARD new_reader<-old_data",new_reader(old_data))
try:
    old_reader_strict(new_data)
except AssertionError as e:
    print("FORWARD FAIL old_reader<-new_data",e)
PY

예상: 새 reader는 default로 old data를 읽어 backward 통과한다. Strict old reader는 currency를 unknown으로 거부해 forward 실패한다. JSON에 field name이 보인다고 자동 호환되는 것이 아니다.

2) Reader 정책 하나가 결과를 바꾸는지 확인

python3 - <<'PY'
new_data={"order_id":"o-2","amount":9000,"currency":"KRW"}
def old_reader_tolerant(x):
    return {"order_id":x["order_id"],"amount":x["amount"]}
print("FORWARD PASS",old_reader_tolerant(new_data))
PY

예상: Unknown field를 무시하는 reader에서는 같은 field 추가가 forward-compatible하다. 변화의 안전성은 schema diff만 아니라 실제 reader policy에 달려 있다.

3) Latest-only 통과, transitive 실패 재현

python3 - <<'PY'
v1={"fields":{"customer_id"},"defaults":set()}
v2={"fields":{"customer_id","buyer_id"},"defaults":{"buyer_id"}}
v3={"fields":{"buyer_id"},"defaults":set()}

def backward(reader,writer):
    missing=reader["fields"]-writer["fields"]
    return missing<=reader["defaults"],missing

print("v2 reads v1",backward(v2,v1))
print("v3 reads latest v2",backward(v3,v2))
print("v3 reads historical v1",backward(v3,v1))
assert backward(v3,v2)[0] and not backward(v3,v1)[0]
print("LATEST=PASS, TRANSITIVE=FAIL")
PY

예상: v2는 default로 v1을 읽고, v3는 직전 v2의 buyer_id를 읽는다. 하지만 v3는 v1에 없는 buyer_id의 default를 제거했으므로 v1 replay에 실패한다. Version별 pair가 연속 통과해도 compatibility가 자동으로 추이적이지는 않다.

4) 실패 주입과 복구 설계

실패 주입: v3를 latest-only gate로 승인했다고 가정하고 v1 fixture를 reader test에 넣는다. TRANSITIVE=FAIL을 incident evidence로 기록한다.

안전한 복구: v3 reader에 buyer_id default/alias 변환을 유지하거나, v1→v3 bridge backfill을 별도 topic으로 수행한다. 과거 schema와 data를 삭제해서 test를 통과시키지 않는다.

8. 놓치기 쉬운 함정

  • Backward 방향 반대로 외우기: 새 reader가 old data를 읽는 방향부터 문장으로 쓴다.
  • Latest-only chain: v3↔v2와 v2↔v1 통과가 v3↔v1 통과를 보장하지 않는다.
  • Default의 의미: Avro default는 missing field를 read할 때 쓰이며 모든 write에 자동 저장되는 값이 아니다.
  • Protobuf number 재사용: 이름을 바꿔도 동일 번호는 wire에서 같은 identity다. 삭제 번호를 reserve한다.
  • Binary와 JSON 혼동: Protobuf binary-safe change가 ProtoJSON에서도 safe하다고 단정하지 않는다.
  • JSON 자유 형식: additionalProperties와 unknown-field parser 설정 없이는 field 추가 결과가 팀마다 다르다.
  • Enum 추가/삭제: 언어 binding과 old reader의 unknown enum 처리까지 확인한다.
  • Semantic drift: 이름·type이 같아도 단위·timezone·정의가 바뀌면 breaking change다.
  • Registry가 single point: Lookup cache, timeout, ACL, backup, history immutability와 장애 시 신규 등록 정책이 필요하다.

9. 대기업 기술 면접 질문

Q1. Avro, Protobuf, JSON 중 무엇을 선택하겠는가?

좋은 답변 구조: 먼저 consumer 언어·replay 기간·debug·size/CPU·schema governance 요구를 수치화 → 세 format의 wire identity와 tooling 비교 → key/value를 분리 → compatibility/rollout/error path → benchmark와 조직 운영 비용으로 결론을 방어한다.

Q2. Backward compatible이면 무중단 배포가 항상 가능한가?

좋은 답변 구조: Backward 방향 정의 → rolling 중 old reader와 new writer가 만나는 forward 방향 지적 → reader-first 전제와 fleet readiness → semantic change·key schema·transitive replay 예외 → canary·rollback·quarantine을 제시한다.

Q3. Schema v1→v2→v3가 매 단계 통과했는데 과거 replay가 실패했다. 원인은?

좋은 답변 구조: Latest-only vs transitive 구분 → 최초 실패 offset의 writer schema ID 확인 → version graph와 default/alias/field number 분석 → bridge reader 또는 backfill 복구 → transitive CI와 golden bytes fixture 도입까지 말한다.

10. 복습과 정답

어제 내용 회상 3문제

  1. Kafka broker가 업무 객체의 field type을 직접 검증하지 않는 이유는?
  2. Key serializer 변경이 value serializer 변경보다 더 위험할 수 있는 이유는?
  3. Poison pill 대응 시 보존해야 할 최소 evidence는?
어제 정답/채점: ① Broker는 serializer 결과인 opaque bytes를 저장하고 type은 client contract에 있기 때문(2점). ② Key bytes hash가 partition·ordering·join locality를 결정하기 때문(3점). ③ Topic/partition/offset, key, schema ID/version, exception, PII-safe 원본 bytes 또는 hash(3점).

오늘 확인 문제 3개

  1. Backward와 forward compatibility를 reader/writer 문장으로 각각 써라.
  2. Avro field default와 Protobuf field number에서 가장 흔한 함정은?
  3. Latest-only 검사와 transitive 검사의 운영상 차이는?
오늘 정답/채점: ① 새 reader←old writer가 backward, old reader←new writer가 forward(3점). ② Avro default는 read resolution용이며, Protobuf number는 재사용 금지 wire identity(3점). ③ Latest는 직전 version만, transitive는 모든 보존 history와 검사해 오래된 replay를 보호(3점). 총 9점 중 7점 이상이면 통과.
