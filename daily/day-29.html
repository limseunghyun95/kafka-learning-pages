APACHE KAFKA 4.3 · WEEK 5 / DAY 29 · GROUP COORDINATION

group coordinator와 generation

Consumer group의 권한자·상태 머신·zombie fencing · 이론 70분 + 실습 30분

한 줄 요약
Group coordinator는 group.id별 membership·assignment·committed offset의 권한자이고, generation은 “현재 assignment 계약의 버전”이다. Rebalance 뒤 이전 generation의 member가 늦게 offset을 덮어쓰지 못하게 coordinator가 fencing한다.

1. 선수 용어 사전

Consumer group같은 group.id를 공유하고 topic partition을 나눠 처리하는 consumer 집합. 한 group 안에서 partition 하나의 현재 소유자는 한 member여야 한다.
Coordinator여러 참여자가 하나의 상태에 합의하도록 순서를 정하는 권한자. Kafka의 group coordinator는 broker 역할이며 KRaft controller와 다르다.
Group coordinator특정 group의 member·subscription·assignment·offset 요청을 처리하는 broker. 해당 group이 매핑된 __consumer_offsets partition leader가 역할을 맡는다.
GenerationClassic protocol에서 한 번의 안정된 membership·assignment 라운드를 식별하는 정수 버전. Record offset도 시간도 아니다.
Member IDCoordinator가 consumer incarnation에 부여하는 식별자. Process 이름이나 client.id와 같다고 가정하면 안 된다.
Group leaderClassic protocol에서 coordinator가 고른 member. Member metadata를 받아 client-side assignor로 assignment를 계산한다. Partition leader나 controller가 아니다.
Assignment어느 member가 어떤 topic partition을 소비할지 정한 소유권 표. Subscription은 희망 목록이고 assignment는 실제 권한이다.
RebalanceMembership·subscription·partition metadata가 바뀌어 assignment를 다시 계산하고 설치하는 상태 전이.
HeartbeatMember가 살아 있고 현재 group 계약에 참여 중임을 coordinator에 갱신하는 liveness 신호. 처리 성공 신호는 아니다.
Fencing오래된 권한을 가진 process의 요청을 거부하는 안전장치. 세대 번호가 자물쇠 버전처럼 작동한다.
Zombie memberCoordinator에게는 탈퇴·timeout 처리됐지만 GC pause·network partition 뒤 다시 움직여 예전 partition을 처리하려는 process.
__consumer_offsetsGroup metadata와 committed offset을 저장하는 partitioned·replicated·compacted internal topic. 단순한 client-side 체크포인트 파일이 아니다.

2. 왜 중요한가

Consumer는 “내가 아직 partition P0의 주인인가?”를 local memory만으로 결정할 수 없다. Network 단절이나 긴 GC pause 동안 다른 member에게 P0가 넘어갈 수 있기 때문이다. Coordinator가 membership과 generation의 단일 권한자가 되어 split-brain consumer를 막는다.

실무 장애에서 lag 증가와 rebalance는 결과이지 원인이 아닐 때가 많다. Slow downstream → poll 지연 → member 제외 → generation 변경 → commit fencing → replay → downstream 부하 증가가 하나의 증폭 고리를 만든다. Coordinator의 상태 전이를 알면 timeout만 무작정 늘리지 않고 최초 병목을 찾을 수 있다.

면접에서는 “consumer끼리 partition을 나눈다”보다 누가 상태를 소유하고, 언제 assignment가 유효해지며, stale member의 commit을 어떤 필드로 거부하는지 설명해야 깊이가 드러난다.

3. Architecture: 발견부터 commit fencing까지

1 · ConsumerFindCoordinator(group.id) → 아무 broker
↓ group.id가 internal topic partition에 매핑
2 · Coordinator__consumer_offsets-N leader broker
↓ JoinGroup: member·subscription 수집
3 · Join barrier새 generation G=42 · group leader 선출
↓ leader가 assignment 계산 → SyncGroup
4 · StableCoordinator가 G=42 assignment 설치·응답
↓ Heartbeat(G=42) · processing · commit
5 · OffsetCommitgroup + member + G=42 + offsets → internal log
↓ membership 변경 → G=43
6 · Fence늦은 G=42 commit 거부 → rejoin 필요
  1. 발견: Consumer는 bootstrap broker가 coordinator라고 가정하지 않고 FindCoordinator로 현재 위치를 찾는다.
  2. 상태 배치: group.id는 internal topic partition에 안정적으로 매핑된다. 그 partition leader가 coordinator이므로 groups가 broker들에 분산된다.
  3. Join: Classic protocol의 coordinator는 join barrier 동안 member metadata를 모으고 group leader와 새 generation을 정한다.
  4. Sync: Group leader가 assignment를 계산해 보내면 coordinator가 검증·설치하고 각 member에게 자신의 assignment를 반환한다.
  5. Stable: Member는 assignment callback을 수행하고 fetch·process를 시작한다. Heartbeat는 membership lease를 유지한다.
  6. Commit과 fencing: Offset commit에 member와 generation이 실린다. Coordinator의 현재 세대와 다르면 zombie commit을 거부한다.

Member join·leave·session timeout·subscription 또는 topic partition 변화가 assignment 입력을 바꾸면 rebalance가 필요하다. 새 라운드가 확정되며 generation이 증가한다. Generation은 Lamport clock처럼 모든 사건의 전역 시간을 주는 것이 아니라 이 group assignment의 stale authority를 구분하는 epoch다.

Fencing이 없으면 A의 늦은 commit이 120을 110으로 되돌려 110~119를 재처리하거나, 더 위험하게 처리하지 않은 미래 offset을 써서 유실을 만들 수 있다. Generation과 member ID 검사는 “현재 소유권을 증명하지 못한 요청은 상태를 바꾸지 못한다”는 불변식을 지킨다.

공식 구현 설명상 coordinator는 offset commit을 __consumer_offsets에 append하고 replicas가 받기 전에는 성공을 반환하지 않는다. 다만 성공 응답이 network에서 유실되면 client에는 결과 불명이다. 재시도는 가능하지만 async commit callback 순서 역전으로 더 작은 offset을 덮어쓰지 않도록 관리해야 한다.

오늘의 “generation” 설명은 Classic의 정확한 용어다. 새 Consumer protocol도 같은 목적의 epoch fencing을 갖지만 state model과 API가 다르다. 내일 두 protocol을 global barrier·incremental reconciliation·설정 소유권 관점에서 비교한다.

Anti-pattern: Coordinator를 KRaft controller로 설명하기, heartbeat 성공을 business 처리 성공으로 해석하기, CommitFailedException을 무한 retry하기, group마다 무작위 UUID를 붙여 internal topic cardinality를 폭증시키기, 같은 group.id를 무관한 pipeline이 공유하기.

Edge case: Coordinator broker가 바뀌면 client는 rediscover하고 새 coordinator가 internal topic partition을 replay해 cache를 복구한다. 이때 NOT_COORDINATOR·COORDINATOR_LOAD_IN_PROGRESS는 짧게 retriable할 수 있지만 deadline·backoff·jitter가 필요하다.

Version 판단: Kafka 4.3의 Java consumer는 Classic이 기본이고 Consumer protocol은 명시적으로 켠다. 새 protocol에서는 heartbeat interval과 session timeout, assignor 소유권이 broker 쪽으로 이동하므로 Classic tuning을 그대로 복사하지 않는다.

7. 30분 실습: generation fencing을 상태 전이로 관찰

실행 전 예측
Consumer A·B가 각각 2 partitions를 가진 상태에서 A를 session timeout보다 오래 멈추면 B가 4 partitions를 얻는다. A가 다시 움직여도 예전 generation 권한으로 계속 처리하지 못하고 rejoin해야 한다. 숫자 generation은 CLI가 직접 노출하지 않아도 assignment 변화와 log로 fencing 결과를 추론할 수 있다.

사전 조건: Docker, 저장소의 공식 Apache Kafka 4.3.1 단일 KRaft broker. 기본 실습 broker 외 다른 자원은 건드리지 않는다.

Step 1 · Broker와 4-partition topic 준비

make up docker compose exec broker /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server localhost:9092 --create --if-not-exists \ --topic day29.group --partitions 4 --replication-factor 1

예상: Topic 생성 성공. 단일 broker라 coordinator failover가 아니라 member generation 전이에 집중한다.

Step 2 · Classic consumer A·B를 background로 시작

docker compose exec broker bash -lc ' nohup /opt/kafka/bin/kafka-console-consumer.sh \ --bootstrap-server localhost:9092 --topic day29.group \ --group day29-generation --from-beginning \ --consumer-property group.protocol=classic \ --consumer-property session.timeout.ms=10000 \ --consumer-property heartbeat.interval.ms=3000 \ --consumer-property auto.commit.interval.ms=1000 \ --property print.partition=true --property print.offset=true \ >/tmp/day29-a.log 2>&1 & echo $! >/tmp/day29-a.pid' docker compose exec broker bash -lc ' nohup /opt/kafka/bin/kafka-console-consumer.sh \ --bootstrap-server localhost:9092 --topic day29.group \ --group day29-generation --from-beginning \ --consumer-property group.protocol=classic \ --consumer-property session.timeout.ms=10000 \ --consumer-property heartbeat.interval.ms=3000 \ --consumer-property auto.commit.interval.ms=1000 \ --property print.partition=true --property print.offset=true \ >/tmp/day29-b.log 2>&1 & echo $! >/tmp/day29-b.pid' sleep 8 docker compose exec broker /opt/kafka/bin/kafka-consumer-groups.sh \ --bootstrap-server localhost:9092 --describe \ --group day29-generation --members --verbose

예상: Stable group에 members 2개, 각 member에 약 2 partitions가 배정된다. Consumer ID는 process PID나 client ID와 다른 coordinator 발급 member ID다.

Step 3 · Record와 offset baseline 고정

for i in 1 2 3 4 5 6 7 8; do printf 'event-%02d\n' "$i"; done | \ docker compose exec -T broker /opt/kafka/bin/kafka-console-producer.sh \ --bootstrap-server localhost:9092 --topic day29.group sleep 5 docker compose exec broker /opt/kafka/bin/kafka-consumer-groups.sh \ --bootstrap-server localhost:9092 --describe \ --group day29-generation --offsets docker compose exec broker /opt/kafka/bin/kafka-consumer-groups.sh \ --bootstrap-server localhost:9092 --describe \ --group day29-generation --state

예상: Four partition offsets가 전진하고 lag가 0에 가까워진다. State는 Stable, member 수는 2다.

Step 4 · 실패 주입: A를 session timeout보다 오래 정지

docker compose exec broker bash -lc \ 'kill -STOP $(cat /tmp/day29-a.pid)' sleep 15 docker compose exec broker /opt/kafka/bin/kafka-consumer-groups.sh \ --bootstrap-server localhost:9092 --describe \ --group day29-generation --members --verbose docker compose exec broker /opt/kafka/bin/kafka-consumer-groups.sh \ --bootstrap-server localhost:9092 --describe \ --group day29-generation --state

예상: Coordinator가 A session을 만료시키고 새 generation을 만든다. B 한 명이 4 partitions를 소유한다. “A process가 존재한다”와 “A가 group member다”는 다르다.

Step 5 · Zombie A 재개와 rejoin 관찰

docker compose exec broker bash -lc \ 'kill -CONT $(cat /tmp/day29-a.pid)' sleep 10 docker compose exec broker /opt/kafka/bin/kafka-consumer-groups.sh \ --bootstrap-server localhost:9092 --describe \ --group day29-generation --members --verbose docker compose exec broker bash -lc \ 'tail -n 40 /tmp/day29-a.log'

예상: A의 오래된 heartbeat·commit 권한은 그대로 인정되지 않는다. Client가 group에 다시 join하면서 또 새 generation과 assignment가 설치되고, 최종적으로 members 2개·약 2 partitions씩으로 수렴한다. Client log level에 따라 explicit generation error가 숨겨질 수 있으므로 member/assignment state transition을 1차 증거로 삼는다.

오류 해석과 cleanup

자주 나는 오류: Session timeout 범위를 벗어나면 broker의 group.min/max.session.timeout.ms 범위를 확인한다. Group이 Empty면 PID와 log를 확인하되 broker를 재시작하지 않는다. Lag가 남으면 producer record가 어떤 partition에 들어갔는지와 auto commit interval을 본다. Shell이 $!를 먼저 확장하지 않도록 single quote를 유지한다.

docker compose exec broker bash -lc ' for f in /tmp/day29-a.pid /tmp/day29-b.pid; do test -f "$f" && kill -TERM $(cat "$f") 2>/dev/null || true done rm -f /tmp/day29-a.log /tmp/day29-b.log \ /tmp/day29-a.pid /tmp/day29-b.pid' docker compose exec broker /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server localhost:9092 --delete --topic day29.group

Cleanup은 day29- consumer process·log와 day29.group topic만 정리한다. Shared broker와 volume은 유지한다.

8. 놓치기 쉬운 함정

  • Coordinator = controller: Group coordinator는 internal topic partition leader인 broker 역할이고 KRaft controller와 다르다.
  • Generation = offset: Generation은 assignment 계약 버전, offset은 partition log 위치다.
  • Heartbeat = 처리 성공: Member liveness만 증명한다. Poll·DB latency와 data quality는 별도다.
  • Join 성공 = 처리 시작: SyncGroup과 assignment 설치 전에는 partition 소유권이 완성되지 않았다.
  • Commit 성공 = DB 원자성: Kafka offset durability와 외부 side effect는 서로 다른 transaction boundary다.
  • CommitFailed 무한 retry: Generation을 잃었다면 먼저 처리를 멈추고 새 assignment를 확인해야 한다.
  • Coordinator 한 대 병목: 모든 groups가 한 broker로 가지 않고 group.id별 internal partitions에 분산되지만 hot coordinator partition은 가능하다.
  • Classic 설정을 Consumer protocol에 복사: 새 protocol은 heartbeat·session·assignor의 소유자가 다르다.

9. 대기업 기술 면접 질문 3개

Q1. Group coordinator는 어떻게 정해지고 장애 시 어떻게 복구됩니까?
좋은 답변 구조: group.id→__consumer_offsets partition mapping → 그 partition leader broker가 coordinator → FindCoordinator로 발견 → coordinator failover 시 client rediscovery → internal log replay·cache load → load-in-progress/backoff → offsets와 membership의 replicated state, KRaft controller와 역할 분리.

Q2. Generation이 없으면 어떤 장애가 생깁니까?
좋은 답변 구조: A가 P0 처리 중 GC pause → session 만료·P0가 B로 재배정 → B가 offset 120 commit → A가 깨어나 offset 110/미래 offset commit → 중복 또는 유실 → generation/member fencing으로 stale mutation 거부 → side effect는 sink idempotency가 추가로 필요.

Q3. Consumer lag와 rebalance가 동시에 증가합니다. 어떻게 진단합니까?
좋은 답변 구조: lag slope·input/processing rate 수치화 → member churn·group state·heartbeat/poll gap → GC/deploy/network/sink latency timeline → coordinator 이동 여부 분리 → 유입 제한·원인 member 격리·sink 복구 → timeout 변경은 가설 검증 후 → Stable generation·assignment·end-to-end SLO로 종료.
