APACHE KAFKA 4.3 · WEEK 3 / DAY 17 · PRODUCER PIPELINE

in-flight request와
ordering 조건

여러 요청을 겹쳐 보내는 성능 이득과 retry 순서 역전의 경계 · 이론 55분 + 실습 35분

한 줄 요약
max.in.flight.requests.per.connection은 한 broker connection에서 응답을 기다리는 ProduceRequest 수의 상한이다. 값을 키우면 네트워크 왕복 대기 시간을 겹쳐 throughput을 높이지만, idempotence를 끈 채 retry와 2개 이상의 in-flight를 함께 쓰면 먼저 보낸 batch가 나중에 기록되는 순서 역전이 가능하다. Kafka 4.3의 idempotent producer는 sequence 검증으로 허용 범위 5 안에서 partition ordering을 보존한다.

1. 선수 용어 사전

In-flight requestclient가 socket으로 보냈지만 아직 response를 받지 못한 요청. 실패했다는 뜻이 아니라 결과가 미확정인 진행 중 상태다.
Connectionproducer와 특정 broker node 사이의 지속 TCP 연결. 설정 상한은 producer 전체나 partition별이 아니라 connection별이다.
Pipelining이전 응답을 기다리지 않고 다음 요청을 보내 대기 시간을 겹치는 기법. CPU pipeline이나 HTTP pipelining과 같은 지연 숨기기 원리다.
OrderingKafka에서는 같은 topic-partition log에 append된 record의 순서. 서로 다른 partition 사이에는 전역 순서를 약속하지 않는다.
Retry일시 오류나 응답 유실 뒤 같은 전송을 다시 시도하는 것. 재시도 횟수보다 전체 delivery.timeout.ms deadline이 실무 경계다.
Head-of-line blocking앞선 작업 하나가 지연되어 뒤 작업까지 진행하지 못하는 현상. in-flight=1은 순서가 단순하지만 한 요청의 RTT가 pipeline 전체를 멈춘다.
RTTRound Trip Time. 요청이 broker에 갔다가 응답이 돌아오는 왕복 시간이다.
Batch같은 partition의 여러 record를 묶은 압축·전송·append 단위. 하나의 ProduceRequest에는 여러 partition batch가 함께 실릴 수도 있다.
IdempotencePID·epoch·partition별 sequence로 retry batch의 중복과 순서를 broker가 판별하는 producer 보장이다.
Backpressuredownstream이 느릴 때 upstream 전송을 제한해 무한 적체를 막는 압력. in-flight 상한은 network client의 bounded concurrency다.

2. 왜 중요한가

요청 하나를 처리하는 데 RTT 10ms가 걸리고 매번 응답 뒤에만 다음 요청을 보낸다면 단순 상한은 초당 약 100 request다. in-flight를 5로 늘리면 다섯 RTT 대기를 겹칠 수 있다. 실제 처리량은 batch 크기·broker disk/network·quota에도 묶이지만, 대기 시간을 겹쳐 link utilization을 높인다는 핵심은 같다.

문제는 실패 경로다. batch A를 먼저 보내고 B를 뒤에 보낸 상태에서 A만 실패하고 B는 성공하면, idempotence가 꺼져 있을 때 A retry가 B 뒤에 append될 수 있다. 평상시 부하 테스트에서는 잘 보이지 않고 timeout·leader change·packet loss 때만 나타나므로 실무 사고와 면접 모두에서 좋은 경계 질문이다.

3. Architecture: 두 batch가 순서를 잃는 순간

1 · Accumulator같은 P0에 batch A=[1,2], B=[3,4]가 순서대로 ready
↓ in-flight 상한이 2 이상이라 응답 전에 연속 전송
2 · SocketProduceRequest A → ProduceRequest B → 같은 broker TCP connection
↓ A는 retriable error/응답 유실 · B는 성공
3 · Broker logidempotence=false라면 B=[3,4]가 먼저 append
↓ backoff 뒤 A retry
4 · Reorder최종 log [3,4,1,2] — producer 호출 순서와 달라짐
↓ idempotence=true면 partition sequence 검증
5 · Preservesequence gap을 허용하지 않고 retry/dedup하여 A → B ordering 보존
  1. Sender thread: partition별 ready batch를 고르고 broker node별 ProduceRequest를 만든다.
  2. NetworkClient: connection의 미응답 요청 수가 상한보다 작을 때 다음 request를 보낸다. 상한에 닿으면 그 node 전송이 대기한다.
  3. Failure window: TCP 전송 순서와 애플리케이션 성공 확정 순서는 동일 개념이 아니다. broker별·partition별 응답과 retry가 갈라진다.
  4. Non-idempotent: broker에 batch 간 인과관계를 증명할 sequence가 없으므로 늦은 retry를 정상 새 append로 볼 수 있다.
  5. Idempotent: 어제 배운 PID·epoch·sequence가 A의 누락과 B의 gap을 감지한다. 허용되는 max.in.flight≤5에서는 ordering을 유지한다.

왜 상한은 “record 수”가 아니라 “request 수”인가

Kafka protocol의 ProduceRequest는 broker node 하나를 대상으로 하며 여러 topic-partition batch를 포함할 수 있다. 따라서 값 5는 record 5개나 partition마다 batch 5개라는 뜻이 아니다. 한 connection에서 response가 돌아오지 않은 protocol request가 최대 5개라는 뜻이다. batch 크기와 request당 partition 수가 달라지면 같은 설정에서도 메모리·wire bytes·risk exposure가 달라진다.

Little's Law로 보는 처리량

안정 상태에서 동시 진행 수 L ≈ 처리량 λ × 체류시간 W다. RTT와 broker 처리시간을 합친 W가 20ms이고 초당 200 request를 원하면 평균 in-flight는 약 4가 필요하다. 이는 설계 출발점일 뿐이다. batch당 bytes, compression CPU, broker request queue, quota를 함께 측정해야 하며 상한을 무작정 키우면 memory와 tail latency만 커질 수 있다.

idempotence를 의도적으로 끔retry가 있고 partition ordering이 필수면 in-flight=1순서 안전 대신 RTT당 한 요청으로 throughput 감소.

p99 지연 상승먼저 request latency/queue, batch, throttling, retry rate 측정상한 증가는 포화 원인을 가리고 queueing을 키울 수 있다.

Best practice: 설정 하나를 튜닝하지 말고 batch.size·linger.ms·compression·delivery.timeout.ms·retry rate와 함께 부하 실험한다. 같은 key가 같은 partition에 간다는 contract를 schema/producer test로 고정하고 callback 오류를 관측한다.

Anti-pattern: “in-flight=1이면 exactly-once”라고 생각하기, consumer 처리 순서를 producer 설정으로 해결하려 하기, 오류 callback을 버리고 성공 건수만 보기, 더 큰 concurrency가 항상 더 빠르다고 가정하기.

Version 경계: Kafka 4.3 공식 설정에서 idempotence는 충돌 설정이 없으면 기본 활성화되고 acks=all·retries>0·max.in.flight≤5가 필요하다. 5보다 크게 명시하면 idempotence 조건과 충돌한다. 향후 제안 상태 KIP의 내용은 현재 배포 동작으로 단정하지 않는다.

7. 35분 실습: 실패 경로의 순서를 증거로 남기기

실행 전 예측
정상 경로에서는 in-flight=1과 5 모두 key 순서를 유지한다. 따라서 단순 console 출력만으로 보장을 입증할 수 없다. 어떤 실패 조건이 있어야 non-idempotent + retry + in-flight>1에서 역전 가능성이 생기는지 먼저 한 문장으로 적는다.

사전 조건: 저장소 루트, Docker 실행, 제공된 Kafka 4.3.1 KRaft broker. 아래 명령은 local 학습 cluster에만 사용한다.

  1. 환경 확인:
    make up make smoke
  2. effective 조건 표 작성: A=idempotence=true, max.in.flight=5, B=false, 1, C=false, 5를 적고 정상/response 유실에서 예상 중복·순서를 표로 예측한다.
  3. CLI producer 속성 확인:
    docker compose exec kafka /opt/kafka/bin/kafka-producer-perf-test.sh --help | head -40
  4. 기준 부하: test topic에 같은 record 수·크기로 in-flight 1과 5를 각각 실행하고 records/sec, MB/sec, avg/p99 latency를 기록한다. 명령의 --producer-props에 acks=all enable.idempotence=true max.in.flight.requests.per.connection=1을 넣고 두 번째 실행에서 마지막 값만 5로 바꾼다.
  5. 실패 주입: 별도 터미널에서 짧게 broker를 pause한 뒤 resume하여 미응답 window를 만든다.
    docker compose pause kafka docker compose unpause kafkaproducer의 retry/error와 전체 delivery deadline을 관찰한다. 같은 실행에서 반복 pause하지 않는다.
  6. 관찰: consumer에서 key, partition, offset, application sequence를 함께 출력한다. “역전이 안 나왔다”는 안전 증명이 아니라 이번 스케줄링에서 재현되지 않았다는 결과로 기록한다.

예상 관찰: in-flight=5는 RTT 대기를 겹쳐 throughput이 같거나 높을 수 있다. broker pause 동안 latency와 retry가 솟고, idempotent 구성에서는 성공한 같은-partition record의 sequence ordering이 유지된다.

자주 나는 오류와 해결: container 이름 불일치는 docker compose ps로 확인한다. idempotence=false인데 acks=all만 썼다고 ordering이 생기지 않는다. perf test가 너무 빨리 끝나면 record 수를 늘리되 production broker에 실행하지 않는다. timeout이면 delivery deadline과 pause 시간을 함께 기록하고 무작정 timeout을 늘리지 않는다.

Cleanup:
docker compose unpause kafka make downpause 상태를 반드시 해제한 뒤 종료한다.

8. 놓치기 쉬운 함정

  • 호출 순서 ≠ 전역 Kafka 순서: ordering은 같은 partition에서만 논할 수 있다.
  • TCP ordered delivery ≠ retry ordering: 재연결·새 request·broker 처리 결과가 포함되면 application-level 순서 문제가 남는다.
  • 5는 partition별 5가 아니다: broker connection별 unacknowledged request 상한이다.
  • in-flight=1은 중복을 제거하지 않는다: response 유실 후 non-idempotent retry는 같은 batch를 다시 append할 수 있다.
  • idempotence도 업무 순서를 발명하지 않는다: key가 바뀌거나 partition 수 변경으로 routing이 바뀌면 별도 contract가 필요하다.
  • 성능은 단조 증가하지 않는다: broker queue가 포화되면 concurrency 증가는 p99와 memory를 악화시킨다.

9. 대기업 기술 면접 질문 3개

Q1. retries가 ordering을 깨뜨리는 정확한 조건을 그려보세요.
좋은 답변 구조: 같은 partition의 A/B batch 가정 → in-flight>1 → A 실패·B 성공 → A retry가 B 뒤 append → idempotence=false 조건 → idempotence sequence 또는 in-flight=1 대안 → throughput trade-off.

Q2. max.in.flight=1과 5를 어떻게 선택하겠습니까?
좋은 답변 구조: ordering scope와 client version 확인 → idempotence 사용 여부 → RTT·목표 request rate로 Little's Law 추정 → batch/latency/error canary 측정 → 기본 5 유지 근거와 1의 HOL 비용 → rollback 기준.

Q3. idempotent producer인데도 사용자가 주문 상태 역전을 봤습니다. 어디부터 조사합니까?
좋은 답변 구조: 주문 ID별 event sequence와 timestamp 수집 → 실제 topic/partition/offset 확인 → key·partitioner·partition-count 변화 → producer effective config와 callback → consumer concurrency·sink upsert → Kafka partition ordering과 end-to-end 처리 순서를 분리 → 보정/replay 계획.

10. 복습과 정답

어제 내용 회상 3문제

  1. PID·epoch·sequence의 상태 key를 말해보라.
  2. response 유실 retry를 broker가 중복으로 판별하는 기준은?
  3. producer idempotence가 외부 DB 중복까지 막지 못하는 이유는?

짧은 정답: ① identity는 PID/epoch이고 sequence는 partition별이다. ② 같은 identity와 이미 수락한 batch sequence history다. ③ Kafka log append 경계의 보장이며 DB side effect·business retry에는 동일 identity가 자동 전달되지 않는다.

오늘 확인 3문제

  1. non-idempotent retry에서 순서 역전에 필요한 세 조건은?
  2. in-flight 5는 정확히 무엇을 세는가?
  3. 값을 키울 때 throughput과 p99가 어떻게 달라질 수 있는가?

채점 기준: ① 같은 partition, retries>0, in-flight>1 및 앞 batch 실패·뒤 batch 성공 failure window(3점). ② producer-broker node connection의 미응답 protocol request 수(3점). ③ RTT overlap 이득과 queueing/memory/tail-latency 비용을 함께 말하면 4점. 총 8점 이상이면 통과.
